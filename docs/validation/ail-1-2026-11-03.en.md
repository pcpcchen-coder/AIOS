# AIL-1 App Integration Layer foundation validation

Date: 2026-11-03 (Asia/Taipei). Branch: `claude/ail-1-registry`, cut from `design/app-integration-spotify-2026-11` (main `6674cec` plus George's design documents). Scope: AIL-1 in [18 §6](../18_App_Integration_Layer_and_Spotify_2026-11.en.md).

**This batch connects no real App.** The only registered Adapter is the simulated `mock`. Spotify has no tools at all: the Registry refuses to register any `app.spotify.*` tool (SP-2 BLOCKED). All tests below ran with fixtures in a Linux cloud container (fake Codex, fake page, fake realtime routes, mock Adapter). **They are not Mac runs and involve no real voice.**

## 1. Deliverables

All paths are under `prototype/ambient-shell/`.

| File | Contents |
|---|---|
| `shared/integrations.ts` (new) | `EffectClass`, `IntegrationRoute` (api_key/live/text/background), `CapabilityStatus`; a unified `ToolResult` whose `ok` is always derived from `status`, so only `confirmed` is true; fixed reason codes; tool IDs `app.<service>.<action>` and the model-facing function names `app__<service>__<action>`, which map back and forth; on-demand status types |
| `server/integrations/contracts.ts` (new) | `IntegrationAdapter`, `ToolDefinition` (with `supportedRoutes` and `timeoutMs`), `ExecutionContext` (with a request-id and an abort signal) |
| `server/integrations/schema.ts` (new) | A schema subset with no new dependency: Adapter schemas are checked at registration, and model arguments are validated at call time. Only flat objects, the listed types and `additionalProperties:false` are accepted; error messages never echo argument values |
| `server/integrations/registry.ts` (new) | Checks duplicate IDs, schemas, versions, service ownership, timeouts (100 ms–60 s) and routes. A tool is listed only when three conditions hold: core configuration enables its Adapter, the tool itself is enabled, and the route is supported. Definitions are copied and frozen at registration; the Registry has no "enable" method |
| `server/integrations/policy.ts` (new) | `SPOTIFY_VOICE_CONTROL_GATE = "blocked"`: every `app.spotify.*` registration is refused; `external_commit` always needs confirmation; 30 calls per minute per Adapter; a 4 KB cap on result data |
| `server/integrations/dispatcher.ts` (new) | Refusals in order: unregistered, disabled, unsupported route, invalid arguments, confirmation required (this batch has no card, so these are always refused), rate limited. Timeout or abort returns `unknown`. When an Adapter throws, read tools return `failed` and side-effect tools return `unknown`. Off-contract results return `failed`. The audit records only the request-id, tool, Adapter, effect, route, status and milliseconds |
| `server/integrations/status.ts` (new) | On-demand health checks (3 s timeout, 5 s cache, no background polling). Timeouts, errors and inconsistent reports always become `unknown`. An Adapter that is not enabled is `not_configured` and is never probed |
| `server/integrations/adapters/mock.ts` (new) | `app.mock.echo` (read) and `app.mock.toggle` (reversible_write); descriptions and results are labelled "mock" |
| `server/integrations/index.ts` (new) | `createIntegrations`: returns null when `NOUS_AIL` is off. `NOUS_AIL_SERVICES` can only pick from the reviewed list; other names are skipped and logged |
| `server/config.ts` | `NOUS_AIL` (default off) and `NOUS_AIL_SERVICES` |
| `server/realtime.ts` | `RealtimeCapabilities.integrations`: integration tools go after the home/memory tools and before MCP; an `INTEGRATION_RULE` paragraph is added only when tools exist |
| `server/live-tool-caller.ts` | ChatGPT plan route: `app__` tools run in the core through the Dispatcher, never through the page, and share `maxHostCalls` with page tools. If a result is unknown and the model says nothing, the reply is "result unknown, please check" rather than "done" |
| `server/app.ts`, `shared/types.ts` | Only when the flag is on: `GET /api/integrations/status`, `POST /api/integrations/call` (checks session_id plus owner, only for API key route sessions, and the core decides the route), and `integrations.tools` in settings |
| `src/realtime-tools.ts`, `src/realtime.ts`, `src/main.ts`, `src/api.ts` | API key route: the page forwards `app__` names that the core listed, and only shows the core's fixed sentences; if forwarding itself fails, the result is `unknown` |
| `server/nous.ts` | Assembles the layer and wires it to both routes |
| `server/messages.en.json` | English versions of the new fixed sentences |

## 3. Limits and open items

- No real App, real voice or Mac validation. `mock` only shows how the layer itself behaves.
- `external_commit` is not wired to a confirmation card yet (reusing ApprovalQueue is left to a later batch), so it is always refused.
- When page forwarding fails, even read tools return `unknown` (a conservative choice).
- The `text` and `background` routes exist only in the contract; no caller uses them.
- Integration tools on the API key route do not light brain regions (the current sources are task steps and conversation topics, and this batch adds no new event source).
- Known existing behavior left unchanged: on the ChatGPT plan route, when a page tool such as `home_control` has an unknown result and the model says nothing, Nous still says "done, but there is no result to relay". This batch fixed only integration tools and did not change the home path.
