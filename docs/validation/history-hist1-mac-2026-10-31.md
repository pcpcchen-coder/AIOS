## 發現

- **F1：即時語音（ChatGPT 方案）會接走本機指令。** 「看著說話」開著時，面向螢幕就自動開始語音；說出的「進度如何」「看結果」被語音辨識成簡體（「进度如何」「看结果」），交給模型以 `get_tasks` 回答，沒有打開進度卡或成果畫面。手冊第 4 步「說『進度如何』」在這條路徑上不成立。驗收時要先關掉「看著說話」並用打字。
- **F2：「晚餐」找不到「晚饭／晚飯」。** 搜尋把「晚餐」和「晚飯」當成不同的詞。手冊第 3 步把「找之前關於晚餐的成果」列為應命中的說法；需要 George 決定是改例句，還是要讓搜尋支援近義詞。
- **F3：執行中的受保護任務在 App 裡顯示占位文字。** 執行中任務的詳細頁與進度卡，標題、原始要求和每一步都顯示「受保護的任務，請在 App 內查看」與「受保護的步驟」；同一筆在成果紀錄清單裡顯示「准备晚饭」，完成後的詳細頁也正常。
- **F4：刪除確認對話框的按鈕是英文。** 內文是中文，按鈕是「Cancel」「OK」，應為「取消」「刪除」。

## 備註

- **N1：** 用本機 API 把引擎切成模擬後，在 App 裡打一句一般對話，App 就把引擎自動切回 ChatGPT（App 的 `prepareConversation` 在引擎不是從 App 選單選的時候會這樣做）。所以第 5 步的重做跑在 ChatGPT `gpt-6.1-sol` 上。手冊「用模擬引擎（`NOUS_PROVIDER=mock`）」在 App 裡不會一直維持。
- 成果紀錄畫面寫「共 14 筆」時，`/api/tasks` 回傳 15 筆，有一筆沒列出，尚未查明是哪一筆。
- 驗收前已完整備份 `~/Library/Application Support/Nous`（`~/Nous-backup-20261031-080317`）。

## Mac 發現修正：F1（2026-10-31，分支 `claude/hist1-f1-local-commands`）

以下修正只在 Linux 上以自動測試驗證，**尚未在 Mac 上重新驗收**；上面的結果列（第 3a、4 步的備註與 F1）維持原樣，不因此改成通過。修正之後經過一次獨立審查（3 個 major、3 個 minor 與幾個細節），審查的修正已併入下面的說明，審查的情境 A–E 都已變成回歸測試。

| 發現 | 原因 | 修正 | 測試 |
|---|---|---|---|
| F1：即時語音接走本機指令 | 即時語音中用說的話只跑鏡頭規則與確認語句，從來不跑 `classify`，所以「進度如何」「看結果」一定交給模型；上游語音辨識又常給簡體（「进度如何」），連 `classify` 也認不得 | 見下面「比對」「請求 id」「這一輪不出聲」三段 | `tests/realtime-local-commands.test.ts`（兩條路徑的正例與反例、審查情境 A–E、確認卡開著時、`AssistantEcho`）、`tests/memory-apikey.test.ts` 與 `tests/live-route.test.ts`（核心只靜這一輪：之前那一輪的交辦結果照常念）、`tests/voice-commands.test.ts`（指令表的「即時語音（說）」欄改用真正的 `matchVoiceCommand` 推算） |

**比對（`src/voice-command.ts`）。** 兩條路徑在**使用者自己的 final 逐字稿**到達頁面時多一個本機比對（`RealtimeCallbacks.onLocalCommand`）；助理逐字稿與未完成的逐字稿不會進來。先把指令用到的簡體字折成繁體（一對一、長度不變；只用於比對），再交給既有的 `classify`；`classify` 認得之後，整句還要就是指令的說法才算：「進度如何（呢）」「進度呢」「看一下進度」「做到哪了」「看結果」「給我看成果」「搜尋成果 …」「找之前…的成果」「成果紀錄」「收起」「回桌布」「關閉畫面」，英文 "show／view progress"、"show results"、"search my／past results for …"（結尾的 please 不算查詢詞）、"dismiss"、"close the view"。只說「進度」或 "progress" 不算。只有四種：進度、最近成果、成果紀錄（查詢詞取使用者原本的字）、收起。不認得、含這些字的長句、意思不明確的短句（「好了沒」「剛才那份」「先這樣」）、雜音（ID-02 F3 的「被談」「对。」）照舊交給模型。

**回音。** 只有同時符合兩件事才當回音、交給模型：(1) 文字被 10 秒內助理說過的話包含或包含它（整句逐字稿，以及 API key 路徑的 `response.output_audio_transcript.delta`、ChatGPT 方案路徑未完成的助理逐字稿，所以使用者逐字稿比助理整句先到也認得）；(2) 這句話和播放重疊：開口時 Nous 正在播放，或播放停下不到 1.5 秒就開口（播放狀態：API key 路徑看 `output_audio_buffer.started／stopped`，ChatGPT 方案路徑看遠端音量）。所以模型問「要看結果嗎？」、播完之後使用者答「看結果」，是使用者自己的指令，照常在本機處理。

**確認卡開著時。** 換上別的畫面就等於拒絕確認卡，所以確認卡開著時「進度如何」「看結果」「搜尋成果 …」不在本機處理，照舊交給模型；「收起」和按 Esc 一樣關掉確認卡，算拒絕（指令表的「容易誤會」有寫）。

**請求 id。** 認得就和打字一樣用 `userRequest()` 登記這一則逐字稿事件的請求 id，`dispatch` 帶 `user_request` 的 Surface，Presentation Policy 照常檢查；「收起」只送 `dismiss`（同即時語音中按 Esc），不結束通話、不取消任務。沒有新增任何模型工具；成果紀錄仍只由使用者的輸入打開。打字的路徑沒有改（打字不做簡轉繁）。

**這一輪不出聲（只有這一輪）。** 不是手掌停止：之前各輪還沒回來的交辦、查詢結果照常請模型念出（審查 M1）。
- API key 路徑：這一輪的回應已建立就只取消它（`response.cancel` 帶它的 `response_id`）；還沒建立就在下一個沒有核心標記的回應建立時取消它（頁面自己先送出、還沒建立的接續請求不算）；這一輪的回應已經結束（逐字稿晚到）就只開畫面，不取消之後的任何回應。不加手掌停止的輪次、不清掉之前各輪「工具結果回來後要接著說」的狀態；被取消的回應建立時清掉的那個狀態會還原。這一輪的工具結果只交回、不念；被取消的回應的字幕不顯示。核心旁路收到 `stop-reply {scope: "turn", response_id}`，只把那個回應（或下一個）的核心工具結果改成不念，不動手掌停止用的輪次與排隊中的接續回應。
- ChatGPT 方案路徑：沒有 `response.cancel`，把播放靜音、字幕不顯示，直到這一輪的回覆（第一則助理逐字稿；這一輪自己開始的交辦還沒結束時，等它的結果）到了之後再等 1.5 秒（`LOCAL_COMMAND_DRAIN_MS`，讓聲音尾巴在靜音中播完）；最多 8 秒（`LOCAL_COMMAND_QUIET_MS`）。下列情況立刻恢復聲音與字幕（審查 M2）：使用者再開口（`speech.started`、新的逐字稿）、打字、系統通知、之前各輪的交辦結束、記憶事件（記憶卡打開、記憶提示、交辦卡、受保護交辦；記憶狀態本身不算）、確認卡（Action Gate）出現。所以核心送出的記憶確認問句、確認卡的說明一定聽得到、看得到。核心收到 `stop-reply {scope: "turn"}`：`NOUS_PALM_QUIET_DELEGATION` 開著時只有這一輪的交辦結果改成不念，之前各輪照常；沒開時核心不改，只靠頁面靜音。
- 預設開啟、沒有設定開關：這是使用者回報的真實錯誤，動作只開關畫面，不會造成外部副作用。

**信任層級。** 比對只用使用者的 final 逐字稿：API key 路徑是頁面自己的 WebRTC 資料通道上 OpenAI 送來的 `conversation.item.input_audio_transcription.completed`；ChatGPT 方案路徑是資料通道或核心經 SSE 轉送的 sideband 逐字稿（同一個 `item_id` 只處理一次）。這和打字同一個信任層級：都是可信主視窗收到的使用者輸入，能偽造這些事件的程式也能直接在輸入框打字；頁面本來就能用 `userRequest()` 登記打字的請求。`stop-reply` 的 `response_id` 只接受上游回應 ID 的形狀，形狀不對就當成還沒建立。逐字稿是麥克風聽到的任何聲音的辨識結果，旁人或電視說的話也可能被辨識（ID-02 F11），所以只認整句、短的固定說法，而且動作只有開關畫面；最壞情況是旁人說「看結果」打開了最近一份成果（模型的 `get_tasks` 原本也可能念出任務標題）。

**殘餘風險。** (1) 逐字稿比模型回答晚到時，API key 路徑的回應已經開始，開頭可能念出一點才被取消；ChatGPT 方案路徑只能靜音，模型仍在上游說完那一輪（只是聽不到），也可能在背景呼叫 `get_tasks`。(2) ChatGPT 方案路徑最多靜音 8 秒；這段時間內模型主動說、但不屬於上面恢復條件的話（例如核心沒有發出事件的提示）聽不到也看不到字幕；這一輪的回覆到了之後 1.5 秒內才到的另一則助理話會立刻恢復並顯示，但它開頭的聲音可能被靜音。(3) 回音判斷靠播放狀態：ChatGPT 方案路徑的播放狀態來自遠端音量（門檻未校準），漏判時回音可能被當成指令（只會開關畫面）。(4) API key 路徑：逐字稿比這一輪的回應先到、而頁面同時有一個自己送出的接續請求時，以「頁面自己的請求先建立」為準；上游順序相反時，會取消到之前那一輪的接續、少念一次結果。ChatGPT 方案路徑的核心若在收到 stop-reply 時還沒看到這一句的逐字稿，會把上一輪當成這一輪（只在 `NOUS_PALM_QUIET_DELEGATION` 開著時有影響）。(5) 沒有給模型「本機指令不要回答」的指示：比對認不出時要讓模型照舊回答，指示可能讓它在認不出時也不說話。

### 要在 Mac 上重新驗證（F1）

1. 「看著說話」開著、面向螢幕自動開始即時語音（ChatGPT 方案路徑）。說「進度如何」：進度卡打開，模型不回答（聽不到回覆，也沒有新的助理字幕）；DevTools console 有 `[live] 本機畫面指令：這一輪的回覆靜音`。
2. 同一通再說「看結果」：打開最近一份成果；說「搜尋成果 晚餐」：成果紀錄打開、搜尋框是「晚餐」；說「收起」：畫面關掉，即時語音指示仍在、還能繼續對話。
3. 說一句一般的話（「新竹今天會下雨嗎」）：模型照常回答、聽得到。
4. 說「我想知道那個報告的進度如何」、只說「進度」：不開進度卡，模型照常回答。
5. 交辦一件要跑一陣子的事（例如「幫我查明天新竹天氣」），模型說「我查一下」之後馬上說「進度如何」：進度卡打開；之後那件事的結果**仍然念得出來、字幕也有**。
6. 記憶開著、會出現語音記憶確認時（MEM-2 的步驟），在說「進度如何」之後的幾秒內觸發記憶確認問句：問句聽得到、字幕也有，說「確認記住」照常有效。
7. 模型問「要看結果嗎？」、念完之後才說「看結果」：在本機打開成果（不是被當成回音）。
8. 改成 API key 路徑重做 1–3、5、7；console 是 `[realtime] 本機畫面指令：這一輪不請模型回答`。記下每次說完到畫面打開的時間，以及有沒有聽到模型開頭的半句（殘餘風險 1）。
9. 英文介面：說 "show progress"、"show results"、"search past results for dinner"、"close the view"。
10. 依手冊 §4 第 4 步與第 7 步，用說的「進度如何」「收起」重做一次。
