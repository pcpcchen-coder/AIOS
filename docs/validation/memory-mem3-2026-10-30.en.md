# MEM-3 family memory on OpenAI API key realtime voice and cross-route consistency: cloud validation and Mac gate

Date: 2026-10-30, Asia/Taipei. Starting point: branch `claude/mem-2` (`658b97a`, already includes MEM-1 and MEM-2; PR #47 is not merged yet). Implemented on the separate worktree branch `claude/mem-3`; nothing was committed, pushed, or merged. All people, accounts, and memory content are fictional test data.

**Status of this batch: the MEM-3 code and the parts that can be verified in the cloud (Linux) are complete; the Mac gate has not been run and has not passed. Memory on the API key route is off by default** (when the release flag `NOUS_MEMORY_ROUTES` does not list `api_key`, this route behaves exactly as before MEM-2). This does not show that Nous can safely use memory in real API key realtime voice. Whether the sideband can attach with the call ID and which events it receives (the wire probes P1–P5 below) is not officially guaranteed and can only be proven on a Mac with a real key; if P1 or P2 fails, MEM-3 is not released. Background-task memory (MEM-4) and automatic curation (MEM-5) are not implemented. The same day, fixes followed an independent review (no blockers; 3 majors, 7 minors, 4 nits); they are listed in §2 items 15–28, and the test numbers below are updated.

### Revocation sequence (api_key)

1. The boundary changes generation and calls the lease cleanup → `ApiKeyCall.revokeMemory(why, rebuild)`.
2. Block the core's output synchronously: `revoked=true`, nothing more is sent on the sideband; `abort` cancels `recall_memory` and pending ToolHost calls.
3. Send SSE `closed{memory_revoked, rebuild}`. `RealtimeSessions` records the revocation: late host results then get `accepted:false`, `/api/realtime/web-search` gets 403, and new starts are refused until the stop result is known.
4. The core sends `POST /realtime/calls/{id}/hangup` (not awaited, at most 1 s), then closes the sideband. This is the second stop and does not depend on the page.
5. Page: `generation++`, mute, pause, clear srcObject, stop every remote track, close the peer and data channel, stop the microphone, cancel speech synthesis; after checking, POST `/api/realtime/stopped`. Tools already running are dropped by the generation check.
6. The core waits at most 1.5 s (`LIVE_STOP_REPORT_MS`). Report accepted: the page rebuilds (api_key only, no greeting, the first sentence is the fixed sentence sent by the page). Timeout: forced silence (main window `setAudioMuted`), the boundary disables `api_key` until restart (reason `stop_unconfirmed`), and a separate receipt says "stop not confirmed".
7. Correction or forget sends `hold` before commit: the page mutes immediately and sideband sends are queued; only if the commit fails is output resumed and the queue sent.

Main-window navigation or renderer exit (`closed`) does not wait for a stop report; OS lock and profile deletion end the call without rebuilding (same as the MEM-2 table).

## 2. Differences from the approved plan (recorded as they are)

1. **No sideband without consent.** Following the test list in plan §5, memory off, no `openai_realtime` consent, release flag off, or a disabled route all skip the sideband, and the request is byte-for-byte identical to the baseline. As a result the API key route **shows no voice memory cards without consent**; MEM-2 live still shows on-screen cards without consent. The two routes differ here; watch for it in the Mac test.
2. **Three new reason codes:** `route_off` (this route is not released; the status bar shows "Memory is not enabled on this path"), `no_control` (no call ID or the sideband cannot connect; this call carries no memory at all), `busy` (another realtime voice call is using memory). The plan mentioned only `route_off`.
3. **The page's playback report has no timestamp.** `POST /api/realtime/playback` has no content; the core uses the time it receives it, and `onAssistantAudioDone` keeps only the later value (MEM-2 live also changed to "only later"; its events arrive in time order, so its behavior is unchanged).
4. **MCP handling:** the client secret request still carries MCP (content unchanged); a call with memory rules replaces the whole tool list with `session.update` before the answer is returned (no MCP, with `recall_memory`), so MCP is already gone when media starts. If the sideband cannot connect, the call carries no memory and MCP stays.
5. **A sideband drop mid-call ends the call** (`closed{connection_lost}` and hangup) without pretending to reconnect; the plan did not cover this.
6. **No voice memory card while an approval card is open**, applied to both routes (MEM-2 live changed too), with the fixed receipt "Another confirmation card is on screen. Answer it first, then say again what to remember or forget".
7. **"Only one voice call may carry memory at a time"** is implemented as the binding's `busy` reason (checked at connect time against whether the previous call still carries memory) instead of refusing the start; there is only one API key session at a time, and a new start ends the old one first.
8. **`recall_memory` limit:** on the API key route, at most 2 per user utterance (live: 2 per delegation).
9. **The sideband is attempted once** (5 s), unlike the live sideband's 5 retries: if it cannot connect, the call starts without memory instead of delaying the answer. Waiting for `session.updated` is capped at 3 s and hangup at 1 s.
10. **The rebuild route** comes from this page's most recent revocation whose stop report was accepted and that has not been rebuilt yet; if none is found, it uses live as in MEM-2. Each revocation can be rebuilt at most once.
11. **Face candidate after the greeting:** IdentityService additionally notifies the sideband of the API key greeting decision (`apiKeyGreeted`, only whether it used a name); the sideband asks the candidate question when the next `response.created` / `response.done` after that ends. If that turn was actually a response to the user speaking first, the question is asked after that turn (when the user speaks first, the binding already asks after their first utterance).
12. **Web search ticket:** only API key calls with memory rules (with core tools) send the session ticket with web searches, so they get 403 after revocation; API key calls without memory still send none, so searches do not fail after the event stream reconnects.
13. **When a new start is refused before the stop result is known,** the reason code remains `session_busy` (`reasons.live`), as in MEM-2.
14. **Option ② of plan 2(b) (renderer handles media only) was not done**; following the default for §8 item 2 it is deferred to MEM-4 / MEM-5. Upstream very likely echoes `session.updated` and system items to the page's data channel (P5); the page reads only `type`, does not store, log, or forward them, and the cloud verifies this rule only with fixtures.

The following fixes were made the same day after an independent review (they replace the conflicting parts of items 7, 9, and 10 above):

15. **(M1) A memory-carrying API key call cannot be replaced.** While an API key call with memory rules (with core tools) is active, `/api/realtime/start` (any route) returns `session_busy` (`reasons.api_key`), and a second `/call` already decided returns 409; it is no longer replaced by "ending the old one" (that only closed the sideband and released the lease while the upstream call still carried memory, out of reach of revocation). An API key call without memory is still replaced by the next one. `busy` now holds when the previous call is still open and has memory rules, or still holds a lease (not only the lease).
16. **(M2) `session.update` carries its own `event_id`.** On an `error` pointing at it, or no `session.updated` within 3 s, the core hangs up (not only closing the sideband: a late update could still take effect) and returns 409 "Realtime voice did not confirm the memory settings, so it did not start this time". This replaces item 9's "counts as carrying memory without an ack"; item 9's 3 s limit remains.
17. **(M3) response.create collisions are matched by `event_id`.** Every `response.create` the core sends carries an `event_id` starting with `nous_core_`; "waiting" is cleared only by `response.done` or an error pointing at that `event_id`. The page's own `response.created` no longer clears the core's line; errors from the page's requests no longer make the core resend (no double reading); a collision error pointing at the core is resent once with a new `event_id` after that turn ends, and other errors are not resent.
18. **(Minor 4) With an approval card open, a pure parse comes first.** If the utterance is a memory command (remember, correct, forget, forget all, inspect), only the fixed sentence is returned and `voiceTurn` is not called, so no pending voice card is created or replaced. Both routes.
19. **(Minor 5) When the sideband sees a typed item from the page, the latest spoken sentence is cleared**, so the delegation card never shows a stale sentence (no card without a sentence).
20. **(Minor 6) If a rebuild finds no revoked call with an accepted stop report that has not been rebuilt, it is refused honestly** ("No call to rebuild was found; please start again") instead of quietly using live. This replaces item 10's "use live when none is found".
21. **(Minor 7) A revocation during the handshake (before the answer reaches the page) only hangs up**: no `closed`, no stop-report wait, no forced silence; the page gets the 409.
22. **(Minor 8) Only items seen in `input_audio_buffer.committed` have their speech-recognition transcript treated as the user's voice.** Whether GA sends `committed` on the sideband and whether the `item_id` matches must be confirmed together with P2; without `committed`, the call never shows a voice card.
23. **(Minor 9) `voiceConsented` also checks runtime disabling** (`stop_unconfirmed`, `cleanup_failed`), so a disabled route speaks no memory metadata.
24. **(Minor 10) Sideband lost while waiting for the ack**: hang up and return 502 "The core's control connection to OpenAI realtime voice was lost while connecting, so it did not start this time", no longer described as the page leaving, and no `closed`.
25. **(nit 11) The request-snapshot baseline is now the stored 658b97a request** (`tests/fixtures/apikey-request-baseline-658b97a.json`, produced from 658b97a's `RealtimeBridge` extracted with `git archive` and a fake fetch; the date is replaced with `<DATE>`), no longer generated by the modified bridge.
26. **(nit 12) Test-only flags take effect only together with `NOUS_TEST_MODE=1`** (`NOUS_TEST_DROP_STOP_REPORT`, `NOUS_TEST_RENDERER_IGNORE_REVOKE`); without it, the log says the flag was ignored. MEM-2 validation step 8 notes this too.
27. **(nit 13) The `unavailable` reason on the API key route is shown accurately as "No memory used (memory is unavailable)"**, not as "Memory is not enabled on this path".
28. **(nit 14) "Byte-for-byte identical" refers only to the upstream requests to OpenAI** (client secret and `/calls`). The page side does change: for API key calls started through `/api/realtime/start`, the page opens an SSE subscription and POSTs `/api/realtime/approval` for approval cards, and with memory it also POSTs `/api/realtime/playback` and `/api/realtime/stopped`; the `/api/realtime/call` answer gains `core_tools` and `memory`.

## 3. Plan §8 "decisions for George": defaults used in this batch (awaiting George's confirmation)

All of the following are the plan's default suggestions in parentheses. **They are not decisions George has confirmed:**

1. When the sideband cannot connect: the call carries no memory at all; no fallback to "renderer transcript plus cards only".
2. The renderer receiving memory content echoed by upstream: option ① (accept, with no-forward rules and canary tests); option ② renderer handles media only is deferred to MEM-4 / MEM-5.
3. Consent key: a separate `openai_realtime`, with the HMAC of the API key as the account; a new key requires new consent.
4. MCP when carrying memory: removed (see §2 item 4).
5. `web_search` when carrying memory: allowed (same OpenAI account, consistent with MEM-2).
6. After an API key call is revoked: rebuild on the API key route, never switching to live; if quota runs out, end honestly.
7. Release flag: API key memory off by default, opened by `NOUS_MEMORY_ROUTES=live,api_key` (or listing only `api_key`); the default changes only after the Mac gate passes; live keeps its current state and this flag cannot turn live off.
8. Core hangup as the second stop: adopted.
9. Fixed sentence after a rebuild: sent by the page (fixed, no memory content); the core records it in the echo list.
10. Typed memory commands during a call: not parsed (consistent with MEM-2).
11. Only one voice call may carry memory at a time: yes.

Prepared in advance to avoid rework in MEM-4 and MEM-5: `byRoute` consent targets and the route-parameterized binding; source tags in `shared/realtime-ga.ts`; `delegatePolicy` in a single function; `RevokedSession`, `StopEvidence`, and `forceSilence` independent of route; the boundary's release table and disable reasons; the voice-card receipt log records the route (`memory: 語音確認（remember，api_key）→ saved`; the store format is unchanged).

**Main release condition: P1 and P2 hold, and step 5 proves with a recording that no late old audio follows revocation.**

## 6. Not done, limitations, and the next gate

- Mac gate 0–15 has not been run at all; API key route memory stays off by default until it passes.
- P1–P5 have no official guarantee: the sideband's event set is unknown, and without the speech-recognition transcript this design does not work.
- Upstream very likely echoes memory content to the page's data channel (P5), so the page handles memory content; this relies only on the "read type only, never forward" rule and fixture tests.
- Both the core and the page send `response.create` and may hit `conversation_already_has_active_response`; the core queues and resends on that error, and the page recovers from a rejected request; real behavior is unverified.
- There is no evidence of what hangup does to RTP (step 12).
- In a call with memory, the model may put memory into `web_search` queries (same OpenAI account, consistent with MEM-2).
- The residual risk of spoken confirmation is the same as MEM-2 (TV, other people, echo with poor AEC).
- A rebuild is billed again by usage on the API key; on the fallback call the two consents differ, so the status bar must show the reason clearly.
- Background tasks (MEM-4) carry no memory; push-to-talk and voice conversation mode still do not use memory.
- Next gate: Mac steps 0–15 above, especially P1, P2, and the step 5 recording.
