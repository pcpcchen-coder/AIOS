# WK-02 validation: wake wired to realtime voice

Date: 2026-10-31, Asia/Taipei. Branch: `claude/wk-02` (based on main `40d92fb`). Scope: WK-02 in [plan 17 §13.4](../17_Wake_Word_and_Speaker_Recognition_Plan_2026-10.en.md#134-交付批次與估時). Rules are in [ADR-0003](../adr/ADR-0003-local-wake-and-voice-recognition.en.md); the foundation is in [WK-01a validation](wk-01a-2026-10-31.en.md).

**This is not a hardware acceptance test, and there is no real wake detection.** The wake engine is still not connected (only the preparatory part of WK-01b is done); the product detector honestly reports `runtime_missing` and does not open the microphone, so **the product cannot produce any wake trigger yet**. This batch wires up what happens after a trigger: opening the call, the greeting, the rate limit, ending when nobody speaks, and cost records. All tests below ran in a cloud container with fixtures (fake routes, fake detection events, fake MediaDevices, fake clocks and fake timers). **They are not a Mac, a microphone, or the wake word.** None of W1–W12 in plan 17 §13.2 has been run on a Mac.

## 1. George's decisions (2026-10-31)

| # | Decision | What this batch does |
|---|---|---|
| E1 | **Always greet** after a wake; no extra switch | `greetingFor("wake_word")` always creates a `GreetingOnce` and does not read "Greet first during look to talk". | E3 | End after **5 s of user silence** | `WakeCallWatch` (`src/audio/wake-call.ts`) uses the WK-01a `NoVoiceWatchdog`: the countdown starts when the call first becomes ready; it pauses while Nous speaks or thinks and restarts a full 5 s on listening; hearing sound, the server detecting speech, or the user typing disarms it; on timeout the call ends with the caption 「沒有聽到聲音，已結束通話，回到喚醒聆聽」 (“No voice was heard, so the call ended; back to wake listening”) |

<a id="3-設計"></a>
## 3. Design

<a id="31-觸發到通話"></a>
### 3.1 From trigger to call

Detection → guard → earcon → not cancelled and still `listening_local` → `onWakeTrigger`. It is ignored while a call is on or starting, or while the family recognition view is open; when realtime voice is unavailable it shows 「即時語音目前不可用（reason）」 (“Realtime voice is unavailable (reason)”); otherwise it calls `startRealtime("wake_word", { wake })`. Route choice, the billing notice, route fallback and the consent card all reuse the existing `openRealtime`. A refused wake start only shows a caption and does not open the input box (the user is not typing). Without realtime voice consent, a wake opens the existing consent card, but at most once per rate-limit window (60 s); other wakes in that window are ignored. If the user agrees, the call starts as `wake_word` (greeting, 5 s silence end and rate limit as usual); if not, nothing opens.

<a id="32-問候"></a>
### 3.2 Greeting

The core issues an interaction ID for `wake_word` in `/api/realtime/start`, and `claimGreeting` returns `source: "wake_word"`. When `IdentityService` sees that source it skips the "Look to talk" and "Greet first during look to talk" requirements and keeps everything else. On the page, ambient recognition relaxes the same two settings until the wake greeting is decided (`ambientEnabled`) and asks `ambient_status` again once the core has issued the interaction ID. On a route fallback both sessions share one `GreetingOnce` and a claim succeeds only once, so each wake greets at most once. The core's relaxation (`wakeGreetingOpen`) holds only while the interaction is unused and either its start decision is still pending, it is connecting, or it connected within 20 s and the call is still on; it ends when the page gives up before connecting (`/api/realtime/end` for a decision that never sent an offer), when the connection fails without a fallback, or when the call ends. The page also clears its own relaxation in `stopRealtime`, when the call closes, and on memory revocation.

<a id="33-限速"></a>
### 3.3 Rate limit

The limit lives in the core (`RealtimeSessions.start`) and counts accepted `wake_word` starts; starts refused because no route is available and starts from other sources do not count. **An accepted start that later fails to connect still counts** (kept simple; no refund). When the page gets `wake_limited` it pauses listening for the core's `retry_after_ms` and resumes automatically when the timer fires (same microphone as before, no “resumed” caption). If the user presses "Pause listening" during that time, the user's pause wins.

<a id="34-沒人出聲就結束"></a>
### 3.4 Ending when nobody speaks

The countdown only looks at a level threshold (RMS 0.03 for 300 ms in a row, the same as the realtime early-speech detector, uncalibrated). **It is not VAD** and cannot tell a voice from a TV. The level comes from the call's own leased microphone clone (`browserWatchLevel`, one number every 50 ms, no samples kept). On a route fallback the old clone is released and the new one is attached. The timeout's end reason `no_voice` goes to the core's cost record.

<a id="35-f6-費用紀錄"></a>
### 3.5 F6 cost records

Every realtime call (not only wake-started ones) writes one record when it ends:

```json
{"v":1,"session_id":"rt_…","route":"api_key","model":"gpt-realtime","source":"wake_word","wake_id":"int_…","started_at":"…","ended_at":"…","connected":true,"connected_ms":7250,"end_reason":"no_voice","no_voice_auto_end":true,"usage":{"responses":2,"input_tokens":120,…},"cost":"unknown"}
```

There are no transcripts, audio or names. The core sometimes sees the end before the page's `/api/realtime/end` (for example a live `closed` arrives first): within 15 s after the end (`COST_AMEND_GRACE_MS`), a late `no_voice` or API key usage from the same owner rewrites the same record (`VoiceCostLog.amend`) instead of adding another. `usage` holds only the `response.done` numbers summed by the page on the API key route (a page report, not a bill); the ChatGPT plan route is always `"unknown"`. `cost` is always `"unknown"`: without unit prices or account usage evidence, no bill is inferred. Legacy API key calls without a `session_id` (`/api/realtime/call` without a session) do not go through `RealtimeSessions` and are not recorded.

<a id="36-nsmicrophoneusagedescription"></a>
### 3.6 `NSMicrophoneUsageDescription`

- English: Nous uses the microphone for voice conversations and, if you turn on always-on wake listening, to detect "Hello Nous" on this Mac only; that audio stays in memory and is not saved or uploaded. After the wake word or when you start a conversation, audio is sent to your selected voice service until the conversation ends.
- Chinese: Nous 使用麥克風進行語音對話；若開啟常駐喚醒聆聽，也只在這台 Mac 本機偵測「哈囉努斯」，偵測時的聲音只留在記憶體、不保存也不上傳。喚醒或開始對話後，音訊會傳送至你選用的語音服務，直到對話結束。

<a id="37-旗標關閉"></a>
### 3.7 Flag off

With `NOUS_WAKE` off, `wake_word` is always treated as `user` (no interaction ID, no rate limit, `wake_id` ignored), and the page does not load `src/audio/`, so there is no trigger and no countdown. **The one intentional exception is F6 cost records**: George decided on 2026-10-31 to “always record, not tied to the wake switch” (「一律記錄，不綁喚醒開關」), so with the flag off the core still creates `VoiceCostLog`, writes `voice-cost.jsonl` for every call, reads `reason`/`usage` on `/api/realtime/end`, and serves `GET /api/realtime/cost-records`, and the page always sends usage when an API key call ends. The snapshots in `tests/wake-flag-off.test.ts` (page headers, `/api/settings`, the menu bar) were not updated and are still byte-identical; a new check confirms byte-identical responses for `wake_word` and `user` starts, and another test names the F6 exception explicitly (`cost-records` returns 200 with the flag off). The statement “byte-identical with the flag off” excludes F6.

<a id="4-與規劃不同之處"></a>
## 4. Differences from the plan

- Ambient recognition for the wake greeting: the core also provides `wakeGreetingOpen()` so that `ambient_status`/`ambient_probe` accept samples while a wake greeting is undecided. Changing only `claimGreeting` would mean that with "Look to talk" off the page could not even sample, so it would never name anyone.
- The trigger handling decision (whether to open a call) is the pure function `wakeTriggerAction` in `src/realtime-session.ts`, because `src/main.ts` may not statically import `src/audio/` (`tests/audio-privacy.test.ts`). `WakeCallWatch` is created by the controller's `watchCall`.
- Cost records cover every call, not only `wake_word`, and do not depend on `NOUS_WAKE` (George 2026-10-31: “always record, not tied to the wake switch”; plan 17 §5.7 only requires wake-started calls; recording more never loses one). This is the one intentional exception to “byte-identical with the flag off”. When live fails to connect and the call falls back, the failed attempt also gets a record (`connect_failed`, `connected: false`).
- The end of a rate-limit pause shows no “resumed” caption (it is not the automatic resume after the App reopens or the Mac wakes); the menu bar status updates honestly.

<a id="8-風險與限制"></a>
## 8. Risks and limitations

- A page script can still send `source: "wake_word"` and open a real call (ADR-0003 §2.2); the rate limit, visible indicators and cost records limit the consequences but cannot remove them.
- The relaxed ambient recognition during a wake greeting relies only on the core knowing that a wake interaction is open and undecided; during that time any page script can send samples, the same kind of residual risk ID-02 already records (responses carry no result).
- The `rate_limited` pause lives in page memory; a page reload forgets it, while the core's rate limit still applies.
- `WakeCallWatch` is a level threshold: with the TV on it may never time out, and the tail of Nous's playback may be taken as someone talking.
- `connected_ms` in the cost records is the core's wall-clock difference, not the seconds the provider bills.
