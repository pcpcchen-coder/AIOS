# 家人辨識 ID-01：登記、刪除、加密保存與畫面內辨識

2026-10-25；分支 `claude/family-id-01`，基於 `claude/family-id-00`（PR #36，尚未合併）。對應 [14 規劃](../14_Family_Recognition_and_Greeting_Plan_2026-10.md) §9 的 ID-01 與 [ADR-0001](../adr/ADR-0001-local-family-recognition.md) §2.1.1、§2.2、§10。

**這份紀錄的結果全部來自 Linux 雲端容器**：vitest、Node、headless Chromium 141（CPU／WASM／SwiftShader）。safeStorage、Keychain、`tmutil`、Electron IPC、AR0144 與 Mac 的 CPU 都沒有執行；這些用替身（明確標示）或待 §6 的 Mac 實測。**門檻未校準**（`CALIBRATED = false`），cosine 只是 sanity check。沒有稱名問候（ID-02），也沒有背景辨識。

## 2. 與交付說明（設計 brief）的差異

| 項目 | brief | 實作 | 理由 |
|---|---|---|---|
| 選單停用原因 | 瀏覽器版／鏡頭未啟用／無法加密／模型未安裝或雜湊不符／需重新登記都是停用原因 | **只有**瀏覽器版與「此 Mac 無法加密保存」讓「家人辨識…」停用。鏡頭未啟用、模型未安裝或雜湊不符時仍可打開，但只能查看與刪除（`limited_reason`，顯示在 sublabel 與畫面）；需重新登記只是畫面上的提示 | 刪除不能被鏡頭或模型狀態擋住（ADR §2.2「本人可以隨時要求刪除」） |
| 變更事件 | SSE 可送 `identity.changed {epoch, gallery_version}` | 沿用既有 `settings.updated`；`settings.identity` 本身帶 `epoch`、`gallery_version` 與人數 | 不新增事件型別，選單列本來就靠 settings.updated 更新 |
| 樣本一致性 | 「核心檢查樣本一致性」 | 每張對平均方向 ≥ 0.5，**且**任兩張 ≥ 0.4（`MATCH_THRESHOLDS`） | 只看平均方向擋不住「兩個人各一半」（各自對平均約 0.7），測試先重現了這個漏洞 |
| startNous 選項 | `{ dir, secretBox, excludeFromBackup, confirm }` | 多一個 `modelDir` | 核心要核對模型雜湊並提供 `/face-runtime/`；雜湊沒過就不提供 |
| 取樣節奏 | ≤4 Hz | ≤4 Hz，但每 50 ms 檢查一次：推論一回來、距上次取樣滿 250 ms 就立刻取下一格 | 讓相鄰畫格間隔盡量貼近推論時間，證據與登記的「斷開 > 500 ms」規則才不會因整點等待而誤觸 |
| 登記「太慢」 | 斷開 > 500 ms 整批丟棄 | 照做；還沒有樣本時另外照實顯示「相鄰畫格隔了 N 秒（超過 0.5 秒，電腦可能太忙），暫時取不到樣本」 | 雲端實測（§4.5）發現推論變慢時畫面會永遠停在 0 張且沒有原因 |
| Family 畫面重畫 | — | 內容沒變就不重畫 | 雲端實測發現每格都換掉 DOM 時，按鈕在按下與放開之間被替換，點不到「停止試認」 |
| YuNet 640 縮放 | 沿用 spike（canvas 縮放） | 改成 OpenCV `cv::resize` 的定點移植（`letterboxToChw`），worker 只讀一次像素 | 補上 ADR §10「letterbox 沒有對 OpenCV 核對」；`preproc` 版本記為 `yunet640-cvlinear-bgr-v1` |

起點門檻（全部未校準）：`match` 0.5、`margin` 0.08、`consistency` 0.5、`consistency_pair` 0.4；品質：臉寬 ≥ 100 px、框在畫面內、分數 ≥ 0.8、鼻尖水平位置偏離正中 ≤ 0.2、俯仰 0.2–0.8、roll ≤ 20°、臉框平均亮度 40–220；清晰度沒有做（可選項，留待 Mac 數據）。

### 2.1 獨立審查後的修正（2026-10-25）

| 審查項目 | 修正 | 測試 |
|---|---|---|
| 刪除先清零特徵再寫檔：寫入失敗時記憶體已壞 | 寫檔成功後才清零；載入時逐一驗證特徵，不合格標「壞資料」、不參與比對、可刪除 | 刪除時 save 拋錯：資料不變、仍認得、之後登記的檔案沒有 0 向量；壞資料載入與刪除 |

### 4.2 產品 worker 對 OpenCV 交叉核對

方法：`worker-crosscheck.mts` 把建置後的 `dist` 交給真的本機核心（`startNous`，注入替身 SecretBox）提供，在 headless Chromium 以 module worker 載入 `/assets/identity-worker-*.js`，模型與 wasm 從 `/face-runtime/` 讀；畫格是 ID-00 的 5 張公有領域肖像（1280×720 RGBA），另合成「兩張肖像並排」與「灰底無臉」兩格。參考值 `opencv-worker-reference.py`：OpenCV 5.0.0 `cv2.resize`（INTER_LINEAR）縮到 640×360、補到 640×640，`FaceDetectorYN`（2023mar、分數 0.6、NMS 0.3、topK 5000），座標除以 0.5，對整個畫格 `FaceRecognizerSF.alignCrop`＋`feature` 後 L2 normalize。每格送 6 次，耗時取第 2–6 次（排除第一次）的中位數與最大值；cosine 是 worker 最後一次的特徵與 OpenCV 特徵的內積。

| 畫格 | worker 臉數 | OpenCV 臉數 | 品質 | cosine（worker vs OpenCV） | worker 耗時中位數／最大 ms |
|---|---|---|---|---|---|
| biden_2013 | 1 | 1 | ok | 0.99996 | 196／250 |
| biden_2021 | 1 | 1 | ok | 0.99993 | 188／212 |
| harris_2017 | 1 | 1 | ok | 0.99994 | 189／245 |
| harris_2021 | 1 | 1 | ok | 0.99995 | 194／214 |
| obama_2012 | 1 | 1 | ok | 0.99995 | 188／224 |
| 兩張並排 | 2 | 2 | multi_face（不送特徵） | — | 92／135 |
| 灰底 | 0 | 0 | no_face | — | 93／113 |

- 模型載入（含 wasm 編譯）914 ms（第一次執行 1961 ms，含檔案快取差異）。審查修正後（`/face-runtime/` 每次讀取都核對雜湊）重跑：臉數、品質與 cosine 完全相同，載入 1000 ms，單格中位數 162–250 ms，CSP 探針結果相同，沒有離開本機的請求。耗時是雲端 1 執行緒、沒有其他負載時的數字，**不代表 Mac，也沒有和感測迴圈同時跑**。
- 同一人不同照片的 cosine：Biden 0.7267、Harris 0.7485；不同人 0.0522–0.2146（sanity check，只有 3 個人，不能定門檻）。
- `tests/face-letterbox.test.ts`：`letterboxToChw` 在 3 種縮小比例下與 `cv2.resize` **逐像素相同**（含產品的剛好 0.5 倍），放大時個別像素差 1（產品不會放大）。

### 4.3 worker CSP（headless Chromium）

同一個核心另提供一個探針 module worker（`/assets/csp-probe.js`，只在暫存的 dist 副本）：`fetch("https://example.com/")` **被擋**、`new Function(...)` **被擋**、`WebAssembly.compile` 允許（`'wasm-unsafe-eval'`）。worker 腳本回應的 `Content-Type` 為 `text/javascript; charset=utf-8`，CSP 與 §3 相同。整個交叉核對期間沒有離開本機的請求。Electron 內的行為待 §6。

### 4.4 核心以真實特徵走一次（`core-real-features.mts`）

用 §4.2 worker 算出的特徵（只在 repo 外的暫存檔）直接驅動核心（替身 SecretBox、自動同意的 confirm、假時鐘每 250 ms 一格）：

| 步驟 | 結果 |

### 4.5 瀏覽器端到端（不含 Electron）

- **UI 煙霧（`ui-smoke.mts`，通過）**：真的 `dist` 頁面＋真的核心；preload 以 Playwright `exposeFunction` 模擬（同樣經 `validateIdentityRequest`），點擊時間窗用 `MenuClickWindow`。頁面腳本自己發 `family` 指令 → 畫面顯示「請從選單列「鏡頭與語音設定 → 家人辨識…」打開」（核心 log：`open_session 拒絕（not_user_initiated）`）；先記點擊再發 → 畫面打開、`data-visibility-reason="user_request"`；試認（沒有雙目鏡頭）→「鏡頭沒有在運作…」＋「門檻未校準…」；收起 → `close_session`。沒有離開本機的請求，沒有原生確認被呼叫。
- **假鏡頭完整流程（`e2e-fake-camera.mts`，沒有完成）**：Chromium 假鏡頭播放 2560×720 y4m（同一張肖像左右並排），既有感測管線（MediaPipe Pose×2＋手勢）照常運作，鏡頭狀態為 ok。但雲端沒有 GPU，MediaPipe 的 GPU delegate 落在 SwiftShader（CPU）上，頁面主執行緒被佔滿：試認的取樣間隔中位數 **2.6–4.3 秒**（兩輪，分別 8 與 6 次取樣，間隔超過 500 ms 的有 7／7 與 5／5），登記因每格都超過 500 ms 而停在 0 張，畫面照實顯示「相鄰畫格隔了 1.8 秒（超過 0.5 秒，電腦可能太忙），暫時取不到樣本」。後幾段甚至因主執行緒延遲超過 10 秒，點擊時間窗過期而被核心拒絕開 session（符合設計）。**這只說明雲端 headless 跑不動同時的感測迴圈，不代表 Mac**；同時運作的取樣間隔、停止手勢與 CPU 是 §6 B 的必測項目。MediaPipe 的用量紀錄連線（`odml.pa.googleapis.com`）照舊被頁面 CSP 擋下（ID-00 §6 的既有發現）。

## 5. 殘餘風險（照實）

- **舊快照可解**：safeStorage 的應用程式金鑰不輪換。Time Machine 或 APFS 本機快照中的舊 `gallery.v1.json`（含當時包裝的資料金鑰）理論上仍可用同一台 Mac 解開；`tests/identity-store.test.ts` 用替身重現。Time Machine 排除只降低風險，APFS 本機快照不受排除影響。畫面與刪除確認都說明了這個限制。
- **記憶體**：資料金鑰的 base64 字串與解密後的 JSON 字串留在 V8 heap，無法主動清零；能清零的 Buffer 與特徵陣列都已清零。
- **探測（審查後仍存在）**：session 內的頁面程式拿同一張臉連續送 3 格以上，仍可從穩定的「認得／不認得」推測它是否已登記（這本來就是試認的功能）；登記流程的重複檢查也透露「可能已登記」。降低方式：只有使用者點選單列才能開 session、開滿 15 分鐘或導覽即失效、每秒 6 次、不回分數、gallery 相關結果要 ≥3 格才回、重複訊息不回名字。
- **回滾**：用較舊的 gallery 檔替換現有檔沒有防護（例如已刪的人回來）；寫入前的版本核對只防兩個核心互相覆蓋。
- **包裝金鑰被改**會表現為「解不開金鑰」（`key_unavailable`），畫面提示的是允許鑰匙圈或重新啟動；這種情況重試不會成功，但資料也不會被清掉或覆寫。
- **照片與螢幕**：沒有活體或防偽；身分只用來稱呼，不作任何授權。
- **雲端數字**：耗時只代表雲端 1 執行緒、無負載；cosine 只有 3 個人。
- **SFace 訓練資料條款**仍未查清（ADR §9 待決）。

## 6. 待 George 在 Mac 上實測

**準備**：`cd prototype/ambient-shell && npm ci && npm run face:setup -- --product`（確認輸出「已安裝到 …/Library/Application Support/Nous/face-runtime」）；`cd desktop && npm ci && npm start`（或 `npm run package` 後安裝）。`.env` 設 `NOUS_CAMERA=on`。記錄 Mac 型號、晶片、macOS 與 Electron 版本。

**A. safeStorage、Keychain 與檔案**

1. 啟動 Nous 時不應出現 Keychain 提示（gallery 延到第一次打開才載入）。第一次打開「家人辨識…」並登記、以及之後重新啟動再打開時，記錄是否跳出 Keychain 存取提示（「Nous 想要使用鑰匙圈中的…」）、按了什麼；若按「拒絕」，畫面應說明可重試（不出現「清除全部」），關閉再打開並按「允許」後恢復。
2. `ls -la@ ~/Library/Application\ Support/Nous/identity/`：資料夾 `drwx------`、`gallery.v1.json` 為 `-rw-------`；沒有 `.tmp-` 殘檔。
3. `tmutil isexcluded ~/Library/Application\ Support/Nous/identity`：應為 `[Excluded]`。若不是，記錄畫面上是否出現「無法把家人資料夾排除在 Time Machine 之外」。
4. `grep -c <登記的名字> ~/Library/Application\ Support/Nous/identity/gallery.v1.json` 應為 0；`grep -n "identity\|家人" ~/Library/Application\ Support/Nous/nous.log` 只有狀態、耗時與世代，沒有名字。

**B. IPC 與選單**

1. 選單列「鏡頭與語音設定」最後一項是「家人辨識…」；鏡頭關掉時仍可打開，但只能查看與刪除（sublabel 與畫面說明一致）。
2. 打開畫面 10 秒後再從 DevTools（若可開）執行 `nousDesktop.identity({ op: "open_session" })`：應回 `not_user_initiated`。`Object.keys(nousDesktop)` 只有 `openExternal`、`reportState`、`identity`。
3. 「語音指令表」視窗（另一個視窗）不能呼叫 identity（它沒有 preload）。
4. 畫面開著時按 ⌘R 重新載入：舊的管理 session 應立即失效（主程序在 `did-navigate` 時關閉），重新載入後的頁面不能沿用；要再從選單列打開。登記確認對話框開著時再按一次「新增家人」或「刪除」應回「另一個變更還在進行」。

**C. AR0144 登記與試認**

1. 1.0 m 正面、正常光線：新增家人 → 依提示轉頭，記錄取滿 7 張的時間、是否出現「太慢」或「整批丟棄」、系統確認對話框的文字（未成年時要有家長勾選）。
2. 試認：本人在 0.8、1.0、1.5 m 各 10 秒，記錄顯示的結果序列（認得／不認得／品質不足）與「門檻未校準」標示；另一位家人與陌生人各一次（陌生人必須是「不認得」）；兩人同時入鏡必須是「多張臉」。

**D. 與感測迴圈同時跑**（I7）

1. 只開 Nous（不開家人辨識畫面）：Nous 播報較長回答時，在 1.5 m 舉手掌 10 次，記錄停止成功次數、大約延遲、活動監視器中 Nous（Renderer 與 GPU）CPU %。
2. 打開家人辨識畫面並按「試認」，重複上述 10 次。
3. 收起家人辨識畫面後，`grep 試認取樣間隔 ~/Library/Application\ Support/Nous/nous.log`：核心在 session 結束時只記這一行數字（個數、中位數、p95、最大、超過 500 ms 的個數）。中位數必須明顯小於 500 ms，否則證據與登記規則永遠不會成立（雲端 §4.5 的現象）。

**E. Electron 中的 worker CSP**：DevTools → Network 檢查 `identity-worker-*.js` 回應帶 `Content-Security-Policy`；Console 沒有 CSP 錯誤（除了 MediaPipe 用量紀錄被擋，既有）；Network 沒有連到外部網址。

**F. 刪除後重啟（I9）**：刪除一位家人（確認對話框要寫明備份快照限制）→ 結束 Nous（⌘Q）→ 重新開啟 → 列表沒有此人、試認此人顯示「還沒有可以比對的家人」或「不認得」。記錄 `gallery.v1.json` 的 `key_generation` 刪除前後的數字（`python3 -c "import json;print(json.load(open('…/gallery.v1.json'))['key_generation'])"`）。
