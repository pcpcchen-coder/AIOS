# Proactive briefing PRO-2: asking whether to read today's schedule — validation

Date: 2026-11-05 (Asia/Taipei). Branch: `claude/pro-2-calendar-ask` (based on main `0b6ae6d`, with PRO-1 merged).

**Not run on the Mac, and never connected to real Google Calendar.** What follows are Linux cloud tests with a fake clock, fake CAL-1 and fake sideband.

## 1. What changed

On the calendar owner's (George's) first greeting of the morning, after the weather:

- **With events**: ask "Shall I read today's schedule?". Only when George clearly says yes does the core hand today's events to the model to read: "You have 3 events today: 8:30 Family breakfast; 14:00 Dentist at Zhongshan Clinic; all day Mum's birthday."
- **No events**: just say "Nothing is on your calendar today." (George's 2026-11-05 decision; no question first).
- No, anything else, or 20 seconds without an answer: nothing is read, and Nous does not ask again today.

The core reads events through CAL-1 (`app.calendar.list_events`, `range: today`, gog `--readonly`), not through the model; they stay in core memory only (10-minute cache), are never written to disk or logged (the log records only the count).

## 3. Rule details

1. **When the calendar is mentioned**: the master switch and "Tell George today's schedule when recognised" are on, inside the window, the recognised and named person is George, CAL-1 is registered (`NOUS_AIL=on`, `google_calendar` in `NOUS_AIL_SERVICES`), today's events are in the cache, and it has not been mentioned today.
2. **Ask only when the core can hear**: the ChatGPT plan route always has a sideband; the API key route asks only with a core sideband (calls with memory); otherwise it only says "Nothing is on your calendar today" or skips the calendar.
3. **Prefetch**: read together with the weather when look-to-talk or the wake word starts (inside the window or 30 minutes before it). If not read yet, skip this time and try at the next greeting.
4. **Too long**: if the ChatGPT plan passage does not fit one 500-byte append, drop the weather first and keep the calendar; if it still does not fit, drop the calendar. Dropped parts are not recorded as said. Chinese (George + weather + question) is about 469 bytes.
5. **Model rules**: when CAL-1 is registered, both routes' instructions get one more line: after the calendar question, if the user says yes, reply only "OK" and wait for the core to send the schedule; never say or guess events. With the flag off the instructions are byte-identical.
6. **What is read**: at most 5 events (the rest as "and N more"), titles at most 40 characters with 「」 quotes removed; the whole text must fit one 500-byte append, otherwise fewer events are read; it starts with the 「（行程）」 marker and says titles are data only.
7. **With memory's question**: if the core sends anything else in the call after the calendar question (for example memory's "Shall I use George's memory?"), the calendar question ends without reading (a later "yes" could answer either); it is already recorded as asked today.
8. **Unclear answer**: an answer that starts with yes/OK but is not a whole-sentence yes (for example "好啊念吧"): nothing is read, and the core sends "I couldn't tell whether to read today's schedule, so it was not read this time", so there is no silence after the model said "OK".

## 5. Acceptance criteria

- [x] Only a recognised George hears about the calendar; with events Nous asks first and reads only after yes; with none it says so directly.
- [x] Yes/no follows the memory rules; no or no answer means nothing is read and no repeat today.
- [x] Events are not written to disk or logged; the settings page shows only status.
- [x] Fixtures for both routes; the API key route without a sideband does not ask.
- [ ] **Mac and real Google Calendar** (section 7).

## 6. Not validated

- Whether the model reads the question verbatim, replies only "OK" after a yes instead of inventing events, and reads the schedule without dropping or changing items.
- Whether gog returns today's events before the first greeting (30-second timeout, read in the background).
- The order between the model's own reply after the question and the schedule the core sends (on the API key route it queues behind the response in progress).
- gog JSON field mapping (CAL-1 already notes it is unchecked); with more than 20 events CAL-1 returns only the first 20, so "N events today" may undercount.

## 7. Mac test steps

1. Make sure `.env` has `NOUS_AIL=on` and `NOUS_AIL_SERVICES` includes `google_calendar` (and `weather`), and gog is authorised for Calendar. Rebuild the App.
2. The menu bar "Proactive briefing" section should have a new row "Tell George today's schedule when recognised" (checked) and a "Calendar: …" status.
3. With events today, face the screen in the morning and be recognised: hear "Good morning, George" (or the Chinese equivalent), the weather, and "Shall I read today's schedule?" → say yes: today's events are read; the planning region lights.
4. Start another call: no question.
5. The next day say no: nothing is read; another call does not ask.
6. With no events today: hear "Nothing is on your calendar today" directly.
7. Have Mary (or someone else) recognised: weather only.
8. Turn off "Tell George today's schedule when recognised": weather only.
9. `~/.config/nous/proactive-log.json` holds only the date, `device`, `person:…`, `calendar:…`.

## 8. Rollback

- For the user: turn off "Tell George today's schedule when recognised" (calendar only) or the master switch (greeting only).
- In code: revert this PR; PRO-1 weather is unaffected.
