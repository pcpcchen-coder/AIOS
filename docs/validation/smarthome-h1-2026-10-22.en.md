## Fake-controller tests

The fake controller is a Node HTTP server, a **fixture with fictional devices and replies**. Format follows `execute()` in controller `backend/app.py`: synchronous `{id, status, message}`, 409 `state_stale`/`not_configured`, 422 `unsupported_command`, and 409 string for same-key/different-content.

`tests/home-bridge.test.ts`:

- `confirmed`: sends `{command:"power", value:false}` with `Idempotency-Key`, prefix `nous_`, at most 128 characters, plus token; subtitle confirms living-room main light off with ✓.
- Brightness “60%” sends 60; color temperature “3000K” sends controller `temperature: 3000`; color temperature “26” refuses locally without sending.
- `unconfirmed` and controller-recorded `accepted` both report sent, unconfirmed, without ✓.
- `failed` reports controller's reason.
- First timeout retries once with identical key/content and uses second result. Two timeouts → `unconfirmed`/`no_reply`. The whole command gets only this one retry: timeout then `state_stale` does not refresh; `state_stale` refresh then timeout → `no_reply`; only two POSTs either way.
- Connection refused, certainly not received → `failed`/`hub_unreachable`; timeout then refusal remains `no_reply` because first attempt may have executed.
- Same-key/different-content 409 → `failed`/`internal`, no retry, token absent from message.
- `state_stale`: refresh once, resend same key, `confirmed`; still stale or refresh fails → `refused`/`not_ready`. A device with timed-out prior readback and `commands: []` is still sent, not labeled unsupported. The entire flow counts once against rate limiting.
- Incomplete setup: `/home` `configured:false` prevents send and controller 409 maps identically. Unsupported: controller 422; AC/IR not sent, wireless button not mislabeled infrared. Controller-rejected values: 422 string.
- Multiple candidates, rooms even with one device, whole home → `ambiguous`, no send; missing → `not_found`.
- Rate limit: seventh command in one minute is not sent; `retry_after_s` 55 as calculated below; allowed after another 61 seconds.
- Confirmation card via test-only `policyFor`: `needs_confirmation` does not send. Approval sends once with key generated by `control()`. Two simultaneous approvals and later approvals/rejections return same result. Approval after rejection, unknown ID, and after 90 seconds → `expired`; `off` → `voice_disabled`.
- Token appears only in `Authorization`, never results, payloads, URLs, `detail`, or realtime tool settings.

`retry_after_s` calculation: six commands arrive in seconds one through six; seventh at second six. Earliest leaves the 60-second window at second 61, so wait 61 − 6 = 55 seconds, `Math.ceil((earliest + 60 000 − now) / 1000)`, minimum one second.

`tests/realtime-voice.test.ts`, fake WebRTC data channel:

- Direct execution returns tool result to model and requests speech; missing device/action does not call local core.
- `needs_confirmation`: queues card before returning tool result; no-MCP explanation notice; still requests speech after tool result, with home cards excluded from MCP count.
- “好” (“okay”) does not send. “確認執行” (“confirm execution”) answers local core, not `mcp_approval_response`; result becomes one system notice after current response ends, adding only one `response.create`.
- “確認執行停止播放” (“confirm execution stop playback”) cancels. “取消” adds background information without requesting another response. Timeout/collapse informs model of non-execution; ending conversation only informs local core with no further events.
- New home cards do not queue behind an existing MCP/home card: local core discards them and model receives `busy`. Spoken confirmation answers only the open card. MCP arriving behind home does queue and receives model explanation on its turn.
- Home card countdown is min(60 seconds, server `expires_in_s`); home result requests speech without waiting for ongoing MCP calls.
- Executing confirmed commands suspends idle timeout; results arriving after conversation end do not notify.

`tests/http.test.ts`: input validation, 409 without controller, `/api/home/control` and `/api/home/confirm` forwarding via local core, no token in response. `tests/voice-commands.test.ts`: real matchers check `home_control` table row and four misconception rows for confirm-plus-stop, okay, AC 26 degrees, and all living-room lights off.

<a id="審查修正"></a>
## Review fixes

Independent review found eight issues, all fixed. Items one through six have regression tests in `tests/realtime-voice.test.ts` and `tests/home-bridge.test.ts` that fail on pre-fix code.

1. Home cards queued behind open/queued cards, risking approval intended for the first applying to the later device. Home cards now never queue: `POST /api/home/confirm` with `approve:false` discards them; tool returns `busy`, and model asks user to answer current card then repeat. MCP approval requests still must queue; model explains them on their turn, already tested.
2. Card 60-second countdown started on display, server confirmation ID from `control()`, potentially mismatching. `needs_confirmation.expires_in_s` now reports server remaining lifetime, 90 seconds; card uses its minimum with 60, so approval remains valid while displayed time remains.
3. Timeout and `state_stale` retries were independent, allowing four POSTs and worst case 8 + 16 × 4 + 15 = 87 seconds; docs/12's “about 50 seconds” was wrong. Whole command now has only one same-key retry, calculated below.
4. AC detection missed real controller devices: Tuya `kt`/`ktkzq` imports as `kind: switch`; Home Assistant AC as `climate.*`, previously permitting power commands. Now also checks `config.cloud_category`/`config.entity_id`, retaining AIFA `config.external_provider` and `kind: air_conditioner` checks even though current controller does not generate them. Tuya `wxkg` wireless buttons, `kind: remote`, no longer claim infrared/AC; they say unsupported device class. Controller code has no AC category list; `kt`/`ktkzq` are standard Tuya cloud category codes.
5. Home-tool results waited for OpenAI MCP completion before requesting speech. Local tools and MCP now track separately; local results do not wait.
6. Every controller 404 was considered missing device. Only `device_not_found` maps to `not_found`; other 404s, such as old controller lacking route, report controller error and command not sent.
7. docs/12 said AC temperature/IR were unsupported while some AC power commands were actually sent. Updated documentation, tool description, and model instructions to match corrected behavior, naming AC power/temperature, IR devices, and wireless buttons.
8. Removed extra blank line at end of `tests/realtime-voice.test.ts`.

Worst-case calculation from `server/home-bridge.ts`: `/home` read eight seconds, POST 16 seconds, refresh 15 seconds. At most two POSTs, with second either a timeout/error retry or a post-`state_stale` refresh retry:

- Timeout retry: 16 + 16 = 32 seconds.
- `state_stale` refresh/retry: 16 + 15 + 16 = 47 seconds; 409 cannot arrive slower than timeout.
- `control()` first reads `/home`: 8 + 47 = 55 seconds. Confirmation `confirm()` skips that read: 47 seconds.

## Not yet validated

- **Real `confirmed`/`unconfirmed` readback:** example devices lack real addresses; these results only tested with fake controller.
- **Timeout/same-key retry:** fake controller only; real slow readback, LIFX up to 14 seconds, not measured.
- **Hardware voice:** no OpenAI key, microphone, or speaker. Initial acknowledgment, spoken results, and repeated calls after `needs_confirmation` remain untested.
- **Confirmation UI:** automated tests only, not visually inspected in browser; no H1 device triggers it before controller `voice` settings in H2.
- **Scoped token:** controller lacks `commands:write` etc., controller P0-1; master token used.
- **AC/infrared:** outside H1 scope, H1b.
