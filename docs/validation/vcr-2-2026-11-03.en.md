## 2. Deliverables

All paths are under `prototype/ambient-shell/`.

| File | Contents |
|---|---|
| `server/integrations/voice-relay/mac-say.ts` (new) | `MacSayOutput`: runs `/usr/bin/say` with an argument array (no shell, stdin closed, SIGTERM on abort). Reads voices with `say -v ?` and speakers with `say -a ?`. Speakers are stored **by name**; before each play the list is re-read and the name is mapped to the current numeric ID, so numbering changes after a reboot or reconnect are followed. If the name is missing the result is `failed`, and audio never goes to another speaker. The text is one argument: `[[volm v]] [[slnc lead]] wake phrase [[slnc pause]] command [[slnc tail]]`; rate `-r` = 175 × rate; volume can only be lowered (gainDb > 0 is clamped to 1.0); a non-zero pitch is refused (`say` has no matching option) |
| `server/integrations/voice-relay/store.ts` (new) | Reads and writes `<NOUS_CONFIG_DIR>/voice-relay/config.json` and `trials.json`: temporary file plus rename, files 0600, folder 0700. Every change validates the whole catalog with `parseRelayCatalog` before writing. Built-in demo targets and built-in voices cannot be changed |
| `server/integrations/voice-relay/routes.ts` (new), `server/app.ts` | The `/api/voice-relay` routes (section 4). They exist only when `voice_relay` is registered, otherwise 404. Unknown fields, wrong types, overlong strings and control characters get 400 with a fixed message that never echoes input |
| `server/integrations/adapters/voice-relay.ts` | The model path and diagnostic play share one playback flow and one busy lock; `mac` mode has `mock=false`; diagnostic play has a 20-second limit; `reload()` applies new settings (the tool schema does not change, see section 6) |
| `server/config.ts` | `NOUS_VCR` accepts `off`/`fake`/`mac`; `mac` is enabled only on macOS, other platforms log one line and skip it |
| `server/integrations/voice-relay/{catalog,builtin,resolver,output}.ts` | Every spoken text field rejects `[[` and `]]` (prevents embedded `say` commands); `mac` mode has no demo targets |
| `shared/voice-relay.ts` | `VoiceRelayView` and the other view types |
| `src/views.ts`, `src/main.ts`, `src/api.ts`, `src/style.css`, `src/messages.en.json`, `shared/types.ts` | The settings page "Voice relay (experimental)" section, bilingual (about 115 new English strings) |

## 3. Settings page "Voice relay (experimental)"

It is fetched and shown only while the settings page is open and the core reports `voice_relay: true`. There is no background polling and it is not a dashboard.

- Header: the mode ("Mac speaker really plays" or "Simulated: no sound is played"), "A successful play only means the sound was sent, not that the speaker obeyed.", and "No echo suppression: Nous's own microphone may hear these plays." After the target or light list changes, a note says a restart is needed.
- Output: counts of voices and speakers, and "Reload voices and speakers".
- "Add Google Home Mini": locale (zh-TW/en-US), speaker, voice (filtered by locale), music service (choosing Spotify or "Don't know" blocks all music commands). In fake mode it also says "Adding a target replaces the demo targets."
- Per target: enable/disable; the voice list (voice for testing, rate, volume, pause, lead/tail silence, "Save voice", "Add candidate voice"). Editing the voice the model currently uses clears all of this target's adoptions; they must be adopted again.
- For each phrasing of each intent: text, wake phrase, status (Adopted / Candidate / Rejected / Policy blocked), the needed slot inputs, and "Preview text", "Test wake word", "Test full command", "Adopt this set"/"Stop using". Policy-blocked phrasings cannot be played or adopted. Each intent has at most one adopted phrasing.
- The recording area appears only after a full-command test reports "sent, unconfirmed": whether it woke, command correct/wrong/not executed, evidence (visual/human confirmed), and "Record result". The summary shows "wake a/b, command c/d, overall e/f", N/A for a zero denominator, and "Not tested" with no data.
- Sound plays only from the "Test wake word" and "Test full command" buttons, and results never say "success".

## 4. HTTP routes

| Route | Contents |
|---|---|
| `GET /api/voice-relay` | View data `VoiceRelayView` |
| `POST /api/voice-relay/refresh` | Re-read voices and speakers |
| `POST /api/voice-relay/preview` | Read-only preview (can name a candidate phrasing and voice); never plays |
| `POST /api/voice-relay/play` | `part: "wake"｜"full"`; candidates the user explicitly picked on the page may be test-played; 20-second limit; the result is never `confirmed` |
| `POST /api/voice-relay/target`, `/profile`, `/adopt`, `/unadopt`, `/trial`, `/enabled` | Change settings or add a test record; return the new view data |

Like the other settings routes, these only pass the localhost/Origin/JSON checks, with no extra sign-in. Request bodies are capped at 16 KB.

## 5. Model path

- The tool is still `app.voice_relay.send_intent` (VCR-0). In `mac` mode the description has no "(Mock)" prefix, and a finished play returns "the voice command was sent, but the result is not confirmed".
- Only phrasings that are "adopted" (approved in the target's `reviewedTemplates`) and that the resolver would pick by default are played; candidates, rejected and policy-blocked phrasings are always refused. Tests against a real HTTP server confirm: not adopted → `not_reviewed`; after adoption → `unconfirmed`; after "Stop using" → refused again.
- Result mapping: `say` exit code 0 → `unconfirmed`; non-zero after start → `unknown`; failed to start → `failed`; speaker or voice missing → `failed` (`say` not started); timeout or abort → `unknown`, no retry. Exit code 0 means `say` sent the sound to the chosen device and finished; it is not a hardware receipt.

## 7. Not verified

- **Running on a Mac**: the real output format of `say -v ?`/`say -a ?`, choosing the speaker with `-a`, whether `[[volm]]`/`[[slnc]]` take effect, and the relation between the exit code and actual playback.
- Google Home Mini recognition rates for any phrasing or voice (NOT TESTED).
- Echo: not handled by decision; during a Nous call, Nous's own microphone may take "Ok Google…" as something the user said.
- Typed chat and background tasks cannot use this tool (only the two realtime voice routes).
- After adding or removing targets or lights, the model tool list updates only after restarting Nous.
- The section inside the Electron App has not been looked at on a Mac.

## 8. Rollback

- `NOUS_VCR=off` (the default) or remove `voice_relay` from `NOUS_AIL_SERVICES`: no section, no routes, and no model tool.
- "Disable" a target or "Stop using" a phrasing on the page: stops only that speaker or phrasing.
- Delete the `<NOUS_CONFIG_DIR>/voice-relay/` folder: back to no targets.
- A bad config file only leaves `voice_relay` disabled or unable to save; HomeBridge, other integrations and voice conversation are unaffected.

## 9. How to use it (Mac)

1. Add `NOUS_AIL=on`, `NOUS_AIL_SERVICES=voice_relay` and `NOUS_VCR=mac` to `.env` and restart Nous.
2. Open settings → "Voice relay (experimental)" → "Add Google Home Mini": choose the locale (the same as the speaker's language setting), the speaker that should play, the voice and the music service. Restart Nous once after adding it.
3. For each intent you want, press "Test wake word" and "Test full command", watch the speaker's reaction and record the result; adjust rate or pause and try again.
4. Press "Adopt this set" on the set you are happy with. Then, in a voice call, say something like "tell Google next song" to Nous, and the model really plays that phrasing with that voice; Nous only says "the voice command was sent, the result is not confirmed".
