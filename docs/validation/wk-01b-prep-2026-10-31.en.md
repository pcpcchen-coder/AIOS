<a id="3-設計"></a>
## 3. Design

<a id="31-wasm-建置"></a>
### 3.1 Building the wasm

- The cmake options follow upstream `build-wasm-simd-kws.sh`: `SHERPA_ONNX_ENABLE_TTS=OFF`, `SHERPA_ONNX_ENABLE_WASM_KWS=ON`, other WASM targets left at their default OFF; `SHERPA_ONNX_ENABLE_WASM_TTS=OFF` is added explicitly.
- Upstream v2.0.1 `build-wasm-simd-kws.sh` states “emsdk 4.0.23 is known to work” (read from upstream on 2026-10-31), so 4.0.23 is pinned.
- Upstream `wasm/kws/CMakeLists.txt` packs the model into `.data` with `--preload-file`, stops with `FATAL_ERROR` when the model is absent, and outputs a classic script. `wake-wasm.mjs patch` changes 4 places, and each original text must occur **exactly once**:
  1. remove the check that stops when assets has no decoder;
  2. replace `--preload-file` with `-sMODULARIZE=1 -sEXPORT_ES6=1 -sEXPORT_NAME=createSherpaKwsModule -sENVIRONMENT=web,worker` (a module worker cannot `importScripts`);
  3. add `FS` to `EXPORTED_RUNTIME_METHODS` (the worker writes the verified model into the in-memory file system);
  4. remove `.data` from the install list.
- The model therefore stays out of the wasm, and the wasm hash does not depend on the model choice. The models reuse the archives and hashes pinned in WK-00.
- Output is 3 files: `sherpa-onnx-wasm-kws-main.mjs` (Emscripten's ES module loader), `sherpa-onnx-wasm-kws-main.wasm`, and `sherpa-onnx-kws.mjs` (upstream `wasm/kws/sherpa-onnx-kws.js` unchanged plus one line `export { createKws };`). `LICENSE.sherpa-onnx.txt` is attached too (release only, not installed; it is also listed with its hash under `release_only` in the manifest).
- The build job outputs the SHA-256 of `wake-runtime-manifest.json` itself as a job output. The release job checks the downloaded manifest against it first, then checks every file (LICENSE included), and the folder may hold no files beyond the manifest.
- Releases are immutable: if a release with the same name already exists, the workflow fails, changes nothing, and leaves it to a person.
- The release is named `wake-runtime-2.0.1-<first 12 hex of the config hash>`; the config hash is the SHA-256 of `build-wake-wasm.sh` and `wake-wasm.mjs`, so changing either gives a different release.

<a id="32-worker-的載入順序"></a>
### 3.2 Worker load order

1. If the manifest has any blocker → no network use, lock the network, report `runtime_missing`.
2. Read the wasm, the chosen model's encoder/decoder/joiner/tokens, and the two JS files from same-origin `/wake-runtime/`, checking each SHA-256 with `crypto.subtle`; any mismatch, HTTP error, or missing file → `runtime_load_failed`.
3. **After all bytes are read and checked, and before `import()` of any third-party module**, `lockGlobals()` runs: `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `WebTransport`, `importScripts`, `Worker`, `SharedWorker`, and `caches` are defined as non-writable, non-configurable functions that always throw, and `bytes()` refuses from then on. So the top-level code of the third-party modules already runs without these APIs (overriding these globals does not affect `import()` itself).
4. The two JS files are then loaded with `import()` (the same same-origin path), followed by `lockImports()`, after which `module()` refuses too. On failure (`finally`) both locks are applied.
   - The real verify-then-execute guarantee comes from **the core re-checking the hash on every read** (`readVerifiedWakeRuntime`): `import()` fetches again rather than executing the bytes the worker just checked, and the worker's CSP (`scriptHeaders()`: `script-src 'self'`, `connect-src 'self'`, no `blob:`) does not allow executing in-memory bytes instead. The worker-side check is an extra layer.
   - The final boundary is that CSP's same-origin restriction: even if `LOCKED_GLOBALS` missed some API, it could only reach the same-origin core.
5. The Emscripten module is initialized with `wasmBinary` (the glue downloads nothing itself), the model is written into the in-memory file system, and the keywords are passed as `keywordsBuf` (`wakeKeywordsText`: one line per keyword, "units [:boost] [#threshold] @ID"). If the engine rejects the keywords (spotter handle 0) → `runtime_load_failed`.
6. Detection: the `keyword` from `getResult` (the `@ID`) is mapped to its position in the manifest's `entries`, and only `{ type: "detected", keyword_index }` is sent. A result that is not in the list only resets the stream and is not reported. Upstream copies the samples into the wasm heap; that block is zero-filled after it reaches the engine, and dispose removes the model from the in-memory file system.

Dynamic `import()` is syntax and cannot be overridden by assignment. It appears only in `module()` in `runtime-net.ts`, accepts listed names only, and refuses after the lock.

<a id="33-清單格式與-wakesetup------product"></a>
### 3.3 Manifest format and `wake:setup -- --product`

- `status`: with `pending_first_build`, the release files' `sha256` must be empty strings and `build.release_tag` and `config_sha256` must be null (the format check rejects hand-filled hashes); with `built`, all three must be set.
- Model files: 4 files for each of two models (`zh-en-3M`, `wenetspeech-3.3M`): int8 encoder, decoder, int8 joiner, tokens.txt. The install name is `<model id>.<name inside the archive>`, and the hashes equal `spike/wake/models.json` (checked by a test). Which model is used is set by `keywords.model`, which waits for George's numbers together with the keywords.
- `keywords`: with `pending_owner_numbers`, `model`, `keywords_score`, and `keywords_threshold` are null and `entries` is an empty array; with `configured`, pronunciation units may not contain `:`, `#`, `@`, or separators other than spaces.
- `npm run wake:setup -- --product`: it first runs the same `validateWakeRuntimeManifest` as the core and stops on any format error; if the manifest is not `built` or any file lacks a hash, it fails **before downloading**; every file name (manifest names, names inside archives, archive names) must match `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$` before `join`. It then downloads the release files (`https://github.com/pcpcchen-coder/AIOS/releases/download/<tag>/<name>`) and the model archives, checks each one, and installs only when everything passes. `--from <folder>` uses files that are already downloaded.
- Installation is atomic: each destination (`wake-runtime/` and, on macOS, `~/Library/Application Support/Nous/wake-runtime/`) is first written to `<destination>.tmp-XXXX` on the same volume; the old destination is renamed to a backup and the temporary folder renamed into place. Any failure removes the temporary folder and restores the backup, and if the second destination fails, the first is restored too. The destination is replaced as a whole by the files checked this time.
- Core: while `runtime()` is not `ok`, `/wake-runtime/` returns 404 for every file, including model files whose hashes are already pinned.

<a id="4-授權查核"></a>
## 4. License check

- The v2.0.1 tag has no `cmake/espeak-ng-for-piper.cmake` (the upstream raw file returns 404), and with `SHERPA_ONNX_ENABLE_TTS=OFF`, `sherpa-onnx/csrc/CMakeLists.txt` compiles no `offline-tts-*` file. In the upstream source, espeak-ng is mentioned only in TTS files, the Python bindings, and comments in `c-api.h`.
- `license-check` runs automatically (as its own workflow step, and again at the end of the build script):
  - `CMakeCache.txt` must have `SHERPA_ONNX_ENABLE_TTS:BOOL=OFF` and `SHERPA_ONNX_ENABLE_WASM_KWS:BOOL=ON`, and `SHERPA_ONNX_ENABLE_WASM_TTS` must not be ON;
  - file names in the build tree and the output, and the contents of `.wasm`, `.js`, `.mjs`, `.a`, `.o`, `.data`, `.so`, and `.dylib` files, must not contain `espeak`, `libespeak`, or a standalone `piper` (case-insensitive, and not preceded by a Latin letter, so `OfflineSpeaker` is not a false positive);
  - the output must be exactly the 3 files plus the LICENSE (no `.data`).
- This is a string and file name check. It catches statically linked espeak-ng symbols (such as `espeak_Initialize`, which WK-00 found in the 1.13.8 native package) and piper C++ names, but a release wasm build strips most function names, so the real guarantee comes from TTS being off and from the build-tree check, not only from strings in the wasm.
- Other third-party licenses are as in [ADR-0003 §3](../adr/ADR-0003-local-wake-and-voice-recognition.en.md#3-授權查核表2026-10-29); onnxruntime is the 1.28.2 wasm static library that upstream cmake pins by hash.

<a id="10-風險與限制"></a>
## 10. Risks and limitations

- **The workflow has never run**: the emcc version string, the `export default createSherpaKwsModule` output format, `-sENVIRONMENT=web,worker` combined with `EXPORT_ES6`, `cmake --install`, and the license check on a real build tree are all unknown until the first CI run. If any of them differs, the workflow fails instead of publishing a wrong artifact.
- **Loading has only been tested with a fake module**: whether the real Emscripten module initializes with `wasmBinary` in an Electron 44.9.3 module worker, whether `FS` is exported, and how the int8 models behave in browser wasm all need the Mac.
- Upstream's `INITIAL_MEMORY=512MB` was not changed; the worker reserves that much memory, which needs measuring on the Mac.
- Actions are pinned by the `@v4` tag, following the convention of the repo's other workflows, not by commit SHA; switching to SHAs is a separate repo-wide decision. emsdk and sherpa-onnx are pinned by full commit SHA.
- Releases are immutable: if a release with the same name already exists, the workflow fails and a person decides (compare the existing release's manifest; delete it only if no manifest references it, or change the build configuration).
- The emsdk toolchain (the LLVM/Emscripten binaries that `emsdk install 4.0.23` downloads) relies only on TLS and the pinned emsdk commit (which decides which build is downloaded); there is no separate archive checksum.
- For the two JS files, verify-then-execute relies on the core re-checking on every read (§3.2); the worker-side check is an extra layer, not the only guarantee.
- The license check is a string and file name check (§4).
- If the repository is private, the public download URL for release assets may return 404; `--from` is the alternative.
