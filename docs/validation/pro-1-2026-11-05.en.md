# Proactive briefing PRO-1: today's weather after the greeting — validation

Date: 2026-11-05 (Asia/Taipei). Branch: `claude/pro-1-weather-briefing` (based on main `ce1489c`).

**Not run on the Mac, and never connected to the real Open-Meteo.** What follows are Linux cloud tests with a fake clock and fake Open-Meteo responses (fixtures).

## 1. What changed

On each person's first greeting of the morning, Nous adds one sentence about today's weather after the greeting, for example:

> Good morning, George. Today in Taipei: partly cloudy, 22 to 28°C, 60% chance of rain this afternoon; take an umbrella.

- **The core decides what is said**: the weather sentence is a deterministic template (`weatherSentence` in `shared/proactive.ts`) filled from the core's own cache; the model only reads it out, inside the same `「」` as the existing greeting.
- **Both voice routes**: on the API key route it goes into the strict instructions of `response.create` (`strictGreetingInstructions`); on the ChatGPT plan route it goes into the sideband's `session.context.append` (at most 500 bytes per piece, using the existing chunking).
- **No repeat when live falls back to the API key route**: the page's `GreetingOnce` greets once per conversation; separately, the core records "said today" only when the greeting is actually sent, so a later decision will not repeat the weather.
- **No new path for voice or page content**: the page still sends only an interaction ID.

## 2. George's decisions (2026-11-05) and how they are implemented

| Decision | Implementation |

| Weather from Open-Meteo (free, no key), fetched by the core, exposed in AIL as a read-only adapter | `server/weather.ts`: fixed host `https://api.open-meteo.com/v1/forecast`, parameters only the listed place's coordinates and time zone; `server/integrations/adapters/weather.ts`: `app.weather.today` (`read`, no arguments). The model gets it only with `NOUS_AIL=on` and `weather` in `NOUS_AIL_SERVICES`; the greeting's weather does not need the AIL flag (same cache) |
| Cache about 30 minutes, fetched before the greeting | Refetch only after 30 minutes; data older than 2 hours or not for today is not used. Prefetch: as soon as a look-to-talk or wake-word call is issued an interaction ID (`onGreetingStart` on `RealtimeSessions`), only inside the window or 30 minutes before it |
| Location in settings; no arbitrary URL from the model or page | Only 12 Taiwanese cities from a fixed list (`WEATHER_PLACES`, coordinates near city hall to two decimals); with none chosen it is inferred from the system time zone: `Asia/Taipei` → Taipei; other time zones infer nothing and must be chosen |

| Settings: master switch (on by default), weather, window, location; bilingual | The menu bar "Proactive briefing" section and the settings page (macOS App and browser) both use `POST /api/settings/proactive`; text is in the shared translation table |

## 3. Rule details

1. **When the weather is added**: master and weather switches on, local time inside the window, a location, today's weather in the cache, and this subject not briefed today.
2. **Subject**: a named family member → `person:<id>` (also records `device`); unrecognised or not named → `device`. So once George has heard it, an unrecognised person will not hear it again; if an unrecognised person heard it first, George still gets his own when recognised.
3. **When it counts as said**: on the API key route with a core sideband (calls with memory), when the sideband sees the greeting turn start (`response.created`); without a sideband the core cannot see the call, so handing the instructions to the page counts. On the ChatGPT plan route, when the sideband actually takes the greeting; if the user speaks first (F10) and the greeting is dropped, it does not count.
4. **Browser version**: the ChatGPT plan route's fallback greeting (no family decision) also adds the weather (device rule); on the API key route the browser page builds "I'm here" itself without the core, so **the browser API key route does not say the weather**.
5. **Too long, no weather**: on the ChatGPT plan route the whole passage (with instructions) must fit one 500-byte append (the 「（開場）」 marker is only in the first piece); if it does not fit, Nous only greets this time and does not record it.
6. **Honest status**: the settings page derives the weather status from "usable cache for this place today"; after changing place or day it no longer says received; a failed refresh with usable cache still says received (the greeting still uses it). Aborting a tool call only stops that caller's wait, not the shared lookup.

## 5. Acceptance criteria

- [x] The weather sentence is composed by the core, and both routes' fixtures send the same sentence.
- [x] At most once per person per day inside the window; device rule when unrecognised; a greeting that was not sent does not count.
- [x] When lookup fails, data is not today's, or there is no location, Nous only greets, and the settings page shows the real state.
- [x] The daily log holds only the date and keys.
- [x] Master switch off = greeting only (rollback).
- [ ] **Mac test** (section 7).
- [ ] **A real Open-Meteo reply** (field names follow the official documentation; never connected).

## 6. Not validated

- Whether the model reads the whole passage verbatim (the API key route has rewritten sentences before, see ID-02 F1), or adds words or drops numbers when reading the weather.
- Real Open-Meteo replies and latency; whether the prefetch returns before the first greeting (look-to-talk about 1.5 s + connection + 600 ms).
- How a longer greeting affects the "user spoke first" checks (F2, F10).
- City coordinates approximate the city hall.
- On the API key route with a sideband, "the first `response.created` after the decision" is taken as the greeting start; if the user speaks within the roughly 100 ms of the decision and the page drops the greeting, the next response can still be taken as the greeting and recorded (the same judgement MEM-3 uses for asking about face candidates after the greeting).

## 7. Mac test steps

1. Pull main and rebuild the App. Menu bar "Camera and voice settings" → "Proactive briefing" should show: master switch (on), Say today's weather (on), window 5:00–11:00, Weather location "From system time zone (Taipei)", status "Weather: not looked up yet".
2. Between 5 and 11 in the morning, face the screen (or say Hello Nous) to start a call: you should hear "Good morning, George" (or the Chinese equivalent) followed by today's Taipei weather. Note whether it was read completely, whether words changed, and how many seconds from the start of the greeting to the end.
3. End and start again: greeting only, no weather.
4. With another family member (or not looking at the camera so Nous does not recognise you): a recognised member hears their own; an unrecognised person does not hear it again today.
5. Change the location to Kaohsiung in the menu bar and check the next morning that Kaohsiung is read.
6. Turn off Wi‑Fi, reopen the App, and on the first greeting the next morning: greeting only, status shows the lookup failed.
7. Turn the master switch off: back to greeting only.
8. With `NOUS_AIL=on` and `weather` added to `NOUS_AIL_SERVICES`, ask "What's the weather today?": the model calls `app.weather.today` to answer.
9. Check `~/.config/nous/proactive-log.json`: only the date and `device`/`person:fam_…`.

## 8. Rollback

- For the user: turn off "Brief me after the morning greeting" in the menu bar or settings page; Nous immediately goes back to greeting only (no restart needed).
- In code: revert this PR; `proactive.json` and `proactive-log.json` can simply be deleted.
