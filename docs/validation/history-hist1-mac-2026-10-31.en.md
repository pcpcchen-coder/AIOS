## Fixes for the Mac findings: F1 (2026-10-31, branch `claude/hist1-f1-local-commands`)

This fix was verified only by automated tests on Linux and **has not been re-accepted on a Mac**. The result rows above (the notes on steps 3a and 4, and F1) stay as they were and are not changed to passed because of this. After the fix, an independent review found 3 major issues, 3 minor issues and a few nits; their fixes are included in the description below, and the review's scenarios A–E are now regression tests.

| Finding | Cause | Fix | Tests |
|---|---|---|---|
| F1: live voice takes over local commands | During live voice, spoken words only ran the camera rules and the approval phrases and never `classify`, so 「進度如何」 and 「看結果」 always went to the model; the upstream speech recognition also often returns Simplified Chinese (「进度如何」), which even `classify` does not recognize | See the three paragraphs "Matching", "Request id" and "Silencing this turn" below | `tests/realtime-local-commands.test.ts` (positives and negatives on both routes, review scenarios A–E, an open confirmation card, `AssistantEcho`), `tests/memory-apikey.test.ts` and `tests/live-route.test.ts` (the core silences only this turn: an earlier turn's delegation result is still spoken), `tests/voice-commands.test.ts` (the "Realtime spoken" column of the command table is now derived from the real `matchVoiceCommand`) |

**Matching (`src/voice-command.ts`).** On both routes, the page runs one more local match when **the user's own final transcript** arrives (`RealtimeCallbacks.onLocalCommand`); assistant transcripts and partial transcripts never reach it. It first folds the Simplified characters used in commands into Traditional (one-to-one, same length; for matching only), then passes the text to the existing `classify`; once `classify` recognizes it, the whole utterance must also be a command phrase: 「進度如何（呢）」, 「進度呢」, 「看一下進度」, 「做到哪了」, 「看結果」, 「給我看成果」, 「搜尋成果 …」, 「找之前…的成果」, 「成果紀錄」, 「收起」, 「回桌布」, 「關閉畫面」; in English "show/view progress", "show results", "search my/past results for …" (a trailing "please" is not part of the query), "dismiss", "close the view". A bare 「進度」 or "progress" does not count. There are only four kinds: progress, latest result, results history (the query keeps the user's own characters), and dismiss. Unrecognized utterances, longer sentences containing these words, unclear short phrases (「好了沒」, 「剛才那份」, 「先這樣」) and noise (「被談」 and 「对。」 from ID-02 F3) go to the model as before.

**Echo.** An utterance is treated as echo, and left to the model, only when both hold: (1) its text is contained in something the assistant said within the last 10 seconds, or contains it (final transcripts, plus `response.output_audio_transcript.delta` on the API-key route and partial assistant transcripts on the ChatGPT-plan route, so it also works when the user transcript arrives before the assistant's full sentence); (2) the utterance overlapped playback: Nous was playing when the user started speaking, or playback had stopped less than 1.5 seconds before (playback state: `output_audio_buffer.started/stopped` on the API-key route, remote audio level on the ChatGPT-plan route). So when the model asks 「要看結果嗎？」 and the user answers 「看結果」 after it finished playing, that is the user's own command and is handled locally.

**With a confirmation card open.** Showing another view rejects the confirmation card, so while a card is open 「進度如何」, 「看結果」 and 「搜尋成果 …」 are not handled locally and go to the model as before; 「收起」 closes the card like Esc, which counts as rejecting it (the "ambiguities" section of the command table says so).

**Request id.** When recognized, it registers a request id for this transcript event with `userRequest()`, exactly as typing does, and `dispatch` shows a Surface with `user_request`, which the Presentation Policy checks as usual; 「收起」 only sends `dismiss` (the same as pressing Esc during live voice) and neither ends the call nor cancels tasks. No model tool was added; results history still opens only from user input. The typed path is unchanged (typing does no Simplified-to-Traditional folding).

**Silencing this turn (only this turn).** This is not a palm stop: delegations and lookups from earlier turns that have not returned yet are still spoken when they return (review M1).
- API-key route: if this turn's response already exists, only that response is cancelled (`response.cancel` with its `response_id`); if it does not exist yet, the next response without a core tag is cancelled when it is created (a continuation request the page itself sent earlier and that is not created yet does not count); if this turn's response has already finished (a late transcript), the view is only opened and no later response is cancelled. The palm-stop epoch is not advanced, and the "speak after tool results" state of earlier turns is not cleared; the state that was cleared when the cancelled response was created is restored. This turn's tool results are handed back without being spoken, and the cancelled response's subtitle is hidden. The core sideband receives `stop-reply {scope: "turn", response_id}` and only marks that response (or the next one) as unspoken for core tool results, without touching the palm-stop turn or queued continuations.
- ChatGPT-plan route: there is no `response.cancel`, so playback is muted and subtitles are hidden until this turn's reply arrives (the first assistant final transcript; if a delegation this turn started is still running, its result), plus 1.5 seconds (`LOCAL_COMMAND_DRAIN_MS`, so the tail of the audio plays out muted); at most 8 seconds (`LOCAL_COMMAND_QUIET_MS`). Sound and subtitles resume at once when (review M2): the user speaks again (`speech.started`, a new transcript), types, a system notice arrives, an earlier turn's delegation finishes, a memory event arrives (memory card opened, memory notice, delegate card, protected delegation; the memory status alone does not count), or a confirmation card (Action Gate) appears. So the core's memory confirmation questions and the confirmation card's explanation are always audible and subtitled. The core receives `stop-reply {scope: "turn"}`: with `NOUS_PALM_QUIET_DELEGATION` on, only this turn's delegation results become unspoken and earlier turns are unaffected; with it off, the core changes nothing and only the page mute applies.
- On by default with no setting: this is a real bug the user reported, and the actions only open or close views, with no external side effects.

**Trust level.** Matching uses only the user's final transcript: on the API-key route it is `conversation.item.input_audio_transcription.completed`, sent by OpenAI on the page's own WebRTC data channel; on the ChatGPT-plan route it is the sideband transcript arriving either on the data channel or relayed by the core over SSE (the same `item_id` is handled once). This is the same trust level as typed input: both are user input received by the trusted main window, and code that could forge these events could equally type into the input field; the page already registers typed requests with `userRequest()`. The `response_id` of `stop-reply` is accepted only in the shape of an upstream response id; otherwise it is treated as not yet created. A transcript is the recognition of whatever the microphone hears, so words from bystanders or a TV can be recognized too (ID-02 F11); that is why only whole, short, fixed phrases count and the actions only open or close views. The worst case is a bystander saying 「看結果」 and opening the latest result (the model's `get_tasks` could already speak task titles).

**Residual risks.** (1) When the transcript arrives after the model has started answering, the API-key route's response has already begun and its first words may be heard before it is cancelled; the ChatGPT-plan route can only mute, so the model still finishes that turn upstream (it just cannot be heard) and may call `get_tasks` in the background. (2) The ChatGPT-plan route mutes for at most 8 seconds; during that time, anything the model says on its own that is not covered by the resume conditions above (for example a prompt for which the core emits no event) is neither heard nor subtitled; another assistant message arriving within 1.5 seconds after this turn's reply resumes sound and is shown at once, but its first sounds may be muted. (3) Echo detection relies on the playback state; on the ChatGPT-plan route that comes from the remote audio level (uncalibrated threshold), and a miss can let an echo count as a command (which only opens or closes a view). (4) API-key route: when the transcript arrives before this turn's response while the page also has its own pending continuation request, the page assumes its own request is created first; if upstream orders them the other way, the earlier turn's continuation is cancelled and one result is not spoken. On the ChatGPT-plan route, if the core has not yet seen this utterance's transcript when stop-reply arrives, it takes the previous turn as this turn (this matters only with `NOUS_PALM_QUIET_DELEGATION` on). (5) The model is not told "do not answer local commands": when the matcher does not recognize an utterance the model must answer as before, and such an instruction could make it stay silent then too.
