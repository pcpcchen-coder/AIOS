# WK-00 喚醒詞 spike 驗證

日期：2026-10-29，Asia/Taipei。分支：`claude/wk-00`（基於尚未合併的 `claude/wake-speaker-plan`，PR #44）。範圍：[17 §13.4](../17_Wake_Word_and_Speaker_Recognition_Plan_2026-10.md#134-交付批次與估時) 的 WK-00。草案決定見 [ADR-0003](../adr/ADR-0003-local-wake-and-voice-recognition.md)。

**這不是產品功能，也不是實機驗收。** 本批只交付不接產品的 spike（`prototype/ambient-shell/spike/wake/`）與雲端容器上的量測。數字來自「雲端容器（Linux x86-64、4 核、Node 22.22.0）、TTS 合成語音或公開語料」，**不是 Mac、不是客廳、不是家人的聲音**。17 §13.2 的 W1–W12 都沒有通過，也沒有在 Mac 上執行任何東西。

## 3. 雲端量測

### 3.1 方法與計算方式

- 音訊依 100 ms 分塊送進引擎（與即時麥克風相近），每偵測到一次就 reset 串流（上游範例的作法）。單執行緒、`maxActivePaths` 4、`numTrailingBlanks` 1。
- **單核 CPU 比例**＝負例段的 CPU 時間（user＋system）÷ 音訊秒數 × 100，即「即時處理時大約占一個核心的百分比」。**RTF**＝牆鐘處理時間 ÷ 音訊秒數。兩者都只量負例段（不含模型載入與 TTS）。
- **每 100 ms 分塊耗時 p95**：nearest-rank（排序後取第 ⌈0.95·n⌉ 個）。
- **記憶體增量**＝載入引擎後的 RSS − 載入前的 RSS。程序的 peak RSS 包含主程序送來的合成正例，不代表引擎，所以不列為結論。
- **每小時誤報**＝誤報次數 ÷（負例秒數 ÷ 3600）。0 次時另以 rule of three 估 95% 上界：3 ÷ 小時數。
- **正例命中**：偵測時間落在 [詞頭, 詞尾 + 1.5 秒] 且關鍵詞相同；同一正例的重複偵測算誤報。計算在 `spike/wake/stats.ts`，並有單元測試。
- 執行環境：雲端容器 Linux x86-64、4 核、Node 22.22.0；掃描以 4 個子程序並行（每個子程序只載一個引擎）。並行與其他程式會互相干擾，**載入時間（0.6–5.4 秒）不穩定，不列為結論**。

正例（300 段，**全部是合成語音，不是真人**）：

- vits-icefall-zh-aishell3（8 kHz，174 位語者中平均取 30 位）與 vits-melo-tts-zh_en（44.1 kHz，單一語者，速度 0.8／0.9／1.0／1.1／1.2），轉成 16 kHz。
- 文字：「哈囉努斯」「嘿努斯」；英文別名以同音的「Hey noose」合成（TTS 詞典沒有 Nous），只有 melo 能念，共 5 段。
- 四種情境：單獨念、加白噪音（SNR 10 dB）、加合成音樂（SNR 10 dB）、接一句指令（例如「哈囉努斯，今天天氣怎麼樣」）。
- 困難負例 192 段：部分音節相同或相近的句子，例如「哈囉，大家好，歡迎收看今天的新聞」「我們一起努力吧」「俄羅斯總統今天發表談話」「Here is the news at nine」「Hey Lucy, how are you」。

負例（公開語料只下載到 repo 外的 scratchpad，不 commit）：

| 來源 | 授權 | 用量 |
|---|---|---:|
| AISHELL-1（OpenSLR 33）串流下載前 500 MB，10 位語者的華語朗讀 | Apache-2.0 | 掃描 3.0 小時、引擎比較 0.5 小時 |
| LibriSpeech dev-clean（OpenSLR 12），英文朗讀 | CC BY 4.0 | 掃描 3.0 小時、引擎比較 0.5 小時 |

### 3.4 原始輸出摘要

- 兩份報告都只含數字、設定與檔名，沒有音訊（`report.ts` 的檢查）。
- `bench-sweep.json`：`results[].job` 是設定；`positives.<情境>.keywords.<詞>` 是命中；`negatives.sources[]` 是各來源的小時數與誤報；`perf` 是 CPU、RTF 與分塊耗時；`tts_word_length_s` 是合成喚醒詞的能量端點長度。
- `bench-engines.json`：同一格式，四個引擎 × 兩種精度 × 兩個模型。
- `bench-variants.json`：同一格式，`--set variants` 的 8 組設定（§3.5）。

## 4. 瀏覽器 wasm 可行性

- npm `sherpa-onnx`（1.13.8 與 2.0.1）只有 `sherpa-onnx-wasm-nodejs.{js,wasm}`，以 `-sNODERAWFS` 建置：非 Node 環境一啟動就丟出 “NODERAWFS is currently only supported on Node.js environment.”。所以它不能直接在瀏覽器或 AudioWorklet 使用。
- 上游有 `build-wasm-simd-kws.sh`（建議 emsdk 4.0.23），產出 `sherpa-onnx-wasm-kws-main.{js,wasm,data}`，模型在建置時打包進 `.data`，檔名固定為 `encoder-epoch-12-avg-2-chunk-16-left-64.onnx` 等。上游沒有 KWS 的 wasm release 資產（只有 ASR、TTS、VAD 等的 HF Space workflow）。這個腳本關閉 TTS，所以自建產物不含 espeak-ng。
- 本批在雲端安裝 emsdk 的指令被環境權限擋下，**沒有自建，也沒有在瀏覽器執行 KWS**。spike 頁（`npm run wake:page`）會從 `spike/wake/public/kws-wasm/` 載入自建產物；找不到時照實顯示「只量擷取管線，不會偵測」。頁面有 `vite build` 成功與型別檢查，**沒有在任何瀏覽器開過**（雲端沒有 Chromium）。
- 備案評估：
  - 自建 wasm（建議）：一個建置步驟，模型（int8 encoder 約 4.7 MB）加 wasm 的實際大小未量，需追蹤二進位雜湊；npm wasm 在 Node 的數字（單核約 5–6%）可作為上限參考，瀏覽器的 SIMD 版通常更快，但要實測。
  - onnxruntime-web（專案已鎖 1.30.0）＋自寫 fbank 與 transducer 關鍵詞搜尋：不需新依賴，但要自己移植 kaldi-native-fbank 特徵與上游的關鍵詞解碼（context graph、門檻、trailing blanks），工作量估計 3–5 人日，且結果要逐一對照上游；目前不建議，除非自建 wasm 在 Electron 不可行。
  - Electron 主程序的 Node addon（17 §10.3 方案 B）：已實測可用、CPU 最低，但會出現第二個麥克風擁有者；只有方案 A 在 Mac 不達標時才重新評估。

## 7. 給 George 的 Mac 實測步驟

前提：在 Mac mini 的 `prototype/ambient-shell`，已 `npm ci`。以下都只在本機，音訊不寫檔；報告預設寫到 `$TMPDIR/aios-wake-spike/`（repo 外）。每位家人在報告裡只填代號（A、B、C）；`--person` 只接受 1–4 個英文字母或數字，填名字會被拒絕。

1. 安裝

```bash
npm ci
npm run wake:setup
brew install sox
```

   第一次執行時 macOS 會詢問終端機的麥克風權限，請允許。

2. 確認麥克風與 CPU（約 1 分鐘，說幾次「哈囉努斯」）

```bash
rec -q --buffer 3200 -t raw -r 16000 -e signed -b 16 -c 1 - | npm run wake:spike -- listen --model zh-en-3M --keywords "哈囉努斯,嘿努斯,Hey Nous"
```

   每次偵測會印一行 JSON（時間、關鍵詞、`score: null`、門檻、推估長度、CPU）。按 Ctrl+C 結束。

3. 家人正例（每人 30 次，安靜與電視開著各一輪，兩個模型各一輪）

```bash
rec -q --buffer 3200 -t raw -r 16000 -e signed -b 16 -c 1 - | npm run wake:spike -- listen --mode family --trials 30 --person A --model zh-en-3M --keywords "哈囉努斯"
rec -q --buffer 3200 -t raw -r 16000 -e signed -b 16 -c 1 - | npm run wake:spike -- listen --mode family --trials 30 --person A --model wenetspeech-3.3M --keywords "哈囉努斯"
```

   畫面提示「第 n/30 次」時，在平常坐的位置自然地說一次「哈囉努斯」；6 秒內偵測到算成功。報告有成功率、從說完到偵測的延遲（能量端點推估）與從最後一個發音單元到偵測的延遲。

   **先做 5 次的試跑**（`--trials 5`）。雲端的合成語音對完整候選詞 0 命中、原因未定（§3.3、§3.5），為了不要念完 30 次才發現都是 0，請每位家人再各跑兩輪，同樣念「哈囉努斯」：

```bash
rec -q --buffer 3200 -t raw -r 16000 -e signed -b 16 -c 1 - | npm run wake:spike -- listen --mode family --trials 30 --person A --model zh-en-3M --keywords "哈囉努斯(hā-lóu)"
rec -q --buffer 3200 -t raw -r 16000 -e signed -b 16 -c 1 - | npm run wake:spike -- listen --mode family --trials 30 --person A --model zh-en-3M --keywords "努斯"
```

   第一輪是台灣常見的 hā-lóu 念法；第二輪只看子詞「努斯」是否觸發（「努斯」只用來診斷，不是喚醒詞候選）。若「努斯」常命中而兩種「哈囉努斯」都很少，問題在「哈囉」的發音單元；若三者都很少，問題可能在收音或模型。若成功率明顯不佳，也可加 `--keywords "哈囉努斯#0.15"` 或 `"哈囉努斯:1.5"` 再跑一輪，並記下設定。

   延遲的偏差：CLI 依樣本序號與最近一塊到達的時間往回推算每個樣本的時間，不再用整塊的到達時間；`--buffer 3200` 讓 sox 每 100 ms 送一塊。sox 與作業系統的固定緩衝沒有算在內，所以延遲仍可能低估約一塊（約 100 ms）以內。

4. 電視負例（至少 8 小時，只計數、不錄音）

```bash
caffeinate -i sh -c 'rec -q --buffer 3200 -t raw -r 16000 -e signed -b 16 -c 1 - | npm run wake:spike -- listen --mode tv --hours 8 --program "新聞台" --model zh-en-3M --keywords "哈囉努斯,嘿努斯,Hey Nous"'
```

   `caffeinate -i` 讓 Mac 在 8 小時內不進入閒置睡眠（螢幕可以關）；睡眠會中斷收音。換台時在同一個終端機打新的節目名稱再按 Enter。每次誤報只記時間、關鍵詞、當時的節目名稱；**事後無法重播**，所以若誤報多，請在旁邊紙本記下當時大概在說什麼。另一個模型請另一天再跑一次。

5. 與鏡頭管線同時運作（W11 的前置）

   - 開 Nous App，鏡頭開著，讓電子腦在待機狀態 10 分鐘；用「活動監視器」或 `top -pid <Nous 的 PID> -stats pid,cpu -l 0` 記錄 CPU。
   - 同時在終端機跑步驟 2 的 `listen`，再記 10 分鐘 CPU；CLI 每分鐘也會印自己的 CPU。
   - 這段期間做幾次「張掌停止」，確認仍有反應。
