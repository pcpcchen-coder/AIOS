# WK-02 喚醒接上即時語音驗證

日期：2026-10-31，Asia/Taipei。分支：`claude/wk-02`（基於 main `40d92fb`）。範圍：[17 §13.4](../17_Wake_Word_and_Speaker_Recognition_Plan_2026-10.md#134-交付批次與估時) 的 WK-02。規則見 [ADR-0003](../adr/ADR-0003-local-wake-and-voice-recognition.md)；底層見 [WK-01a 驗證](wk-01a-2026-10-31.md)。

**這不是實機驗收，也沒有真正的喚醒偵測。** 喚醒引擎仍未接上（WK-01b 只做了準備部分），產品偵測器照實回報 `runtime_missing`、不開麥克風，所以在產品裡**現在不會有任何喚醒觸發**。本批把觸發之後的路接好：開通話、問候、限速、沒人出聲就結束、費用紀錄。以下測試全部在雲端容器以 fixture（假路徑、假偵測事件、假 MediaDevices、假時鐘與假計時器）執行，**不是 Mac、不是麥克風、不是喚醒詞**。17 §13.2 的 W1–W12 都沒有在 Mac 上執行。

## 1. George 的決定（2026-10-31）

| # | 決定 | 本批的做法 |
|---|---|---|
| E1 | 喚醒後**一律打招呼**，不另加開關 | `greetingFor("wake_word")` 一律建立 `GreetingOnce`，不讀「看著說話時先打招呼」。稱名照既有的「打招呼時稱呼認出的家人」，**不需要**「看著說話」與「看著說話時先打招呼」；其他條件（雲端稱名說明、證據新鮮、同一追蹤世代）不變，不符合時只說不含名字的句子（例如「我在」） |

## 3. 設計

### 3.1 觸發到通話

偵測 → 防護 → 提示音 → 沒有取消而且仍在 `listening_local` → `onWakeTrigger`。通話進行中或開始中、家人辨識畫面開著時忽略；即時語音不能用時顯示「即時語音目前不可用（原因）」；其餘呼叫 `startRealtime("wake_word", { wake })`。路徑選擇、計費通知、改路徑與同意說明全部沿用既有的 `openRealtime`。喚醒開始的拒絕只顯示字幕，不打開輸入框（使用者沒有在打字）。還沒有即時語音同意時，喚醒打開既有的同意說明，但每個限速時窗（60 秒）最多一次，其餘喚醒忽略；使用者按同意後以 `wake_word` 開始（問候、沉默 5 秒結束與限速照常），不同意就不開。

### 3.2 問候

核心在 `/api/realtime/start` 對 `wake_word` 發互動 ID，`claimGreeting` 回傳 `source: "wake_word"`。`IdentityService` 看到這個來源時跳過「看著說話」「看著說話時先打招呼」的要求，其他照舊。頁面端的同步辨識在喚醒問候還沒決定前也放寬同樣兩個設定（`ambientEnabled`），並在核心發出互動 ID 之後重新問一次 `ambient_status`。改路徑時兩個工作階段共用同一個 `GreetingOnce`，claim 只能成功一次，所以一次喚醒最多一次問候。核心的放寬（`wakeGreetingOpen`）只在互動還沒用過，而且開始的決定還在、正在連線，或連上 20 秒內且通話還在時成立；頁面在連線前放棄（`/api/realtime/end` 帶著還沒送 offer 的決定）、連線失敗而沒有改路徑、或通話結束時就結束。頁面在 `stopRealtime`、通話結束與記憶撤銷時也清掉自己的放寬。

### 3.3 限速

限速在核心（`RealtimeSessions.start`），計算被接受的 `wake_word` 開始；路徑不能用而被拒的、其他來源的都不算。**被接受之後才連線失敗的也算**（為了簡單，不另外退回次數）。頁面收到 `wake_limited` 時以核心給的 `retry_after_ms` 暫停聆聽，計時器到期自動恢復（沿用上次的麥克風，不顯示「已恢復」字幕）。使用者在這段時間按「暫停聆聽」時以使用者的暫停為準。

### 3.4 沒人出聲就結束

計時只看音量門檻（RMS 0.03、連續 300 ms，與即時語音的開口偵測相同，未校準），**不是 VAD**，分不出人聲與電視。音量來自通話租到的那一份麥克風複製品（`browserWatchLevel`，每 50 ms 一個數字，不保存樣本）。改路徑時舊的那份歸還、新的那份重新接上。逾時的結束原因 `no_voice` 交給核心的費用紀錄。

### 3.5 F6 費用紀錄

每通即時語音（不只喚醒開始的）結束時寫一筆：

```json
{"v":1,"session_id":"rt_…","route":"api_key","model":"gpt-realtime","source":"wake_word","wake_id":"int_…","started_at":"…","ended_at":"…","connected":true,"connected_ms":7250,"end_reason":"no_voice","no_voice_auto_end":true,"usage":{"responses":2,"input_tokens":120,…},"cost":"unknown"}
```

沒有逐字稿、音訊或名字。核心有時比頁面的 `/api/realtime/end` 先看到結束（例如 live 的 `closed` 先到）：結束後 15 秒內（`COST_AMEND_GRACE_MS`），同一個擁有者晚到的 `no_voice` 或 API key usage 會改寫同一筆（`VoiceCostLog.amend`），不另加一筆。`usage` 只有 API key 路徑頁面加總的 `response.done` 數字（頁面回報，不是帳單）；ChatGPT 方案路徑一律 `"unknown"`。`cost` 一律 `"unknown"`：沒有單價與帳號用量證據，不推算成確定帳單。沒有 `session_id` 的舊 API key 呼叫（`/api/realtime/call` 不帶 session）不經 `RealtimeSessions`，不記。

### 3.6 `NSMicrophoneUsageDescription`

- 英文：Nous uses the microphone for voice conversations and, if you turn on always-on wake listening, to detect "Hello Nous" on this Mac only; that audio stays in memory and is not saved or uploaded. After the wake word or when you start a conversation, audio is sent to your selected voice service until the conversation ends.
- 中文：Nous 使用麥克風進行語音對話；若開啟常駐喚醒聆聽，也只在這台 Mac 本機偵測「哈囉努斯」，偵測時的聲音只留在記憶體、不保存也不上傳。喚醒或開始對話後，音訊會傳送至你選用的語音服務，直到對話結束。

### 3.7 旗標關閉

`NOUS_WAKE` 關閉時 `wake_word` 一律當成 `user`（沒有互動 ID、沒有限速、不收 `wake_id`），頁面不載入 `src/audio/`，所以不會有觸發或計時。**唯一刻意的例外是 F6 費用紀錄**：George 2026-10-31 決定「一律記錄，不綁喚醒開關」，所以旗標關閉時核心照樣建立 `VoiceCostLog`、每通都寫 `voice-cost.jsonl`、`/api/realtime/end` 讀 `reason`／`usage`、有 `GET /api/realtime/cost-records`，頁面在 API key 路徑結束時一律送 usage。`tests/wake-flag-off.test.ts` 的快照（頁面標頭、`/api/settings`、選單列）沒有更新，仍逐位元組相同；新增的檢查確認 `wake_word` 與 `user` 開始的回應逐位元組相同，另有一個測試明確列出 F6 這個例外（旗標關閉時 `cost-records` 是 200）。「旗標關閉時逐位元組相同」的說法不包含 F6。

## 4. 與規劃不同之處

- 喚醒問候的同步辨識：核心另外提供 `wakeGreetingOpen()`，讓 `ambient_status`／`ambient_probe` 在喚醒問候還沒決定時接受取樣。只改 `claimGreeting` 的話，頁面在「看著說話」關閉時連取樣都做不了，就永遠不會稱名。
- `WakeTrigger` 的處理邏輯（要不要開通話）放在 `src/realtime-session.ts` 的純函式 `wakeTriggerAction`，因為 `src/main.ts` 不能靜態 import `src/audio/`（`tests/audio-privacy.test.ts`）。`WakeCallWatch` 由控制器的 `watchCall` 建立。
- 費用紀錄記錄所有通話，不只 `wake_word`，而且不綁 `NOUS_WAKE`（George 2026-10-31「一律記錄，不綁喚醒開關」；17 §5.7 只要求喚醒開始的；多記不會少記）。這是旗標關閉「逐位元組相同」唯一刻意的例外。live 連線失敗而改路徑時，失敗的那一次也記一筆（`connect_failed`、`connected: false`）。
- 限速暫停結束時不顯示「已恢復」字幕（不是 App 重開或睡眠回來的自動恢復）；選單列狀態照實更新。

## 6. 現在不能驗證的

- **真正的喚醒觸發**：要等 WK-01b（關鍵詞與門檻、Mac 上真的偵測；第一次 CI 建置的雜湊已於 2026-10-31 寫入清單）。在那之前產品不會觸發，本批的觸發路徑只在 fixture 裡跑過。
- **沉默 5 秒是否合適**、RMS 門檻能否分辨客廳的電視與人聲、Nous 說完後的回聲會不會被當成有人說話（可能讓計時提早停止）。
- 兩條路徑實際的問候時間與稱名（17 §13.2 的 W4 通話部分、S13）。
- 費用紀錄裡 API key 路徑的 usage 是否與 OpenAI 帳號用量一致（只是頁面回報的數字）。
- 誤喚醒的真實代價（W6 電視負例要對照費用紀錄）。

| 7 | — | 電視負例（W6）每次誤報都對照費用紀錄的通話數、連線秒數與 `no_voice` |

## 8. 風險與限制

- 頁面腳本仍可以送 `source: "wake_word"` 開真的通話（ADR-0003 §2.2）；限速、可見指示與費用紀錄限制後果，不能消除。
- 喚醒問候期間的同步辨識放寬只靠核心知道「有喚醒開始、還沒決策的互動」；那段時間任何頁面腳本都可以送取樣，與 ID-02 已記錄的殘餘風險同類（回應不含結果）。
- `rate_limited` 暫停存在頁面記憶體；頁面重新載入會忘記，核心的限速照舊。
- `WakeCallWatch` 是音量門檻：電視開著時可能永遠不逾時；Nous 播音的尾巴可能被當成有人說話。
- 費用紀錄的 `connected_ms` 是核心的牆鐘差，不是供應商計費的秒數。
