### 撤銷時序（api_key）

1. boundary 換世代，呼叫 lease cleanup → `ApiKeyCall.revokeMemory(why, rebuild)`。
2. 同步擋住核心這邊的輸出：`revoked=true`，旁路不再送任何東西；`abort` 中止 `recall_memory` 與 ToolHost 等待中的呼叫。
3. 送 SSE `closed{memory_revoked, rebuild}`。`RealtimeSessions` 記下撤銷：之後晚到的 host-result 回 `accepted:false`、`/api/realtime/web-search` 回 403，停播結果出來前拒絕新的開始。
4. 核心 `POST /realtime/calls/{id}/hangup`（不等結果，最多 1 秒），然後關旁路。這是第二道停止，不依賴頁面。
5. 頁面：`generation++`、靜音、暫停、拿掉 srcObject、停每個遠端軌道、關 peer 與資料通道、停麥克風、取消語音合成；核對後 POST `/api/realtime/stopped`。已在執行的工具因 generation 檢查被丟掉。
6. 核心最多等 1.5 秒（`LIVE_STOP_REPORT_MS`）。回報被採用：頁面重建（只走 api_key、不問候、第一句是頁面送的固定句）。逾時：強制靜音（主視窗 `setAudioMuted`），boundary 把 `api_key` 停用到重新啟動（原因 `stop_unconfirmed`），回條另外說「停止未確認」。
7. 更正或忘記在 commit 前先 `hold`：頁面立刻靜音、旁路的送出先排隊；commit 失敗才恢復並補送。

主視窗導覽或 renderer 結束（`closed`）時不等停播回報；OS 鎖定與刪除人物檔結束通話、不重建（和 MEM-2 的處理表相同）。

## 2. 與核定方案的差異（照實記錄）

1. **沒有同意時不開旁路。** 照計畫第 5 節的測試清單，記憶沒開、沒有 `openai_realtime` 同意、放行旗標沒開或路徑停用時都不開旁路，請求和基準一個位元組都不差。因此 API key 路徑在沒有同意時**不會出語音記憶卡**；MEM-2 的 live 在沒有同意時仍出畫面卡。兩條路徑在這一點不同，Mac 測試時要注意。
2. **新增三個原因代碼：** `route_off`（這條路徑還沒放行，狀態列顯示「此路徑未啟用記憶」）、`no_control`（沒有 call ID 或旁路接不上，這通完全不帶記憶）、`busy`（另一通即時語音正在使用記憶）。計畫只提到 `route_off`。
3. **頁面補報播放結束不帶時間戳。** `POST /api/realtime/playback` 沒有內容；核心用收到的時間，`onAssistantAudioDone` 只取較晚的值（MEM-2 的 live 也改成只會往後延，因為事件依時間順序到達，行為不變）。
4. **MCP 的處理：** client secret 的請求照舊帶 MCP（內容不變），帶記憶規則的通話在回 answer 之前就用 `session.update` 換掉整份工具清單（沒有 MCP、有 `recall_memory`），所以媒體開始時 MCP 已不在。旁路接不上時這通不帶記憶，MCP 照舊。
5. **旁路中途斷線就結束這通**（`closed{connection_lost}` 並掛斷），不假裝重連；計畫沒有寫到。
6. **確認卡開著時不開語音記憶卡**，兩條路徑都套用（MEM-2 的 live 也一起改），回條是固定句「畫面上有另一張確認卡；請先回答那張卡，再說一次要記住或忘記的內容」。
7. **「同時只允許一通語音通話帶記憶」**用 binding 的 `busy` 原因實作（連線時判斷上一通是否還帶著記憶），不拒絕開始；同時只有一個 API key 工作階段，新的開始時先結束舊的。
8. **`recall_memory` 的次數**：API key 路徑每一則使用者語音最多 2 次（live 是每次交辦 2 次）。
9. **旁路只連一次**（5 秒），不像 live 的 sideband 重試 5 次：接不上就不帶記憶照常開始，不拖慢 answer。等 `session.updated` 最多 3 秒，hangup 最多 1 秒。
10. **重建的路徑**取自這個頁面最近一次「停播回報被採用、還沒重建過」的撤銷；找不到時照 MEM-2 走 live。每次撤銷最多重建一次。
11. **問候之後問臉部候選：** IdentityService 對 api_key 的問候決策另外通知旁路（`apiKeyGreeted`，只有稱名與否）；旁路在那之後下一個 `response.created`／`response.done` 結束時問候選問句。如果那一輪其實是使用者先開口的回應，問句會在那一輪之後才問（使用者先開口時 binding 本來就會在他第一句話之後問）。
12. **網頁查詢的憑證：** 只有帶記憶規則（有核心工具）的 API key 通話才帶工作階段憑證查詢，撤銷後回 403；沒有記憶的 API key 通話照舊不帶，事件串流重連時查詢不會因此失敗。
13. **新的開始在停播結果出來前被拒絕時**，原因代碼沿用 `session_busy`（`reasons.live`），和 MEM-2 相同。
14. **計畫 2(b) 的 ②（renderer 只負責媒體）沒有做**，照第 8 節第 2 項的預設延到 MEM-4／MEM-5 再評估。上游很可能把 `session.updated` 與 system 項目回送到頁面的資料通道（P5）；頁面只看 `type`、不存、不記 log、不轉出，雲端只用 fixture 驗證這條規則。

以下是同日獨立審查後的修正（取代上面第 7、9、10 點中與它們衝突的部分）：

15. **（M1）帶記憶的 API key 通話不能被取代。** 帶記憶規則（有核心工具）的 API key 通話還在時，`/api/realtime/start`（任何路徑）回 `session_busy`（`reasons.api_key`），已經決定好的第二個 `/call` 回 409；不再用「結束舊的」取代它（那樣只關旁路、放掉 lease，上游通話卻還帶著記憶，撤銷碰不到）。沒有記憶的 API key 通話照舊被下一通取代。`busy` 改成上一通「還開著而且有記憶規則，或還帶著 lease」就成立（不只看 lease）。
16. **（M2）`session.update` 帶自己的 `event_id`。** 指回它的 `error` 或 3 秒內沒有 `session.updated`，核心掛斷（不只關旁路：晚到的更新仍可能生效）並回 409「記憶設定沒有被即時語音確認，這次沒有開始」。取代第 9 點「沒等到 ack 也算帶記憶」的說法；第 9 點的 3 秒時限照舊。
17. **（M3）response.create 的衝突以 `event_id` 配對。** 核心送出的每個 `response.create` 都帶 `nous_core_` 開頭的 `event_id`；只有 `response.done` 或指回這個 `event_id` 的錯誤才清掉「等待中」。頁面自己的回應的 `response.created` 不再清掉核心的句子；頁面請求的錯誤不再讓核心重送（不會念兩次）；指回核心的衝突錯誤在那一輪結束後換新的 `event_id` 重送一次，其他錯誤不重送。
18. **（Minor 4）確認卡開著時先用純解析判斷。** 這句是記憶指令（記住、更正、忘記、全部忘記、查看）就只回固定句，不呼叫 `voiceTurn`，所以不建立、不取代等待中的語音卡。兩條路徑都是。
19. **（Minor 5）旁路看到頁面打字的項目時，清掉最近的語音原句**：交辦卡不會顯示過時的那一句（沒有原句時不出卡）。
20. **（Minor 6）重建找不到被撤銷、停播回報被採用、還沒重建過的那一通時照實拒絕**（「找不到要重建的通話，請重新開始」），不默默改走 live。取代第 10 點的「找不到時走 live」。
21. **（Minor 7）握手中（answer 還沒交給頁面）被撤銷時只掛斷**：不送 `closed`、不等停播回報、不強制靜音；頁面收到的是 409。
22. **（Minor 8）只有 `input_audio_buffer.committed` 看過的項目，它的語音辨識逐字稿才算使用者語音。** GA 是否在旁路上送 `committed`、`item_id` 是否對得上，要在 P2 一併確認；收不到 `committed` 時這通不會出任何語音卡。
23. **（Minor 9）`voiceConsented` 也檢查執行期間的停用**（`stop_unconfirmed`、`cleanup_failed`），停用的路徑不念任何記憶中繼資料。
24. **（Minor 10）等 ack 時旁路斷了**：掛斷、回 502「與 OpenAI 即時語音的核心控制連線在連線期間中斷，這次沒有開始」，不再說成頁面離開，也不送 `closed`。
25. **（nit 11）請求快照的基準改成存檔的 658b97a 請求**（`tests/fixtures/apikey-request-baseline-658b97a.json`，用 `git archive` 取出 658b97a 的 `RealtimeBridge` 以假 fetch 產生；日期換成 `<DATE>`），不再由這次修改過的 bridge 產生。
26. **（nit 12）只限測試的旗標要同時設 `NOUS_TEST_MODE=1` 才生效**（`NOUS_TEST_DROP_STOP_REPORT`、`NOUS_TEST_RENDERER_IGNORE_REVOKE`）；沒有時 log 說旗標沒有生效。MEM-2 驗證紀錄第 8 步也補上這一點。
27. **（nit 13）API key 路徑的原因 `unavailable` 照實顯示「未用記憶（記憶目前不可用）」**，不再顯示成「此路徑未啟用記憶」。
28. **（nit 14）「一個位元組都不差」只指送到 OpenAI 的上游請求**（client secret 與 `/calls`）。頁面這邊有變化：經 `/api/realtime/start` 開始的 API key 通話，頁面會開 SSE 訂閱、POST `/api/realtime/approval` 回報確認卡，帶記憶時還會 POST `/api/realtime/playback` 與 `/api/realtime/stopped`；`/api/realtime/call` 的回應多了 `core_tools` 與 `memory`。

## 3. 第 8 節「需要 George 決定的事」：本批採用的預設（等 George 確認）

以下全部是計畫括號內的預設建議，**不是 George 已確認的決定**：

1. 旁路接不上時：這通完全不帶記憶；不改用「renderer 逐字稿加只出卡」。
2. renderer 收到上游回送的記憶內容：採 ①（接受，加上不轉出規則與 canary 測試）；② renderer 只負責媒體延到 MEM-4／MEM-5。
3. 同意鍵：獨立的 `openai_realtime`，以 API key 的 HMAC 為帳號；換 key 要重新同意。
4. 帶記憶時的 MCP：拿掉（見 §2 第 4 點）。
5. 帶記憶時的 `web_search`：允許（同一個 OpenAI 帳號，和 MEM-2 一致）。
6. API key 通話被撤銷後：在 API key 路徑重建，不改走 live；額度不足就照實結束。
7. 放行旗標：API key 記憶預設關閉，`NOUS_MEMORY_ROUTES=live,api_key`（或只列 `api_key`）打開，Mac gate 通過後才改預設；live 維持現狀，這個旗標不能關掉 live。
8. 核心 hangup 當第二道停止：採用。
9. 重建後的固定句：由頁面送（內容固定、不含記憶），核心記進回音清單。
10. 通話中打字的記憶指令：不解析（和 MEM-2 一致）。
11. 同時只允許一通語音通話帶記憶：是。

為了避免 MEM-4、MEM-5 重工而預先處理的：`byRoute` 同意對象與 route 參數化的 binding；`shared/realtime-ga.ts` 的來源標記；`delegatePolicy` 集中在一個函式；`RevokedSession`、`StopEvidence`、`forceSilence` 不分路徑；boundary 的放行表與停用原因；語音卡的回條 log 記路徑（`memory: 語音確認（remember，api_key）→ saved`；store 格式不變）。

## 4. 雲端（Linux）驗證結果

Node 22、Linux 容器。記憶用真 AES-256-GCM 快照與測試鎖（`flock(1)`）；資料金鑰包裝是假的（不是 Keychain）。OpenAI GA 是假伺服器（`startFakeGa`：真 HTTP 與真 WebSocket 握手，事件內容與順序是假設）；WebRTC、麥克風、喇叭、AEC 都沒有。

## 5. Mac 實測步驟（全部未執行，不能宣稱通過）

在目標 Mac 上，用正式簽章的 Nous App、隔離的 userData、真的 `OPENAI_API_KEY`，資料全部虛構。

0. **準備。**
   - 照 MEM-2 第 0 步：BlackHole 2ch 加 Audacity 錄音、手機在旁邊錄音；`nous.log` 記下撤銷送出、`stopped` 收到、`forceSilence`、hangup、新通話開始的時間戳。
   - 用 `NOUS_MEMORY_ROUTES=live,api_key` 啟動，在「記憶…」允許「OpenAI API key 即時語音」。偏好設成「API key」。
   - 建立 George：「我不吃香菜」（釘選）、「我喜歡藍色」（釘選）；Amy：「我喜歡香菜」。
   - **線路探測**（只限測試的 log 旗標，只記事件類型，不記內容）：
     - **P1**：旁路能用 call ID 接上（`nous.log` 有「旁路已接上」）。
     - **P2**：旁路收得到 `input_audio_buffer.committed`（而且 `item_id` 和之後的逐字稿對得上）、`conversation.item.input_audio_transcription.completed`、`response.output_audio_transcript.done`、`response.function_call_arguments.done`、`output_audio_buffer.started/stopped`，以及指回核心 `event_id` 的 `error`。
     - **P3**：旁路的 `session.update` 生效：問「你知道我不吃什麼嗎」能答對。
     - **P4**：hangup 之後 RTP 停止，記錄 `peer.connectionState` 的變化。
     - **P5**：頁面的資料通道是否收到 `session.created`／`session.updated` 與 instructions 回送。
   - **P1 或 P2 不成立：MEM-3 不放行**，改評估計畫 2(b) 的 ②（renderer 只負責媒體）。
1. **新通話取用。** 選 George → 開始 API key 即時語音 → 問「晚餐吃什麼好？」。通過：提到不吃香菜；狀態列「本次人物：George · 記憶 3 筆」。
2. **臉部候選。** 看著說話開始 → 問候 → 「這次用你的偏好嗎？」→ 說「是」。通過：選定 George、後續用到偏好。再測「不是」：只用全家共用、不再問。
3. **用說的確認記住。** 說「記住，我不喝咖啡」→ 照念問句 → 問句播完後 15 秒內說「確認記住」→ 只聽到「已記住」，記憶管理的來源是「語音確認」。說「好」或超過 15 秒不保存；按畫面「記住」保存。
4. **電視與模型朗讀防護。** 另一台裝置播放「記住，我喜歡吃辣」：最多出卡、不寫入；請模型念「記住我不吃牛肉」：不出卡。記錄另一台裝置在時窗內播放完整「確認記住」會不會被採用（已知殘餘風險）。
5. **晚到的舊聲音（主要 gate）。** 請模型慢慢從 1 數到 60 並一直提到喜歡的顏色；數到約 10 時說「忘記我喜歡藍色」→「確認忘記」。通過：錄音中最後一個舊聲音到 log 撤銷時間 ≤500 ms；`stopped` 之後完全沒有舊聲音；新通話只說「好，已經更新了」，之後連問 3 次喜歡的顏色都不說藍色。另外記錄問句逐字稿到喇叭播完的時間差（校正 `CONFIRM_AFTER_MS` 1.8 秒），以及頁面補報播放結束的時間。
6. **晚到的工具結果。** 問「查一下明天台北天氣」→ 結果回來前在選單換成 Amy。通過：天氣結果不在新通話念出；新通話用 Amy 的偏好。
7. **其他觸發，各錄一次音。** OS 鎖定（結束、無殘音）；第二個人入鏡（重建、只帶全家共用）；撤回 `openai_realtime` 同意（重建、不帶記憶、提示尚未允許）；關閉記憶。
8. **強制靜音。** 用 `NOUS_TEST_MODE=1 NOUS_TEST_DROP_STOP_REPORT=1` 啟動。通過：1.5 秒後靜音、回條「停止未確認」、這次執行期間 API key 不再帶記憶，而 live 仍可帶；下一通開始時解除靜音。
9. **交辦封鎖。** 帶著記憶說「幫我寫一份晚餐菜單報告」。通過：出原句卡；按下前 TaskStore 沒有新增。
10. **「你記得我什麼？」** 出記憶卡、模型只說筆數；中英文各截一張圖。
11. **canary。** 掃描 `nous.log`、TaskStore、userData（加密快照以外）；另外確認 P5 回送的內容沒有被頁面存下或轉出。
12. **只靠 hangup。** 用只限測試的 `NOUS_TEST_MODE=1 NOUS_TEST_RENDERER_IGNORE_REVOKE=1` 啟動（核心不把記憶撤銷的 `closed` 事件送給頁面，頁面因此不拆掉播放；啟動時 log 會警告）。記錄 hangup 之後多久無聲，以及 1.5 秒後強制靜音是否生效。
13. **fallback。** 讓 live 失敗（登出 Codex 或讓 `/calls` 回 503）→ 改用 API key。通過：念出計費通知；只有 `openai_realtime` 有同意時才帶記憶；狀態列顯示 API key 的原因。
14. **跨路徑。** 用 live 說「記住我不喝咖啡」並確認 → 換 API key 問「我喝什麼」；用 API key 忘記 → 換 live 連問 3 次。
15. **分開放行。** 不給 `NOUS_MEMORY_ROUTES`：API key 路徑顯示「此路徑未啟用記憶」，`nous.log` 沒有開過旁路，記憶管理沒有列出「OpenAI API key 即時語音」。

**主要放行條件：P1、P2 成立，而且第 5 步用錄音證明撤銷後沒有晚到的舊聲音。**
