# MEM-1 family memory for ordinary text chat: cloud verification and Mac gate

Dated 2026-10-29, Asia/Taipei. The starting point is main `2af1aa7`; the work was done on branch `claude/mem-1` in a separate worktree and was not committed, pushed, or merged. All people, accounts, and memory content are fictional test data.

**Batch status: the MEM-1 code and the parts verifiable in the cloud (Linux) are complete; none of the Mac gate items has been run or passed.** This does not show that Nous can remember family members on real hardware. Voice memory (MEM-2, MEM-3), background-task memory (MEM-4), and automatic consolidation (MEM-5) are not implemented.

Fixes after an independent review on the same day (parser misreads, pausing not wired, delegation across turns, memory reaching unconsented accounts through history, expiry purge, sensitive data, Keychain timing, family-deletion reporting, minors and credentials, and more) are listed in §2 items 2, 4, 9, and 12–22; test numbers are updated.

## 2. Differences from 16 and the approved plan (recorded as is)

1. **Simplified-Chinese command words do not trigger writes.** The simplified/traditional mapping is used only for search tokens; “记住…” is treated as ordinary chat rather than rewriting the user's text to fit a command.
2. **Correct and forget need a leading verb and an explicit memory target.** Correction needs 「更正，…」 or 「更正／改一下記憶：…」; forget needs 「忘記…」「忘掉…」 or `forget about/that …`. 「把報告改一下」「這段文字幫我改一下」「我現在可以吃香菜了，改一下」「忘記密碼了怎麼辦」 and “forget it” are ordinary chat. When no matching memory is found, the original sentence goes to the model unchanged (no “not found” reply). The trailing 「…，改一下」 form from 16 §1 is therefore not supported; use 「更正一下，…」 instead.
3. **When a sentence needs a card, the question waits.** Chat is sent only after the card is answered, with a fresh `memory_turn` from the card answer. 16 does not specify this order; it keeps an unconfirmed person or unsaved content from shaping the answer.
4. **“I am X” selects a person only when X is an existing person.** If X is not an existing person and the sentence does not go on to “remember” (「我是老闆」, “I'm Fine”), it is ordinary chat; only with a following “remember” does the “Create a memory profile for X?” card appear. 「現在是…」「這裡是…」, “It's…”, and “This is…” are not self-identification. The same-name choice card appears only when older data already has duplicates.
5. **There is no “moved out” field.** Family recognition only has `minor`, so when deleting a family member only minors default to deleting memory; a moved-out default waits for a matching identity field.
6. **Consent is stored per service + account, separately for a person or the household.** First-time setup allows the chosen person and the household together; afterwards memory management changes only the chosen scope. Mock mode has no account and sends no memory.
7. **`reviewAfter` is always null.** The field is stored; the review prompt flow is not implemented.
8. **Edit and forget in memory management obtain tickets through the MEM-0 literal grammar** (`更正：id@rev：content`, `忘記：id@rev`). Pin, profile deletion, and family recognition linking are not memory-content writes; they are gated by native confirmation (delete, link) and the management token, without tickets.
9. **Minors: neither chat nor cards can write, correct, or forget**, and “Save for household instead” is not offered; the reply is always “a parent manages this in Memory…”, and the buttons on the “What do you remember about me?” card do not work either. Memory management can add, edit, and forget, and can manually “Mark as minor” (also without a family recognition link). The 17 §9.5 supplementary proposal of a parent-confirmation card was not adopted.
10. **Resending the same sentence after a restart** is deduplicated by “same person, same normalized key, same content” and returns `unchanged`; store operation receipts can still be queried as `saved` / `receipt_expired`.
11. **On revocation the text stream does not send `done`**; `memory_revoked` is terminal, and the page marks the turn stopped and clears history containing memory.
12. **History clearing scope**: if any turn used memory, correction, forgetting, switching person, pausing (OS lock, idle, more than one face or tracking loss, family deletion), or revocation clears the whole history; affected sentences cannot be separated (16 §8). Every core response carries the presence epoch (`presence.epoch`), and when it changes the main process also pushes a content-free notification, so the page clears history even without a stream.
13. **Core memory receipts and pure memory commands are not put in model history.** Receipts contain memory content; keeping them would let a later service account without consent receive memory through history. The page already clears the conversation when the service or account changes.
14. **The delegation block after memory spans turns.** If this turn or the conversation history used memory, delegation always becomes “Delegate this?” (titled with the user's own sentence); speech sources share the same conversation and follow the same rule. The core also records whether memory was used since the last request without history, so requests without a `memory_turn` are blocked too.
15. **Sensitive data is refused.** Fixed words such as password, token, card number, account, medical record, diagnosis, national ID, and passport, and long digit runs (≥6 digits, or ≥9 digits with spaces or hyphens) always get “This kind of data cannot be stored in memory”, including additions and edits in memory management.
16. **“Forget everything” is only in memory management.** Saying 「全部忘記」 in chat only returns a hint and deletes nothing; “Forget all … memory” in memory management needs the management token and is followed by a native confirmation.
17. **Turning memory on/off, changing consent, and selecting a person need a credential.** setup accepts only the first-time setup card or a management token; select accepts only the one-time `select_card` of the main window's “Current person” menu (a new one per epoch) or a management token.
18. **When Keychain and the folder are touched.** status never opens the memory file; while memory is off or unknown, typing only runs the parser. The memory file is opened only after saying “remember…”, opening “Memory…”, or on the first typed turn when memory was on in the previous run (`configDir/memory-enabled.json` stores only `{ enabled }`, no content). After a key failure memory stays disabled for this run and is reopened only on an explicit retry from “Memory…”. Deleting a family member does not open the memory file just to count items (the dialog says they are handled at deletion).
19. **“Remember for today” is purged with a tombstone at the next write after it expires.** Capacity (1,000 items) counts only active memories, the same measure as the store limit; over capacity returns `full`.
20. **Definition of an interaction ending.** With a camera: presence ending (PresenceTracker, about 60 seconds) or the camera stopping counts as tracking loss, and sampling more than one face counts as multiple people; turning the head or looking at the keyboard does not count. Without a camera: 30 minutes idle. OS lock and deleting the linked family member also count.
21. **Deleting a family member and clearing all.** Single deletion follows George's decision ⑨ (adults unchecked by default, minors checked). A native dialog can have only one checkbox, so clear-all lists each member's count; minors' memory is always deleted, and adults' only when “Also delete adult family members' memory” is checked, otherwise only the link is removed and the current person is paused. If the memory step fails, the family recognition view says so.
22. **Trust boundary stated plainly.** SourceTicket is a core self-check (it keeps the core from getting a command wrong or having it altered); the real security boundary is the IPC sender check (main-window main frame, local core page) plus the page only forwarding what the user typed. Saying “I am X” is enough to view and edit X's household-usable data: this is grouping by person on a shared household device, not identity verification.

## 4. Mac gate (none run; must not be claimed as passed)

These require the target Mac, the production-signed Nous App, and an isolated memory folder, operated or witnessed by the user with fictional data, without reading the existing gallery.

1. Production-signed Keychain: the system prompt on first memory use and cross-process restart readback after allowing; after actually pressing “Deny”, memory is disabled, no plaintext is created, and chat continues.
2. Real `/usr/bin/lockf` with two cores: open two cores on the same userData; the second reports that another Nous core is using memory.
3. SIGKILL: force-quit the production App during a write; after reopening, receipts and data agree.
4. Performance: with 1,000 active memories, warm retrieval p95 ≤50 ms and durable write p95 ≤300 ms; also record first unlock and the full user wait without hiding Keychain prompt time in an average.
5. Face candidate and interaction end: after look-to-talk recognizes a linked family member, typing shows “Use X's preferences this time?” and selects only after confirmation; more than one face, the person leaving the camera (presence ending), or the camera stopping pauses; merely turning the head or looking at the keyboard does not.
6. OS lock: lock and unlock the screen; the current person is paused and an ongoing reply stops.
7. UI screenshots: first-time setup, clarification card, create person, list (edit / forget / pin), memory management, and the family-deletion checkbox dialog, in both Chinese and English.
8. M02 with real Claude and real ChatGPT accounts: the same item is used once with each service; another account without consent receives nothing.
9. Time Machine exclusion result and a canary scan of `nous.log`.
10. Whether `safeStorage.isEncryptionAvailable()` (called when settings report availability) triggers a Keychain prompt; with memory off, startup, status checks, and ordinary chat should neither prompt for Keychain nor create `userData/memory`.

## 5. Unfinished work, limitations, and next gate

- Live and API key voice do not read or write memory (MEM-2, MEM-3); speech sources (push-to-talk, voice conversation mode) do not use the memory IPC or send `memory_turn`. Background tasks receive no memory (MEM-4). Automatic consolidation and Markdown export are not done.
- The parser uses fixed rules and lexicons and will miss phrasings that are not listed; when unsure it shows a card instead of guessing.
- First-version memory is ordinary household-usable preferences, not a private space; selecting a person is not identity verification. Forgetting does not delete content already sent to a model service, older APFS / Time Machine snapshots, or results the user saved elsewhere.
- Next gate: Mac gate items 1–10 above. Until they pass, README and the status document keep “MEM-1 code complete, not verified on real hardware”.
