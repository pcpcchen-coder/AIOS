# 電子腦 Canvas 每格成本優化（方案 A）驗證

日期：2026-11-06。分支 `claude/brain-canvas-perf`（基於 main `d28ce23`）。狀態：**程式、像素比對與 Linux 雲端量測完成；Raspberry Pi 4 上的改善未量測。**

## 目的

Pi 4 終端機上電子腦（`prototype/ambient-shell/src/brain.ts`，Canvas 2D，775 個粒子、1382 條連線）跑不順。本批只降低每格主執行緒的 `step()` 加 `draw()` 時間（設定畫面「每格主執行緒繪製」量的就是這一段），畫面不能有看得出的改變。效能設定（完整／平衡／省電）、每秒格數上限、減少動態、`frameStats()` 的意義都不變；腦區仍由真實事件亮起、畫光脈衝與區名。

## 先找限制因素

用 Chromium 的 CPU profiler（50 µs 取樣，不列入報告的量測）跑舊版 630 格：`drawNodes` 自身時間約佔腦部 JavaScript 取樣時間的六成，其次是 `rgba()` 字串組合。原因是每個粒子每格都組一個 `rgba(r,g,b,a.toFixed(3))` 字串，再交給 `fillStyle` 解析，一格 775 次。

## 改了什麼

| # | 做法 | 畫面影響 |
|---|---|---|
| A1 | 粒子的底色（不隨時間變）在建腦時存進 `Float64Array`；每格顏色照舊逐粒子算（RGB 取整數，和舊的 `rgba()` 一樣），透明度改用 `globalAlpha`（數字），`fillStyle` 用快取的 `rgb()` 字串 | `globalAlpha` 與字串裡三位小數的透明度捨入不同，疊到背景後最多差 2/255 |
| A2 | 粒子依顏色分組（counting sort，重複使用的陣列）後再畫，同組只設一次 `fillStyle`；粒子光暈另一輪畫 | 這一段在 `lighter`（相加）合成下畫，換順序不改結果：A1 不分組與分組的像素差異完全相同 |
| A3 | 光脈衝的線色字串在產生時算一次、染色光點第一次畫時取一次；淡出改用 `globalAlpha` | 同 A1 的捨入差異 |
| A4 | 連線依深度分四組改用重複使用的 typed array（counting sort），每格不配置陣列與閉包；組內順序不變 | 無（路徑相同） |

沒有改：腦區光暈的漸層（位置每格都變，`tests/brain-performance.test.ts` 也檢查每格兩個漸層）、區名與光環、`step()`、光脈衝的亂數用法。

## 量測方法

腳本：`prototype/ambient-shell/scripts/bench-brain.mjs`。它用 `git show` 取出優化前的 `brain.ts`（固定 commit `d28ce235f98b75097c97e8efc5870407e1740b46`，不放進產品程式），和工作目錄的 `brain.ts` 各自以 esbuild 打包，在同一個無頭 Chromium 頁面（1920×1080、裝置像素比 1、跨來源隔離，所以 `performance.now()` 解析度是 5 µs）裡執行：

- 固定情境：即時語音接通、聆聽中、正在說話、處理中、進度 0.4、語言區（語音播放）與規劃區（主題分類）亮起；`Math.random` 用固定種子，每 15 格送 `step`、`stream`、`stepDone` 光脈衝，每 90 格一次處理中波紋。舊版與新版收到完全相同的事件。
- 每格固定 `dt = 1 / maxFps`（30／20／12），在 `requestAnimationFrame` 裡呼叫一次 `step()` 加 `draw()`，量的範圍和 `frameStats()` 相同。
- 每一檔先跑 60 格暖機，再量 300 格；每次執行依序跑三檔，舊版與新版的先後每次交替。共 5 次，報告 5 次中位數的中位數與 5 次的範圍。
- 另一組「含點陣化」：每格量完後呼叫 `getImageData(0, 0, 1, 1)` 逼畫布把這一格的指令畫出來，一起計時，避免成本只是被移到之後。
- 正確性：兩版畫出的粒子、光脈衝數（31／21／12）與區名（「語言區 · 語音播放」「規劃區 · 主題分類」）相同；頁面沒有錯誤。

```
cd prototype/ambient-shell
node scripts/bench-brain.mjs --runs 5
```

環境：雲端容器 x86、4 核、開始時 load average 約 0.9；Chromium 153.0.8010.12 無頭模式，畫布由 SwiftShader（軟體 GPU）點陣化；Node v22.23.4。**這是 x86 軟體點陣化下的相對比較，不是 Pi 的數字。**

## 結果

### 每格 step＋draw（主執行緒，毫秒；5 次執行的中位數，括號內是 5 次的範圍）

| 設定 | 優化前 中位數 | 優化後 中位數 | 變化 | 優化前 p95 | 優化後 p95 |
|---|---|---|---|---|---|
| 完整 | 1.600（1.440–1.685） | 0.620（0.565–0.650） | −61.2% | 2.420（2.120–2.540） | 0.900（0.870–1.040） |
| 平衡 | 1.515（1.415–1.560） | 0.600（0.545–0.615） | −60.4% | 2.235（2.075–2.335） | 0.890（0.840–0.930） |
| 省電 | 1.425（1.365–1.490） | 0.570（0.500–0.590） | −60.0% | 2.195（2.110–2.270） | 0.860（0.710–0.900） |

兩組範圍沒有重疊。結論：主執行緒時間約減少六成。

### 含點陣化（step＋draw＋逼畫布畫出，毫秒）

| 設定 | 優化前 中位數 | 優化後 中位數 | 變化 |
|---|---|---|---|
| 完整 | 12.150（11.775–12.740） | 11.320（10.925–11.470） | −6.8% |
| 平衡 | 9.800（9.335–9.930） | 8.365（8.240–8.760） | −14.6% |
| 省電 | 6.735（6.565–6.945） | 5.930（5.525–6.105） | −12.0% |

在這個環境，點陣化（SwiftShader）比主執行緒的指令記錄貴很多，佔含點陣化時間的 79%–95%（以兩表中位數相減計算）；本批沒有讓它變慢，還少了 7–15%。Pi 上點陣化由 GPU 或另一條執行緒做，比例會不同，見「限制」。

### 各做法的效果（累加，每列 5 次執行，只量主執行緒）

| 版本 | 完整 | 平衡 | 省電 |
|---|---|---|---|
| 優化前（4 批共 20 次的中位數；範圍） | 1.610（1.520–2.265） | 1.600（1.510–2.200） | 1.585（1.400–2.175） |
| A1 粒子：底色快取＋`globalAlpha`，不分組 | 0.795（0.770–0.850） | 0.770（0.725–0.780） | 0.685（0.650–0.730） |
| ＋A2 依顏色分組 | 0.740（0.725–0.800） | 0.685（0.665–0.715） | 0.645（0.620–0.670） |
| ＋A3 光脈衝 | 0.695（0.635–0.720） | 0.665（0.640–0.745） | 0.630（0.555–0.665） |
| ＋A4 連線（＝出貨版） | 0.650（0.600–0.940） | 0.625（0.595–0.805） | 0.590（0.540–0.805） |

幾乎所有效果來自 A1（約 −50%）。A2、A3 各再少約 0.03–0.06 ms，範圍大致分開；A4 的範圍和前一列重疊，在雜訊內，不宣稱有可量的效果（保留它是因為它移除每格的陣列配置，畫面完全相同）。這些數字是另一批執行，和上面主表的數字不是同一次。中間版本是把出貨版的 `drawEdges`、`drawPulses` 換回舊版原始碼做成的暫存檔，用 `--candidate` 量，不在 repo 裡；當時光脈衝的染色光點還是在產生時取，之後才改成第一次畫時取（為了讓 `pulse()` 不碰畫布），主表是改完後的版本。

### 像素比對

同一個固定情境，第 1、30、120、300 格，兩版各自用 `getImageData` 取整張畫布比對（每檔 4 張，共 12 張）：

- 看得到的差異（把畫布疊到黑底與白底後的 RGB）：每個通道最多 **2/255**；有差異的像素最多 **0.109%**（省電第 1 格 1270／1166400）。
- 原始（未預乘）數值最多差 17/255，只出現在透明度很低的像素：`getImageData` 回傳未預乘的顏色，透明度 17 時預乘值差 1 會被放大成約 15。
- 每張的亮點像素都在 28 萬到 54 萬之間，兩版畫的區名與光脈衝數相同。
- 門檻寫在腳本裡（看得到的差異每通道 ≤ 2/255，且有差異的像素 ≤ 0.5%），超過時腳本以非 0 結束。

開發時另外確認過：(1) 粒子光暈改成另一輪畫、但字串與透明度照舊時，12 張完全相同（0 個像素差異）；(2) A1 不分組與 A2 分組的差異像素數完全相同；(3) 加上 A4 前後的差異像素數完全相同。所以差異只來自 `globalAlpha` 的捨入，不來自換順序。

## 限制

- **沒有在 Pi 上量。** 容器的 x86 CPU 比 Pi 4 的 Cortex-A72 快很多，點陣化也是軟體 GPU；只能說相對變化，不能推算 Pi 上的毫秒數。
- 主執行緒時間不含 GPU 點陣化；Pi 上若瓶頸在 GPU 或合成，每秒格數不一定變多。
- 沒有用眼睛在真的螢幕上比較；看不出差異的判斷只靠 2/255 的像素比對。
- 情境固定為一種（通話中、兩個腦區亮起）；其他狀態走同樣的程式路徑，但沒有個別量。

## George 在 Pi 上怎麼比較

1. 在 Pi 頁面開「設定」→「這台裝置的畫面效能」，選「平衡」，等 1 分鐘，記下「實測：每秒 N 格，每格主執行緒繪製 M 毫秒」。最好在即時語音通話中記一次（腦區亮起、光脈衝最多）。
2. 部署這一批之後，同一檔、同樣情境再記一次。
3. 「每格主執行緒繪製」應該明顯變小；若每秒格數沒有跟著變多，瓶頸可能在 GPU 或合成，請一併記 `top` 的 Chromium CPU 與 `vcgencmd measure_temp`。
4. 結果補記在本文件或 [Pi 畫面效能紀錄](pi-performance-2026-11-05.md)。
