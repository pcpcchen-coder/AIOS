# LGTV-1 Voice control of the living-room LG TV: connection, pairing, basic control and state

Date: 2026-11-07 (Asia/Taipei). Branch: `claude/lgtv-1`. George asked on 2026-11-07 for Nous to control the LG TV on request and play the shows he wants. This batch (LGTV-1) covers connection, pairing, power on/off, volume, mute, input switching, opening apps, playback control and state readback. **Playing a specific show (YouTube video, search, Netflix deep link) is left to LGTV-2.**

**Not run on a Mac or a real TV.** There is no TV in the cloud: the tests use `ws` to start a "fake webOS TV" (a fixture that only simulates SSAP messages) and a fake Wake-on-LAN. Real-hardware behaviour quotes LGTVG3's records on an OLED65G3PSA, not results from this batch.

## 1. Source: LGTVG3

[`pcpcchen-coder/LGTVG3`](https://github.com/pcpcchen-coder/LGTVG3) (George's other repo; read at commit `2a52bec` of 2026-11-08) is a Python prototype and research report. This batch does not call its code; it rewrites a minimal client in Nous's Node core based on that research.

| Item | LGTVG3's finding |
|---|---|
| Model | LG OLED G3 (webOS 23); the real set is an OLED65G3PSA |
| Control protocol | SSAP: LAN WebSocket `wss://<TV IP>:3001` (self-signed certificate); the first time you press "Allow" on the TV and get a client-key; older firmware uses `ws://:3000` |
| Power on | Wake-on-LAN (the TV needs "Turn on via Wi‑Fi" and "LG Connect Apps" on); sending several packets works more reliably |
| Registration | The same permission list as aiowebostv 1.0.0 (Apache-2.0) used by Home Assistant, `pairingType: PROMPT` |
| Common app IDs | YouTube `youtube.leanback.v4`, Netflix `netflix`, Prime Video `amazon`, Disney+ `com.disney.disneyplus-prod`; the TV's `listLaunchPoints` is authoritative |
| Verified on the real TV (LGTVG3) | LAN discovery, SSAP pairing and key storage, YouTube playback by name, screenshots, the TV reporting both a wired and a Wi‑Fi MAC |
| Not yet verified on the real TV (LGTVG3) | Wake-on-LAN power-on, Netflix deep links, HDMI switching |

## 2. Design

- **Integration-layer Adapter**: `lg_tv` (service segment `tv`). Both realtime voice routes (API key and ChatGPT plan) get the same `app__tv__*` tools, executed by the core; there is no separate tool interface.
- **The core connects to the TV directly**: the Nous core on the Mac connects over SSAP (new dependency `ws@8.22.0`, MIT). Each tool call opens one connection and closes it when done; no persistent connection or subscriptions. Nous opens no new ports; TV control does not go through the page and is not exposed outside the LAN.
- **Configuration**: `NOUS_LGTV_HOST` accepts only private IPv4 addresses (10/8, 172.16/12, 192.168/16); a bad value stops startup. The model cannot specify an IP, MAC, key or SSAP address; it can only choose from fixed actions.
- **Pairing key**: stored only in `<configDir>/lgtv.json` (default `~/.config/nous/lgtv.json`, mode 0600), written by `npm run tv:pair` and only read by the core. The key never goes into logs, the page or the model, and is not in the repo. If the paired IP differs from `NOUS_LGTV_HOST`, the TV counts as unpaired.
- **MAC**: when pairing, the Mac's ARP table is checked first; if it shows the network card the TV is using, only that one is stored. Otherwise both the wired and Wi‑Fi MACs the TV reports are stored, and wake packets go to both. `NOUS_LGTV_MAC` overrides this.
- **Confirmation**: power, volume and the rest are reversible, outside the external side effects listed in the product red lines, so no confirmation card is shown. If the TV is off when opening an app or switching input, it is turned on first (2026-10-31 "convenience first"). George needs to confirm both points; see section 10.
- **Just say it, like the lights** (George 2026-11-07): both realtime routes' speaking rules gain a TV rule (only when `app__tv__` tools exist): "the TV" with no room named means the living-room set and uses `app__tv__*`; "TV louder" and "mute the TV" use `app__tv__volume`/`app__tv__mute` and no longer go to the hub.
- **The hub route's "TV" is cancelled** (George 2026-11-07): when `lg_tv` is enabled (`NOUS_LGTV_HOST` set), `home_control` returns `refused` (`unsupported`, pointing to the TV tools) for "電視" (TV), "客廳電視" (living-room TV), "LG 電視" (LG TV), and hub devices in the living room whose names end in TV; no infrared key is sent. TVs in other rooms (for example 臥室電視, the bedroom TV), other appliances and `home_status` queries are unaffected. The `home_control` tool description is unchanged (locked by byte-identical tests); the speaking rule and the hub-side refusal steer to the new method.
- **Spotify**: Spotify Developer Policy III.3 prohibits voice control of Spotify, and AIOS's SP-2 is BLOCKED. Until George decides, `launch_app` refuses to open Spotify on the TV and sends nothing; the list returned when an app is not found also omits Spotify.

## 3. Supported commands

| Tool | Arguments | How (SSAP) | Readback |
|---|---|---|---|
| `app.tv.status` (read-only) | none | `getPowerState`, `getForegroundAppInfo`, `listLaunchPoints`, `audio/getVolume` (falls back to `audio/getStatus` when there is no mute field) | It is the readback |
| `app.tv.power` | `state`: on/off | On: nothing if already on; `system/turnOn` when reachable but in standby; Wake-on-LAN when unreachable (ports 9 and 7, resent while waiting), polling for 25 s. Off: `system/turnOff` without waiting for a reply (the TV drops the connection) | On: reads `Active`. Off: unreachable or reads standby |
| `app.tv.volume` | `action` set/up/down; `level` 0–100; `steps` 1–10 | `audio/setVolume`, `volumeUp`, `volumeDown` | Volume read back matches the expected value |
| `app.tv.mute` | `muted` | `audio/setMute` | Mute state read back |
| `app.tv.input` | `input` (HDMI 1, hdmi2, 2, or an input name set on the TV) | find the input with `tv/getExternalInputList`, then `tv/switchInput` | Foreground app becomes `com.webos.app.hdmiN` |
| `app.tv.launch_app` | `app` (app name) | match in `listLaunchPoints`: app ID → title → built-in alias (網飛 for Netflix, 油管 for YouTube, 迪士尼 for Disney+…) → similarity; only apps on the list are opened. `system.launcher/launch` | Foreground app becomes the target |
| `app.tv.media` | play/pause/stop/rewind/fast_forward | `media.controls/*` | The TV does not report playback state, so always `unconfirmed` |

## 4. Status mapping (honest states)

| Situation | status | Notes |
|---|---|---|
| Command sent and readback matches | `confirmed` | The only case that may be called done |
| Command sent but nothing or a mismatch read back (for example volume with a soundbar, foreground unchanged after opening an app, not online 25 s after waking, playback control) | `unconfirmed` | Ask the user to check |
| Connection dropped or no reply after the command was sent; Dispatcher time limit reached | `unknown` | Cannot say success or failure |
| An error after a write was already accepted (for example the 3rd volume step rejected, or the TV not recognising the key after waking) | `unconfirmed` | Never "not sent" or "failed" |
| Power-on not confirmed while opening an app or switching input | `unconfirmed` | Says "power-on sent, but the app has not been opened yet"; the app launch was not sent |
| TV unreachable (nothing sent); TV explicitly rejected; no such app or input; volume while in standby; no MAC to wake; wake packet could not be sent | `failed` | State the reason |
| Not paired, Spotify, bad arguments | `refused` | Nothing sent |
| TV unreachable when turning off | `failed` (`sent: false`) | It may already be off, but no power-off command was sent |
| Status query unreachable | `confirmed` (`reachable: false`) | Says "unreachable, may be in standby or off the network"; does not assume it is off |

The settings page's "App integrations" shows "Living-room LG TV": reachable is "Available: connected"; unreachable is "Unknown: unreachable (the TV may be in standby or off the network)", with the note "being unreachable is normal in standby"; unpaired shows "Not paired yet". The integration layer's health reason codes gain `unreachable` and `not_paired` for this.

## 5. Tests (fixtures, not the real TV)

New test file `tests/integration-lg-tv.test.ts` with 30 tests, plus 1 in `tests/home-bridge.test.ts`:

- **SSAP client**: waits for "Allow" on a pairing prompt and gets the key; ordinary calls stop immediately on a prompt without waiting for the user; a wrong key needs re-pairing; unreachable, TV rejection and drop after sending are three distinct errors; if the first URL is unreachable the second is tried (matching wss:3001 → ws:3000).
- **Pairing file, MAC, names**: the pairing file is mode 0600; an unreadable file counts as unpaired; it can be deleted. MAC normalisation; the magic packet is 102 bytes. App aliases and similarity matching; apps not installed are not opened. Inputs can be named HDMI 2, 2 or "Apple TV".
- **Adapter**:
  - Not paired, or a different IP: the TV is not contacted.
  - Status is correct when on, in standby and unreachable.
  - Power on: already on, Quick Start+ standby, and coming online after Wake-on-LAN (the fake TV starts only after receiving the packet) are `confirmed`; no MAC is `failed`; not online after waking is `unconfirmed`, with packets resent while waiting.
  - MAC override, and sending to both network cards.
  - Power off: the TV dropping the connection is `confirmed`; the TV ignoring it is `unconfirmed`; unreachable is `failed` (`sent: false`); already in standby sends nothing.
  - Volume set, up and down are all read back; a soundbar that cannot be read gives `unconfirmed`; nothing is sent in standby or when unreachable.
  - Mute: success, TV rejection, and drop after sending (`unknown`).
  - Input: success, no such input, and foreground unchanged.
  - Open app: Chinese alias, not installed, Spotify refused with nothing sent, and foreground unchanged.
  - Opening an app while the TV is in standby turns it on first, then opens the app.
  - Playback control is only ever `unconfirmed`.
  - Three health states.
  - Neither results nor the tool list contain the key.
- **Configuration and integration layer**: `NOUS_LGTV_HOST` rejects public IPs, domain names and invalid addresses; MAC and broadcast address formats are checked; with no IP nothing is registered and a log line is written; both routes get identical tool names and parameters; when the model adds a `host` argument the Schema refuses it and nothing runs.
- **Added after independent review**: a socket error (bad frame) during the handshake only fails the connection and does not crash the core; multiple messages in one packet and late replies are matched by id; a volume change rejected halfway is `unconfirmed`; a pairing error after waking is `unconfirmed`; a wake packet that cannot be sent is `failed`; opening an app when power-on is unconfirmed says the app has not been opened; a leading-zero address such as `010.0.0.1` is rejected (it would parse as the public 8.0.0.1).
- **Speaking rules and the hub**: the TV rule appears only when TV tools exist, and "TV volume" no longer points to `home_control`; with the flag on, the hub refuses "電視", "客廳電視" and "LG 電視" without sending infrared, while the bedroom TV works as before; with the flag off everything works as before.
- The pairing command itself has only been run in the cloud on its error paths: no IP, public IP, unreachable, `--forget`.

## 6. Independent review

An independent review by the same model (not a cross-model review) found 9 issues, all fixed:
- High: no listener for socket errors during the handshake, which could crash the core. The reviewer reproduced it; a test was added.
- Medium: errors after a write had been accepted were reported as "not sent" or "failed".
- Medium: opening an app when power-on was unconfirmed returned "sent", as though the app was opening.
- Medium: power-off when unreachable used `unconfirmed`.
- Medium-low: a wake packet that could not be sent was treated as sent.
- Low: handshake messages were not matched by id.
- Low: an IP with leading zeros could bypass the private-network check.
- Low: wake packets were still resent after an abort, and the worst-case power-on could exceed the tool time limit (limits are now 50 s for power and 60 s for opening apps and switching input).

## 7. Steps to test on the Mac at home (not yet done)

1. **TV settings**: Settings → General → Devices → TV Management (or "External Devices"): turn on "Turn on via Wi‑Fi" and "LG Connect Apps". Reserve a fixed IP for the TV in the router.
2. **Update and install**: after pulling main, run `npm ci` in `prototype/ambient-shell` (this adds `ws`).
3. **Pair**: with the TV on, run `npm run tv:pair -- --host <TV IP>` and press "Allow" with the remote when prompted. On success it prints where the key is stored and the MAC (never the key). Check that `ls -l ~/.config/nous/lgtv.json` shows `-rw-------`. If you set a custom `NOUS_CONFIG_DIR`, use the same `.env`: `npm run tv:pair -- --env <your .env>`.
4. **Configure Nous**: add `NOUS_LGTV_HOST=<TV IP>` to `.env`, add `lg_tv` to `NOUS_AIL_SERVICES` (with `NOUS_AIL=on`), then restart Nous.
5. **Check status**: the settings page's "App integrations" should show "Living-room LG TV: Available".
6. **By voice** (try each once on both realtime routes):
   - "Is the TV on? What's it showing?": the answer must match the screen and volume.
   - "Turn off the TV": the TV turns off and Nous says so. After 1 minute, 1 hour and overnight, say "turn on the TV" each time and record whether it woke and how many seconds it took (LGTVG3 has not tested Wake-on-LAN).
   - "Set the volume to 15", "louder", "mute", "unmute": must match what the TV shows. With a soundbar, check whether it says "please listen".
   - "Switch to HDMI 2", "open YouTube", "open Netflix (網飛)", "open Disney+": the TV switches; an app that is not installed must be reported as not installed.
   - "Pause", "resume": may only say "sent, please check the TV".
   - "Open Spotify": must say it is not authorised and nothing was sent.
   - Confirm the hub no longer controls the TV: when you say "turn the TV on/off", the hub log must show no infrared key; a bedroom TV (if any) is still controlled through the hub.
7. **Failure path**: unplug the TV's network cable (or turn off Wi‑Fi) and ask for its status; Nous must say it is unreachable, not that it is off.
8. **No leaks**: Nous's log shows only the integration layer's tool and status codes, with no key and no configuration beyond the IP.
9. **Report**: record each result, especially the power-on time, which MAC worked, and whether volume readback matches.

## 8. Rollback

- **Disable** (also restores hub control of the TV): remove `lg_tv` from `NOUS_AIL_SERVICES`, or delete `NOUS_LGTV_HOST`, then restart Nous; no `app.tv.*` tool is registered. `NOUS_AIL=off` turns off the whole integration layer.
- **Remove the key**: `npm run tv:pair -- --forget` (deletes `<configDir>/lgtv.json`). On the TV, the pairing can be removed from the connected devices under "Settings → General → Devices → External Devices/TV Management"; menu names vary by firmware and need checking on the real TV.
- **Code rollback**: revert this PR. The new health reason codes are used only by this Adapter.

## 9. Limits and unfinished work

- Not validated on a Mac or a real TV; section 7 has not been done.
- Playing a specific show (YouTube video ID or search, Netflix deep links, the YouTube "Who's watching?" screen) is left to LGTV-2. LGTVG3 has verified on the real TV that YouTube `contentTarget` plays directly.
- Terms for search sources (checked 2026-11-07; details in LGTV-2):
  - YouTube Data API `search.list` now has its own quota of about 100 calls a day.
  - Getting results with yt-dlp or by parsing youtube.com's search page violates the YouTube Terms of Service (no scrapers).
  - Netflix, Disney+ and Prime Video have no public deep links, only community methods or partner documents under NDA.
  - DIAL was introduced by Netflix and YouTube, but YouTube's `v=` parameter is documented only by the community.
- Reconnecting on every call adds roughly 0.5–1 s, which may affect responsiveness; only the real TV can measure it.
- With the TV's screen off (sound only), status returns `screen_off` and the power tool treats it as already on.
- No brain-region animation: on the API key route, integration tools currently only show a subtitle, like the other `app__` tools.
