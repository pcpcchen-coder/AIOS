## 3. 設計

### 3.1 wasm 建置

- 照上游 `build-wasm-simd-kws.sh` 的 cmake 選項：`SHERPA_ONNX_ENABLE_TTS=OFF`、`SHERPA_ONNX_ENABLE_WASM_KWS=ON`，其他 WASM 目標維持預設 OFF；另外明確加 `SHERPA_ONNX_ENABLE_WASM_TTS=OFF`。
- 上游 v2.0.1 的 `build-wasm-simd-kws.sh` 寫明 “emsdk 4.0.23 is known to work”（2026-10-31 從上游讀取），所以固定 4.0.23。
- 上游的 `wasm/kws/CMakeLists.txt` 以 `--preload-file` 把模型打包進 `.data`，沒有模型就 `FATAL_ERROR`，輸出是 classic script。`wake-wasm.mjs patch` 改 4 處，每處都要求原文**剛好出現一次**：
  1. 移除「assets 裡沒有 decoder 就停止」的檢查；
  2. `--preload-file` 換成 `-sMODULARIZE=1 -sEXPORT_ES6=1 -sEXPORT_NAME=createSherpaKwsModule -sENVIRONMENT=web,worker`（module worker 不能 `importScripts`）；
  3. `EXPORTED_RUNTIME_METHODS` 加 `FS`（worker 把核對過的模型寫進記憶體檔案系統）；
  4. 安裝清單移除 `.data`。
- 這樣模型不進 wasm，wasm 的雜湊與模型選擇無關；模型沿用 WK-00 釘住的壓縮檔與雜湊。
- 輸出 3 個檔案：`sherpa-onnx-wasm-kws-main.mjs`（Emscripten 的 ES module 載入程式）、`sherpa-onnx-wasm-kws-main.wasm`、`sherpa-onnx-kws.mjs`（上游 `wasm/kws/sherpa-onnx-kws.js` 原文加一行 `export { createKws };`）。另附 `LICENSE.sherpa-onnx.txt`（只在 release，不安裝；也列在清單的 `release_only`、附雜湊）。
- build job 把 `wake-runtime-manifest.json` 本身的 SHA-256 輸出成 job output；release job 先以它核對下載到的清單，再逐檔核對（含 LICENSE），而且資料夾裡不得有清單以外的檔案。
- release 不可變：同名 release 已存在時 workflow 失敗，不改任何東西，由人處理。
- release 名稱 `wake-runtime-2.0.1-<設定雜湊前 12 碼>`，設定雜湊是 `build-wake-wasm.sh` 與 `wake-wasm.mjs` 內容的 SHA-256；改任何一個就是另一個 release。

### 3.2 worker 的載入順序

1. 清單有任何阻擋理由 → 不連網，關閉網路，回報 `runtime_missing`。
2. 從同源 `/wake-runtime/` 讀 wasm、所選模型的 encoder／decoder／joiner／tokens、兩個 JS，逐一以 `crypto.subtle` 核對 SHA-256；任一不符、HTTP 錯誤或缺檔 → `runtime_load_failed`。
3. **位元組都讀完、核對過之後，在 `import()` 任何第三方 module 之前**，先 `lockGlobals()`：`fetch`、`XMLHttpRequest`、`WebSocket`、`EventSource`、`WebTransport`、`importScripts`、`Worker`、`SharedWorker`、`caches` 都定義成一律丟錯、不可寫、不可重設的函式，之後 `bytes()` 也拒絕。所以第三方 module 的頂層程式執行時已經不能用這些 API（覆蓋這些全域不影響 `import()` 本身）。
4. 再以 `import()` 載入兩個 JS（同一個同源路徑），然後 `lockImports()`，之後 `module()` 也拒絕。失敗時（`finally`）兩者都關閉。
   - 「核對後才執行」的真正保證來自**核心每次讀取都再核對雜湊**（`readVerifiedWakeRuntime`）：`import()` 會重新讀取，不是執行 worker 剛核對過的那份位元組；而 worker 的 CSP（`scriptHeaders()`：`script-src 'self'`、`connect-src 'self'`，不允許 `blob:`）不能改成執行記憶體裡的位元組。worker 端的核對是多一層檢查。
   - 最後的邊界是這個 CSP 的同源限制：即使 `LOCKED_GLOBALS` 漏了某個 API，也只能連到同源核心。
5. 以 `wasmBinary` 初始化 Emscripten 模組（glue 不自行下載），模型寫進記憶體檔案系統，關鍵詞以 `keywordsBuf` 傳入（`wakeKeywordsText`：每行「發音單元 [:提升分數] [#門檻] @ID」）。引擎拒絕關鍵詞（spotter handle 是 0）→ `runtime_load_failed`。
6. 偵測：`getResult` 的 `keyword`（即 `@ID`）對應清單 `entries` 的位置，只送出 `{ type: "detected", keyword_index }`；不在清單上的結果只重設、不回報。上游把樣本複製到 wasm heap，送進引擎後以 0 覆寫那一塊；釋放時刪掉記憶體檔案系統裡的模型。

動態 `import()` 是語法，不能以指定覆蓋；它只出現在 `runtime-net.ts` 的 `module()`，而且只接受清單檔名、關閉後拒絕。

### 3.3 清單格式與 `wake:setup -- --product`

- `status`：`pending_first_build` 時 release 檔的 `sha256` 必須是空字串、`build.release_tag` 與 `config_sha256` 必須是 null（格式檢查會擋下自行填寫的雜湊）；`built` 時三者都必須有值。
- 模型檔：兩個模型（`zh-en-3M`、`wenetspeech-3.3M`）各 4 個檔案（int8 encoder、decoder、int8 joiner、tokens.txt），安裝名稱是 `<模型 id>.<壓縮檔內檔名>`，雜湊與 `spike/wake/models.json` 相同（測試核對）。用哪一個模型由 `keywords.model` 決定，跟關鍵詞一起等 George 的數字。
- `keywords`：`pending_owner_numbers` 時 `model`、`keywords_score`、`keywords_threshold` 是 null、`entries` 是空陣列；`configured` 時發音單元不得含 `:`、`#`、`@` 或空白以外的分隔。
- `npm run wake:setup -- --product`：先跑與核心相同的 `validateWakeRuntimeManifest`，任何格式錯誤就停下；清單不是 `built` 或任何檔案缺雜湊時，**下載前**就失敗；每個檔名（清單檔名、壓縮檔內的檔名、壓縮檔名）在 `join` 之前都要符合 `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`。之後下載 release 檔（`https://github.com/pcpcchen-coder/AIOS/releases/download/<tag>/<檔名>`）與模型壓縮檔，逐一核對，全部通過才安裝。`--from <資料夾>` 可改用已下載的檔案。
- 安裝是原子的：每個目的地（`wake-runtime/` 與 macOS 的 `~/Library/Application Support/Nous/wake-runtime/`）先寫到同一磁碟區的 `<目的地>.tmp-XXXX`，再把原本的目的地改名備份、把暫存 rename 成目的地；任何一步失敗就刪掉暫存並還原備份，第二個目的地失敗時第一個也還原。目的地整個換成這次核對過的檔案。
- 核心：`runtime()` 不是 `ok` 時，`/wake-runtime/` 對所有檔案都回 404，包括雜湊早已釘住的模型檔。

## 4. 授權查核

- v2.0.1 標籤沒有 `cmake/espeak-ng-for-piper.cmake`（上游 raw 檔回 404）；`SHERPA_ONNX_ENABLE_TTS=OFF` 時 `sherpa-onnx/csrc/CMakeLists.txt` 不編譯任何 `offline-tts-*` 檔案。上游原始碼提到 espeak-ng 的地方只有 TTS 檔案、Python 綁定與 `c-api.h` 註解。
- `license-check` 自動檢查（workflow 的獨立步驟，建置腳本最後也跑一次）：
  - `CMakeCache.txt` 必須是 `SHERPA_ONNX_ENABLE_TTS:BOOL=OFF`、`SHERPA_ONNX_ENABLE_WASM_KWS:BOOL=ON`，`SHERPA_ONNX_ENABLE_WASM_TTS` 不得是 ON；
  - 建置樹與輸出的檔名、以及 `.wasm`、`.js`、`.mjs`、`.a`、`.o`、`.data`、`.so`、`.dylib` 的內容，不得出現 `espeak`、`libespeak` 或單獨的 `piper`（不分大小寫，前面不能是英文字母，所以 `OfflineSpeaker` 不會誤判）；
  - 輸出必須剛好是 3 個檔案加 LICENSE（沒有 `.data`）。
- 這是字串與檔名檢查：能抓到靜態連結的 espeak-ng 符號（WK-00 在 1.13.8 原生套件找到的 `espeak_Initialize` 等）與 piper 的 C++ 名稱，但 release 建置的 wasm 會去掉多數函式名稱，所以真正的保證來自 TTS 關閉與建置樹檢查，不只來自 wasm 的字串。
- 其餘第三方授權同 [ADR-0003 §3](../adr/ADR-0003-local-wake-and-voice-recognition.md#3-授權查核表2026-10-29)；onnxruntime 是上游 cmake 以雜湊釘住的 wasm 靜態庫 1.28.2。

## 6. 第一次 CI 建置之後：把雜湊寫進清單

1. 這個 PR 的 `Wake KWS wasm build` 會在 pull_request 上建置。打開該次執行的 job summary，看到 `wake-runtime-manifest.json`（3 個檔案的 SHA-256、位元組數、固定版本與 release 名稱）；artifact 同名。若授權檢查失敗，整個 job 失敗，不產生 artifact。
2. PR 合併到 main 後，在 Actions 手動執行 `Wake KWS wasm build`（`workflow_dispatch`，分支 main），建立 GitHub Release `wake-runtime-2.0.1-<12 碼>`（同名 release 已存在時 workflow 失敗，要由人處理）。確認 release 的 `wake-runtime-manifest.json` 與 PR 上的 job summary 相同；不同時要先查原因（建置不可重現），不要直接採用。
3. 另開一個 PR 修改 `shared/wake-runtime.json`：`status` 改 `built`，`build.release_tag`、`build.config_sha256` 填 release 的值，3 個 release 檔的 `sha256` 從 `wake-runtime-manifest.json` 逐一抄入。`validateWakeRuntimeManifest` 會擋下少填或格式錯誤。
4. 這時 `wakeRuntimeBlockers` 只剩 `keywords_pending`，引擎仍不可用，直到 §7 完成。

## 9. Mac 步驟（§6 與 §7 都完成之後）

1. `git pull`，在 `prototype/ambient-shell` 執行 `npm ci`，再執行 `npm run wake:setup -- --product`。若 repo 是私人的，下載 release 檔可能要登入：先 `gh release download <tag> -R pcpcchen-coder/AIOS -D ~/Downloads/nous-wake`，把兩個模型 `.tar.bz2`（網址在 `spike/wake/models.json`）也放進同一個資料夾，再加 `--from ~/Downloads/nous-wake`。
2. `.env` 加 `NOUS_WAKE=on`，重新啟動 App；核心啟動記錄應該不再出現「喚醒引擎：missing」。
3. 選單列打開「常駐喚醒聆聽」：狀態應先是「準備中」，worklet 開始處理後才是「本機聆聽中」；若是「喚醒引擎載入失敗，已停止收音」，記下來（這是本批無法在雲端驗證的部分）。
4. 說「哈囉努斯」：應出現「聽到了」字幕與提示音（WK-02 之前不會開通話）。依 [WK-01a 驗證 §6](wk-01a-2026-10-31.md#6-mac-gatewk-01a-可先做的部分) 的表格補完「等 WK-01b」那一欄（W2、W3、W4、W7、W9、W10、W11、背景 worklet、提示音）。
5. 用「活動監視器」記錄 Nous 的 CPU 與記憶體（上游設定 `INITIAL_MEMORY=512MB`，見 §10）。
6. 網路關閉（在真的 worker 裡）：若這個 App 建置能開 DevTools，在 DevTools 選喚醒 worker 的執行環境，載入完成後執行 `fetch("/")`，必須丟出 “wake worker network is locked”；`new Worker("x.js")`、`caches` 也一樣。若不能開 DevTools，記下「未驗」。

## 10. 風險與限制

- **workflow 從未執行**：emcc 版本字串、`export default createSherpaKwsModule` 的輸出格式、`-sENVIRONMENT=web,worker` 搭配 `EXPORT_ES6` 的行為、`cmake --install` 與授權檢查在真的建置樹上，都要第一次 CI 才知道；任何一項不符時 workflow 會失敗，而不是發布錯的產物。
- **載入只用假模組測過**：真的 Emscripten 模組在 Electron 44.9.3 的 module worker 裡能否以 `wasmBinary` 初始化、`FS` 是否匯出、int8 模型在瀏覽器 wasm 的表現，都要 Mac 驗證。
- 上游的 `INITIAL_MEMORY=512MB` 沒有改；worker 會預留這麼多記憶體，Mac 上要量。
- actions 照 repo 其他 workflow 的慣例以 `@v4` 標籤固定，不是 commit SHA；改成 SHA 屬於整個 repo 的另一個決定。emsdk 與 sherpa-onnx 以完整 commit SHA 固定。
- release 不可變：同名 release 已存在時 workflow 失敗，需要人決定（比對既有 release 的清單；只有沒有任何清單引用它時才可刪除，或改建置設定）。
- emsdk 工具鏈（`emsdk install 4.0.23` 下載的 LLVM／Emscripten 二進位）只依賴 TLS 與固定的 emsdk commit（它決定下載哪一個建置），沒有另外的壓縮檔雜湊核對。
- 「核對後才執行」對兩個 JS 而言依賴核心每次讀取都再核對（§3.2）；worker 端的核對是多一層，不是唯一保證。
- 授權檢查是字串與檔名檢查（§4）。
- 如果 repo 是私人的，release 資產的公開下載網址可能回 404；`--from` 是替代做法。
