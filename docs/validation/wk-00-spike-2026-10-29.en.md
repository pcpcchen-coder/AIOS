# WK-00 wake-word spike validation

Date: 2026-10-29, Asia/Taipei. Branch: `claude/wk-00` (based on `claude/wake-speaker-plan`, PR #44, not yet merged). Scope: WK-00 in [plan 17 §13.4](../17_Wake_Word_and_Speaker_Recognition_Plan_2026-10.en.md#134-交付批次與估時). Draft decisions are in [ADR-0003](../adr/ADR-0003-local-wake-and-voice-recognition.en.md).

**This is not a product feature and not hardware acceptance.** This batch delivers only a spike that is not wired into the product (`prototype/ambient-shell/spike/wake/`) and measurements in a cloud container. The numbers come from "a cloud container (Linux x86-64, 4 cores, Node 22.22.0) with TTS-synthesized speech or public corpora", **not a Mac, not a living room, and not family voices**. None of W1–W12 in plan 17 §13.2 passed, and nothing ran on the Mac.

## 1. Summary of findings

| Question | Finding |

| Synthetic positives | **0/300 hits; cause undetermined**. 300 TTS-synthesized clips of 「哈囉努斯」, 「嘿努斯」 and "Hey Nous" scored 0 hits under all 12 settings (§3.3). | Browser wasm | The npm package has no browser build (it uses NODERAWFS for file access and throws immediately in a browser). It must be self-built with the upstream `build-wasm-simd-kws.sh`. The cloud self-build was blocked by environment permissions and not completed. The spike page can load a self-built output but **has never run in a browser** (§4) |

## 3. Cloud measurements

<a id="31-方法與計算方式"></a>
### 3.1 Method and calculations

- Audio is fed to the engine in 100 ms chunks (similar to a live microphone), and the stream is reset after each detection (as in the upstream examples). One thread, `maxActivePaths` 4, `numTrailingBlanks` 1.
- **Single-core CPU percent** = CPU time (user + system) during the negative segment ÷ audio seconds × 100, that is, roughly the percentage of one core used at real time. **RTF** = wall-clock processing time ÷ audio seconds. Both cover only the negative segment (excluding model loading and TTS).
- **p95 time per 100 ms chunk**: nearest rank (sort, then take item ⌈0.95·n⌉).
- **Memory increase** = RSS after loading the engine − RSS before. The process peak RSS includes the synthetic positives sent by the parent process and does not represent the engine, so it is not used for conclusions.
- **False alarms per hour** = false alarms ÷ (negative seconds ÷ 3600). For 0 events, the rule of three gives a 95% upper bound: 3 ÷ hours.
- **Positive hit**: a detection with the same keyword between [word start, word end + 1.5 s]; repeated detections of the same positive count as false alarms. The calculations are in `spike/wake/stats.ts` with unit tests.
- Environment: cloud container, Linux x86-64, 4 cores, Node 22.22.0. The sweep ran 4 child processes in parallel (each loads only one engine). Parallel runs and other programs interfere with each other, so **load times (0.6–5.4 s) were unstable and are not used for conclusions**.

Positives (300 clips, **all synthesized speech, not human**):

- vits-icefall-zh-aishell3 (8 kHz; 30 speakers spread evenly over 174) and vits-melo-tts-zh_en (44.1 kHz; one speaker at speeds 0.8/0.9/1.0/1.1/1.2), converted to 16 kHz.
- Text: 「哈囉努斯」 and 「嘿努斯」. The English alias was synthesized as the homophone "Hey noose" (the TTS lexicon has no Nous); only melo can say it, giving 5 clips.
- Four contexts: spoken alone, with white noise (SNR 10 dB), with synthetic music (SNR 10 dB), and followed by a command (for example 「哈囉努斯，今天天氣怎麼樣」).
- 192 hard negatives: sentences sharing or resembling some syllables, for example 「哈囉，大家好，歡迎收看今天的新聞」, 「我們一起努力吧」, 「俄羅斯總統今天發表談話」, "Here is the news at nine", and "Hey Lucy, how are you".

Negatives (public corpora downloaded only to a scratchpad outside the repository; not committed):

Interpretation:

- All 12 settings had 0 false alarms over 6.501 hours of negatives (Hey Nous only in the 6 zh-en settings). **This coincides with 0 hits and must not be read as a low false-alarm rate**: under settings where even synthetic positives do not fire, 0 negatives only shows that the detector rarely fires. The 95% upper bound for 0 events = 3 ÷ 6.501 ≈ 0.46 per hour. The W6 target is ≤ 1 per 8 hours (0.125 per hour), so **this data cannot show whether the target is met**; at least 8 hours with the living-room television are required.
- Every positive scored 0 hits, so the sweep **found no usable operating point**. The pipeline was checked separately: all upstream real-speech test keywords were detected (§3.2); syntax such as `:2 #0.1` works on real speech; `:3` makes some real-speech keywords go missing.
- **The cause is undetermined.** It may be the synthetic speech (TTS prosody and bandwidth differ greatly from the model's training data) or the candidates' pronunciation units. Reproducing the reviewer's probe (same TTS, node@2.0.1, `:2 #0.05`): `t iān q ì` in the sentence 「今天天氣怎麼樣」 and the sub-word 「努斯」 `n ǔ s ī` when followed by a sentence do hit; 「哈囉」 `h ā l uō`, its variants `h ā l óu`/`h ā l ōu`, and the full candidates never hit; with `n ǐ h ǎo` in the list, 「哈囉」 and 「努斯」 alone are often recognized as 「你好」 (that low-threshold setting also fires too easily). The alternative-pronunciation sweep in §3.5 shows the same pattern. This batch **cannot tell** whether the synthetic speech is at fault or the pronunciation units for 「哈囉」 do not match the model (it is commonly said hā-lóu in Taiwan), so family testing must also run the alternative pronunciation and watch the sub-word (§7 step 3).

People usually speak more slowly than TTS, and the 2-second buffer still has headroom. The "shrink only, never grow" rule in plan 17 §5.2 waits for human lengths.

<a id="4-瀏覽器-wasm-可行性"></a>
## 4. Browser wasm feasibility

- The npm `sherpa-onnx` package (1.13.8 and 2.0.1) ships only `sherpa-onnx-wasm-nodejs.{js,wasm}`, built with `-sNODERAWFS`: outside Node it throws "NODERAWFS is currently only supported on Node.js environment." at startup. It cannot be used directly in a browser or AudioWorklet.
- Upstream provides `build-wasm-simd-kws.sh` (emsdk 4.0.23 recommended), which produces `sherpa-onnx-wasm-kws-main.{js,wasm,data}`. The model is packed into `.data` at build time with fixed file names such as `encoder-epoch-12-avg-2-chunk-16-left-64.onnx`. Upstream publishes no KWS wasm release asset (HF Space workflows exist only for ASR, TTS, VAD, and others). The script turns TTS off, so a self-built output contains no espeak-ng.
- In this batch, installing emsdk in the cloud was blocked by environment permissions, so **nothing was self-built and KWS never ran in a browser**. The spike page (`npm run wake:page`) loads a self-built output from `spike/wake/public/kws-wasm/`; when it is missing the page honestly reports "capture pipeline only, no detection". The page passed `vite build` and type checking but **was never opened in any browser** (the cloud has no Chromium).
- Fallback assessment:
  - Self-built wasm (recommended): one build step. The model (int8 encoder about 4.7 MB) plus wasm size was not measured, and the binary hash needs tracking. The npm wasm numbers in Node (about 5–6% of one core) are an upper reference; the browser SIMD build is usually faster but must be measured.
  - onnxruntime-web (already pinned at 1.30.0 in the project) plus hand-written fbank and transducer keyword search: no new dependency, but it means porting kaldi-native-fbank features and the upstream keyword decoding (context graph, thresholds, trailing blanks), estimated at 3–5 person-days, with results to be checked one by one against upstream. Not recommended for now unless a self-built wasm proves infeasible in Electron.
  - Node addon in the Electron main process (plan 17 §10.3 option B): proven to work and lowest in CPU, but it creates a second microphone owner. Re-evaluate only if option A misses the bar on the Mac.

<a id="7-給-george-的-mac-實測步驟"></a>
## 7. Mac test steps for George

Prerequisite: on the Mac mini in `prototype/ambient-shell`, after `npm ci`. Everything stays local and audio is never written to files. Reports go to `$TMPDIR/aios-wake-spike/` (outside the repository) by default. Use only codes (A, B, C) for family members in reports; `--person` accepts only 1–4 letters or digits and rejects names.

1. Install

```bash
npm ci
npm run wake:setup
brew install sox
```

   On first run macOS asks for the Terminal's microphone permission; allow it.

2. Check the microphone and CPU (about 1 minute; say 「哈囉努斯」 a few times)

```bash
rec -q --buffer 3200 -t raw -r 16000 -e signed -b 16 -c 1 - | npm run wake:spike -- listen --model zh-en-3M --keywords "哈囉努斯,嘿努斯,Hey Nous"
```

   Each detection prints one JSON line (time, keyword, `score: null`, threshold, estimated length, CPU). Press Ctrl+C to stop.

3. Family positives (30 per person; one round quiet and one with the TV on; one round per model)

```bash
rec -q --buffer 3200 -t raw -r 16000 -e signed -b 16 -c 1 - | npm run wake:spike -- listen --mode family --trials 30 --person A --model zh-en-3M --keywords "哈囉努斯"
rec -q --buffer 3200 -t raw -r 16000 -e signed -b 16 -c 1 - | npm run wake:spike -- listen --mode family --trials 30 --person A --model wenetspeech-3.3M --keywords "哈囉努斯"
```

   When the screen shows "Trial n/30", say 「哈囉努斯」 once, naturally, from the usual seat; a detection within 6 seconds counts as success. The report gives the success rate, the delay from end of speech to detection (energy-endpoint estimate), and the delay from the last token to detection. 

   **Start with a 5-trial pilot** (`--trials 5`). In the cloud, synthetic speech scored 0 hits on the full candidates for an undetermined reason (§3.3, §3.5). So that nobody finishes 30 trials only to find all zeros, run two more rounds per family member, still saying 「哈囉努斯」:

```bash
rec -q --buffer 3200 -t raw -r 16000 -e signed -b 16 -c 1 - | npm run wake:spike -- listen --mode family --trials 30 --person A --model zh-en-3M --keywords "哈囉努斯(hā-lóu)"
rec -q --buffer 3200 -t raw -r 16000 -e signed -b 16 -c 1 - | npm run wake:spike -- listen --mode family --trials 30 --person A --model zh-en-3M --keywords "努斯"
```

   The first round uses the common Taiwanese hā-lóu pronunciation; the second only checks whether the sub-word 「努斯」 fires (「努斯」 is diagnostic only, not a wake-word candidate). If 「努斯」 hits often but both forms of 「哈囉努斯」 rarely do, the problem is the pronunciation units for 「哈囉」; if all three are rare, the problem may be capture or the model. If the success rate is clearly poor, you can also run another round with `--keywords "哈囉努斯#0.15"` or `"哈囉努斯:1.5"` and note the setting.

   Delay bias: the CLI now estimates each sample's time by counting back from the sample index and the arrival time of the latest block, instead of using the whole block's arrival time; `--buffer 3200` makes sox send a block every 100 ms. Fixed buffering in sox and the operating system is not included, so delays may still be underestimated by up to about one block (about 100 ms).

4. TV negatives (at least 8 hours; counts only, nothing recorded)

```bash
caffeinate -i sh -c 'rec -q --buffer 3200 -t raw -r 16000 -e signed -b 16 -c 1 - | npm run wake:spike -- listen --mode tv --hours 8 --program "新聞台" --model zh-en-3M --keywords "哈囉努斯,嘿努斯,Hey Nous"'
```

   `caffeinate -i` keeps the Mac from idle sleep for the 8 hours (the display may turn off); sleep would interrupt capture. When changing channels, type the new program name in the same terminal and press Enter. Each false alarm records only the time, keyword, and program name at that moment; **it cannot be replayed later**, so if false alarms are frequent, jot down on paper roughly what was being said. Run the other model on another day.

5. Running together with the camera pipeline (groundwork for W11)

   - Open the Nous App with the camera on and leave the electronic brain idle for 10 minutes; record CPU with Activity Monitor or `top -pid <Nous PID> -stats pid,cpu -l 0`.
   - Meanwhile run the step 2 `listen` in a terminal and record CPU for another 10 minutes; the CLI also prints its own CPU every minute.
   - During this time, try the open-palm stop a few times and confirm it still responds.
   - The product currently exposes no per-frame timing for the 80 ms sensing loop. The W11 requirement "p95 no more than 10% worse" can only be judged precisely after WK-01 adds that measurement; this step is a first observation.

6. Self-built browser wasm (optional; evaluates plan 17 §10.3 option A)

## 8. Not done and concerns

- There are no human positives at all. Synthetic positives scored 0/300 hits for an undetermined reason (synthetic speech or the pronunciation units for 「哈囉」), so neither model nor any of the 12 settings has recall evidence. W5 needs family testing, run together with the alternative pronunciation and the sub-word (§7 step 3).
- Whether plan 17 §5.6's "filter with VAD first and skip KWS decoding without speech" saves CPU was not compared in this batch.
- False alarms were measured as 0 only on public read-speech corpora and synthetic noise (upper bound about 0.46 per hour), not television. W6 needs at least 8 hours in the living room.
- The browser wasm was not self-built and the spike page never ran in a browser; AudioWorklet behavior and Electron behavior with a hidden window are unverified.
- CPU and memory were not measured on the Mac, nor together with the camera pipeline; the product also lacks a measurement point for the 80 ms loop.
- sherpa-onnx KWS outputs no score. When a score distribution is needed (for example to calibrate thresholds), the only options are threshold sweeps or modifying upstream.
- Pinyin is written with standard tones (`h ā l uō n ǔ s ī`). Family members in Taiwan may use different tones. If the hit rate is low, try other tones or pronunciations (for example 「諾斯」) with `--keywords-file`, keeping in mind that each extra pronunciation adds false-alarm opportunities.
- 2.0.x is a new major line released on 2026-10-23. Upgrades need their own PR and a rerun of this batch's measurements.
