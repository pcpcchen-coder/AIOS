# SP-00 speaker model spike and SP-01 voice enrollment validation

Date: 2026-11-01, Asia/Taipei. Branch: `claude/sp-00` (based on main `32efe10`). Scope: SP-00 and the enrollment part of SP-01 in [17 §13.4](../17_Wake_Word_and_Speaker_Recognition_Plan_2026-10.en.md#134-交付批次與估時). Rules: [ADR-0003 draft](../adr/ADR-0003-local-wake-and-voice-recognition.en.md). Face enrollment: [ID-01 validation](family-id-01-2026-10-25.en.md).

**This batch does enrollment only, not recognition.** Family members can record their voice in the Family recognition screen, store it as encrypted voice features, and delete it. Calls do **not** yet recognise anyone by voice, and nobody is named because of their voice (SP-02, SP-03). The consistency and duplicate thresholds used during enrollment are starting points and **uncalibrated**. Score distributions for real family members have not been measured.

## 2. SP-00: model choice

Material: 6 macOS TTS voices (Chinese Meijia, Tingting; English Samantha, Daniel, Karen, Fred), each saying Hey Nous plus 3 sentences. **Synthetic speech, not real people.** The numbers only pick a model; they do not describe recognition rates for the family.

| Model | Sentence vs sentence: same voice, min | Sentence vs sentence: different voices, max | Decision |
|---|---|---|---|
| CAM++ zh-cn common (sha256 `f682b514…21fd11`) | 0.766 | 0.812 | Overlap, rejected |
| CAM++ zh_en advanced (native sherpa) | 0.776 | 0.698 | Separated, **chosen** |
| CAM++ zh_en advanced (browser semantics, §3.2) | 0.788 | 0.673 | Separated further |

- Hey Nous vs sentences: same voice min 0.45, different voices max 0.58, which **overlap**. Wake segments must therefore be compared with the enrolled wake-word templates ([17 §4.4](../17_Wake_Word_and_Speaker_Recognition_Plan_2026-10.en.md), text-dependent matching), never with the read sentences. That is why enrollment stores `keyword` and `utterance` separately.
- Speed: sherpa-onnx Node takes about 2–7 ms per second of audio. `onnxruntime-web` (wasm inside Node, single thread): fbank 2–6 ms plus inference 25–78 ms for 1–3.7 s segments.

## 3. SP-00: browser path

### 3.1 fbank

The sherpa-onnx browser wasm has no API that outputs speaker features on its own, so we took the fallback in [17 §7](../17_Wake_Word_and_Speaker_Recognition_Plan_2026-10.en.md): our own Kaldi-style 80-bin fbank (`src/speaker/fbank.ts`). Settings follow the model metadata: 25 ms window, 10 ms shift, `snip_edges` false, povey window, preemphasis 0.97, DC removal, 512-point FFT, mel 20–7600 Hz, log floor FLT_EPSILON, then subtracting the whole-segment mean (`global-mean`). Frame by frame against `kaldi-native-fbank`, the maximum difference is 4e-4 (`tests/speaker-fbank.test.ts`, fixture `tests/fixtures/speaker-fbank-knf.json`).

### 3.2 onnxruntime-web differs from native

With identical fbank input, `onnxruntime-web` 1.30 produces features different from native onnxruntime 1.19 (used by sherpa-onnx): cosine 0.83–0.99. The cause is the AveragePool in CAM++'s segment pooling (kernel 100, `ceil_mode` 1, `count_include_pad` 1). When a window runs past the end, native ORT divides by the full kernel while `onnxruntime-web` divides by the number of valid elements (the PyTorch behaviour). Changing the model to `count_include_pad` 0 makes native results identical to web (cosine 1.000000), which confirms the cause.

The product does not modify the model and keeps the hash in the manifest. Rule: **enrollment and recognition are both computed in the App's worker**, so they are consistent with each other. Never compare against features from native sherpa-onnx or any other tool. `model_version.preproc` is recorded as `kaldi-fbank80-globalmean-v1`; if the model or front end changes, old voices are marked "needs re-recording".

### 4.1 Recording flow

1. Starting creates the worker and loads the model, then gets the microphone: if wake listening is on, it leases from `WakeController.lease()` (KWS pauses and resumes after return); otherwise it opens its own with the same constraints as realtime voice (AEC / NS / AGC on).
2. Each prompt plays a 0.15 s, 880 Hz chime first, then starts listening. The 5 wake words are Hey Nous, Hello Nous, Hey Nous, Hello Nous, Hey Nous (2.5 s each, at least 0.4 s of voice). The 3 sentences have 6 s each and need at least 1.2–1.5 s of voice.
3. The worker keeps the voiced part by volume (20 ms frames, threshold max(0.006, 3× the quiet part), 100 ms padding on each side). Too quiet returns “didn't hear anything”; too short returns “too short”. Each prompt allows up to 3 tries.
4. Once all 8 segments have features they go to the core. The core checks consistency within each group (wake words: ≥0.45 to the mean direction and ≥0.3 for every pair; sentences: ≥0.5 and ≥0.4). A score ≥0.8 against another member's voice counts as a duplicate and is not overwritten. These numbers are starting points, uncalibrated.

### 4.2 Privacy boundaries

- Microphone samples go from the AudioWorklet straight into the worker over a MessagePort; the page's main thread never touches audio. Only the 192-d feature, voiced milliseconds and level numbers leave the worker.
- Recordings and intermediate tensors are overwritten with zeros after use. No files, no network, no local storage. The model and wasm are read only from same-origin `/speaker-runtime/`.
- Only encrypted voice features are stored, never recordings. Voice features travel only over Electron IPC to the core, never over local HTTP.
- Static checks (`tests/speaker-enroll.test.ts`, `tests/audio-privacy.test.ts`): `src/speaker/` has exactly these 5 files; no `fetch`, local storage, WebSocket, IPC or console; the worker only posts `ready` / `level` / `segment` / `error`, and `segment` carries no samples; only `family-view.ts` and `main.ts` import from `src/speaker/`.

## 6. Bug found and fixed on the Mac

On the first Mac try, every segment returned “didn't hear anything”. Cause: at a 16 kHz AudioContext no resampling is needed, so the chunk the worker receives is the same chunk it measures and stores, but the code overwrote it with zeros before using it. At 48 kHz resampling first creates a new array, so that path was unaffected. The earlier tests only exercised the pure volume-gate function and never went through the worker. Fix: overwrite the incoming chunk immediately only when it was resampled; otherwise overwrite only chunks that are not kept. Added `tests/speaker-worker.test.ts`; with the old code the 16 kHz case fails, and it passes with the fix.

## 9. Risks and limitations

- Training-data licensing for the speaker model is accepted and recorded per 17 §14 ②. This batch uses zh_en advanced instead; its training data is likewise unpublished.
- The consistency and duplicate thresholds are starting points set from TTS numbers. Real voices may differ: a normal enrollment may be rejected, or two family members with similar voices may both enroll.
- If the microphone used at enrollment differs from the one used later for recognition, scores may drop (17 §13).
- The chime plays through the speakers; echo cancellation usually removes it, but whether it reaches the recording has not been measured.
