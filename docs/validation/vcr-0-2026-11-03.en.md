# VCR-0 + VCR-1 (Fake Output) validation: cross-brand command lookup, per-speaker TTS settings and fake output

Date: 2026-11-03 (Asia/Taipei). Branch: `claude/vcr-0-catalog`, created from `docs/voice-command-relay-multibrand-2026-11` (Draft PR #88: main `c88ab77` plus George's VCR design documents). Specifications: [19 design](../19_Voice_Command_Relay_Design_2026-11.en.md), [implementation plan](../development/voice-command-relay-implementation-plan.en.md) §1 and §2, [test plan](../experiments/VOICE_COMMAND_RELAY_TEST_PLAN.en.md).

**This batch plays no real audio.** The only output is `FakeRelayOutput` (mock): no speaker makes a sound, macOS `say` is never called and no Pi is involved. Every Google Home Mini command template is a "candidate, awaiting real tests". They are **not an official compatibility guarantee**, and there is no recognition-rate data. All tests below ran with fixtures in a Linux cloud container.

## 1. Design mapping

| Specification requirement | Implementation (`prototype/ambient-shell/`) | Status |

One speaker can hold several candidates with one selected | `VoiceProfile`, `Target.voiceProfileId` + `candidateVoiceProfileIds`, `voiceDefaults` | Done (fixture tests) |
| Overrides, candidate versions and deterministic resolution | `server/integrations/voice-relay/resolver.ts` (`resolveRelay`) | Done (fixture tests) |
| `candidateTemplateId`/`candidateVoiceId` only in a diagnostic mode the user explicitly opens | `VoiceRelayAdapter.diagnose()` (core code only, never plays); the model tool's schema has neither field | Done; the diagnostic screen belongs to VCR-2 |
| A/B recognition-rate data model and formulas | `RelayTrial`, `summarizeTrials` (`shared/voice-relay.ts`), `parseTrials` (`server/integrations/voice-relay/trials.ts`) | Done; **no measured data, everything is NOT TESTED** |

This batch reuses AIL. The Registry, Dispatcher and HomeBridge are unchanged, and no new tool interface was added. The factories in `KNOWN_ADAPTERS` may now return `null`, which means "do not register this time" and writes a log line.

## 2. Configuration and enabling

| Setting | Value | Behaviour |
|---|---|---|
| `NOUS_VCR` | `off` (default) | No `voice_relay`. Even if `NOUS_AIL_SERVICES` lists it, it is skipped with one log line; the tool list, instructions and HTTP routes are the same as before |
| `NOUS_VCR` | `fake` | Requires `NOUS_AIL=on` and `voice_relay` in `NOUS_AIL_SERVICES`. The Adapter is marked `mock` and its tool descriptions start with "(Mock)" |
| `NOUS_VCR` | any other value (including `on`) | Startup error: real playback (VCR-2/3) is not implemented yet |
| `<NOUS_CONFIG_DIR>/voice-relay/config.json` | optional | The user's own targets, voiceProfiles, voiceDefaults and extra commandPacks. If the file does not exist, the two fixture targets are used. If the file is invalid, `voice_relay` is not enabled and a log line is written (fail closed; Nous startup and voice conversation are not blocked) |

In `fake` mode, the fixture targets (`fixture_google_mini_zh`, `fixture_google_mini_en`) mark the selected non-Spotify templates as approved in `reviewedTemplates`, with the note "fixture only — not a real test result". This exists only so the fake output can reach `unconfirmed`. The user's own targets start with no approved templates; the user adds approvals by hand after real tests.

## 3. Resolution priority

Template lookup goes from specific to general. Each level considers only entries with `selected: true`, and moves to the next level only when nothing is found:

| Order | Level (`level`) | Matches when |
|---|---|---|
| 0 | `diagnostic` | Only when `diagnose()` names a `candidateTemplateId` that belongs to the same intent in a pack compatible with the target |
| 1 | `device_override` | `target.templateOverrides[intentId]`; its pack must be compatible with the target |
| 2 | `model_locale` | Pack with `scope: model` and identical vendor, assistant, model and locale |
| 3 | `assistant_locale` | Pack with `scope: assistant` and identical vendor, assistant and locale |
| 4 | `vendor_locale` | Pack with `scope: vendor` and identical vendor and locale |
| 5 | `generic` | Pack with `scope: generic`, identical locale, and `compatibleAssistants` explicitly listing the target's assistant |

- Two or more selected entries at the same level → `ambiguous_template`.
- A matching entry with `supported: false` → `unsupported_intent`; the resolver does **not** continue to less specific levels.
- Locale matching is exact only; the resolver never switches to another language.
- Then, in order: policy → review status → voice (`diagnostic.candidateVoiceId` → `target.voiceProfileId` → `voiceDefaults`, model first, then assistant) → output (always the target's own speaker; a voice that names a different output is refused) → wake phrase (`target.wakePhraseId`, which must come from a pack with the same vendor, assistant and locale → the selected wake phrase of a same-model pack → a same-assistant pack; never from a generic pack, another brand or another locale) → slot text substitution → a final check, on normalised text (NFKC, lowercase, whitespace and format characters removed), that the command contains no wake phrase.
- No randomness and no clock: the same input always gives the same output (tests compare deep equality and identical JSON strings).

## 4. Refusal reasons

| `vcr_reason` | Meaning | AIL `reason` |
|---|---|---|
| `unknown_target` | No target with this ID | `invalid_arguments` |
| `target_disabled` | Target has `enabled: false` | `unavailable` |
| `unsupported_intent` | Unknown intent, no template at any level, template `supported: false`, incompatible override, or no wake phrase | `invalid_arguments` |
| `invalid_slots` | Missing, extra, wrongly typed or out-of-range slot, light not in the target's device list, or text after substitution that is invalid or contains any wake phrase | `invalid_arguments` |
| `ambiguous_template` | Several selected templates at the same level | `unavailable` |
| `not_reviewed` | Template is a candidate (only an explicit diagnostic `candidateTemplateId` may try it) or rejected (a catalog rejection cannot be overridden by the target's approval; blocked in diagnostic mode too) | `unavailable` |
| `policy_blocked` | Non-low-risk intent, Spotify downstream, any music-category intent when the target's music service is Spotify or unknown (whatever the template's label), or normalised command text containing Spotify/聲破天 (full-width, zero-width and spaced forms are caught). Runs before the review check; diagnostic mode cannot bypass it | `unavailable` |
| `tts_unavailable` | No voice, voice locale differs, or the output has no such voice. **Never substitutes another voice** | `unavailable` |
| `output_unavailable` | No output node/device, or the voice names an output different from the target's speaker (`output_mismatch`; audio is never moved to another speaker) | `unavailable` |
| `diagnostic_invalid` | The diagnostic template or voice does not belong to this target | `unavailable` |
| `output_busy` | The same output is already playing another command (one at a time) | `unavailable` |

AIL's `reason` is a shared fixed list, so VCR's detailed reason goes in `data.vcr_reason`.

## 5. Result states

| Situation (fake scenario) | `status` | Notes |
|---|---|---|
| Resolution refused, output busy | `refused` | `play` is not called |
| Synthesis failed, device unavailable or start failed, and playback never started (`synthesis_failed`, `device_unavailable`, `start_failed`) | `failed` | Definitely no sound was produced; each failure has its own fixed message |
| Receipt fields not boolean, contradictory (not started yet finished), or interrupted reported before start | `unknown` | It cannot be ruled out that sound was produced |
| Only synthesis reported complete, playback never started (`synthesis_only`) | `unknown` | `synthesisComplete` does not mean the speaker finished |
| Playback started but was interrupted, timed out, lost its receipt, or the receipt's jobId or device did not match (`interrupted`, `timeout_mid`, `receipt_lost`, `wrong_job`, `wrong_device`) | `unknown` | No automatic retry (tests confirm `play` is called exactly once) |
| The selected output reports start and finish (`finished`) | `unconfirmed` | The model says "the voice command was sent, but the result is not confirmed"; fake adds "(mock)… this was fake output, no real speaker made a sound" |
| Any case | never `confirmed` | There is no independent downstream state read; `ok` is always false |

The `data` returned to the model contains only IDs and states (`mock`, target, intent, template, version, voice profile, `test_status`, job ID). It never contains the command text, the wake phrase or light names.

## 6. Model tool

`app.voice_relay.send_intent` (`reversible_write`, `api_key`/`live`, 20-second timeout). The flat schema contains only: `target_id` (enum of enabled targets), `intent_id` (enum of V1 intents), `genre` (controlled enum), `device` (enum of registered light IDs), `on`, `percent` (0–100) and `seconds` (1–3600). It has no `raw_text`, `spoken_text`, `wake_phrase`, `voice_id`, `candidateTemplateId` or `candidateVoiceId` (tests check each one). With no enabled target there is no tool. Both routes produce identical function specs.

## 7. Built-in data

- V1 intents (all `riskClass: low`): `music.next`, `music.pause`, `music.resume`, `music.play_genre`, `volume.set`, `light.power`, `light.brightness`, `assistant.timer`. There are no payment, lock, security, shopping or account intents; the policy still blocks every non-low intent.
- `google.home_mini.zh-TW.v1` and `google.home_mini.en-US.v1`: wake phrases "Ok Google" (selected) and "Hey Google". Each intent has one selected candidate template (docs/19 §4.3). There is also an unselected "play on Spotify" template with a Spotify downstream, which exists only to prove the policy blocks it. Google has no timer template (`assistant.timer` → `unsupported_intent`). Everything is `candidate` and `NOT_TESTED`.
- `apple.homepod.zh-TW.v0`, `amazon.echo.en-US.v0`, `xiaomi.xiaoai.zh-CN.v0`: empty packs.
- Four fixture voices: `google_zh_a` (Meijia, 600 ms pause), `google_zh_b` (Meijia, rate 0.9, 1000 ms pause), `google_en_a` (Samantha) and `google_en_b` (Alex). **Nobody has checked that these voices exist on any Mac.**

## 9. Acceptance criteria (VCR-0 and the fake part of VCR-1)

- [x] The three data layers and voice settings are separate, versioned and validated; targets reference by ID only.
- [x] Explicit priority; not-found and same-level conflicts are refused; candidates and voices are independent per brand.
- [x] The tool schema is identical on `api_key` and `live`; with `NOUS_VCR=off` it does not appear among model tools.
- [x] Mock never claims real-device success; finished TTS playback is at most `unconfirmed`.
- [x] Spotify downstream usage is `policy_blocked`.
- [x] Formulas are written into tests; with no data the status is NOT TESTED.

## 10. Results

Linux cloud container (2026-11-03): `npm ci` completed; `npm run typecheck` passes; `npx vitest run` ran 129 files with 2384 passed, 5 skipped and 0 failed; `node scripts/verify-aios.mjs` PASS; `node scripts/check-pstack.mjs` passes; `git diff --check` prints nothing; `node scripts/check-bilingual-docs.mjs` passes after `--record` following translation review.

An independent review (same model, separate session, reproduced with scripts) found 10 issues, all fixed with regression tests: a user config scope named `constructor` and similar crashed startup (now a validation error, and any throwing Adapter factory is logged and skipped); with a Spotify music service, another downstream label bypassed the block; Spotify text could bypass the check with full-width, zero-width or spaced forms; a wake phrase could smuggle a second command through slot words or device names; the wake phrase could come from another locale or brand; a voice's output setting could move audio to another speaker; an invalid `NOUS_VCR` still broke startup with `NOUS_AIL` off; trial group keys could collide; `candidateVoiceId` alone allowed an unreviewed template, and a target approval overrode a catalog rejection; contradictory receipts were reported as failed. The output busy lock is per process; if playback ignores abort it stays held. That is left to the real outputs of VCR-2/3 (see section 11).

## 11. Not verified

- Any real playback: Mac `say`, whether the voices exist, output device selection (VCR-2); the Pi 4 output node and its receipts (VCR-3).
- Whether Google Home Mini recognises any candidate template or voice: **NOT TESTED**.
- Echo suppression (pausing Nous's own wake word and ASR while VCR plays) is not implemented; it belongs to VCR-2/3.
- The user-triggered diagnostic screen and saving/displaying trial records are not implemented; only the data model and calculations exist.
- Siri, Alexa and XiaoAI: empty packs only, no templates.
- "Generic music playback" relies on the `musicService` the target declares. If the speaker's real default music service differs from the declaration, the policy cannot know.
- The output busy lock lives only in the core process and is per output node, not per room. After an abort, if a real output keeps playing, the lock is either released before playback ends or held indefinitely; VCR-2/3 must redesign it when real outputs arrive.
- With only negative trials, `summarizeTrials` still reports NOT_TESTED (positive trials untested) but computes `falseWakeRate`.

## 12. Rollback

- Set `NOUS_VCR=off` (the default) or remove `voice_relay` from `NOUS_AIL_SERVICES`: the Adapter is not registered and the model has no such tool.
- Set a target's `enabled` to false, or remove targets/voices from `voice-relay/config.json`: only that speaker is disabled.
- HomeBridge, other AIL Adapters and voice conversation are unaffected: an invalid config file only leaves `voice_relay` disabled, and Nous starts normally.
