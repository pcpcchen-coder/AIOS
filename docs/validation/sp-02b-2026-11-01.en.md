## 3. Rules

### 3.1 Capture and windows

- Runs only in the desktop App with “Recognise speaker during calls” on and a wake controller present (`NOUS_WAKE` on); applies to calls started by look-to-talk, the wake word or the user (17 §7.2).
- For calls started by the wake word, the pre-connection collection (SP-02a) has already stopped before the greeting decision; in-call collection starts after that, so the two are never attached to the speaker worker at once.
- One window every 6 s; the worker keeps the voiced part by volume; under 2 s nothing is sent. A window during which Nous was speaking (realtime phase `speaking`) is thrown away without computing a feature, so its own playback is not counted.
- When the call ends (phase back to off), collection always stops and the microphone is returned; a window still being computed is discarded.
- Audio stays in local memory; only the 192-d feature and voiced milliseconds go to the core.

### 3.2 Core

- `call_voice` is accepted only while the switch is on, at most 2 per second; it replies only ok and refusals give no reason.
- It compares only against the read-sentence templates (speech thresholds).
- A person is selected:
  - same person: log “與本次人物一致” (consistent with the current person);
  - another family member: log “像另一位家人（只記錄，不打斷）” (sounds like another member, logged only, no interruption), and the memory layer's suspend is not called (G2).
- No person is selected and the voice recognises a family member:
  - if the face does not disagree (no multiple faces and no other member recognised in this tracking generation) and the previous window did not point at someone else: record a voice candidate, valid for 60 s. The first time for the same person is kept so the candidate card stays matched; the memory layer is asked to ask once.
  - otherwise: the voice candidate is withdrawn, with the log “和其他證據不一致，不提候選” (inconsistent with other evidence, no candidate).
- The name may be spoken under the same conditions as face naming: “Use recognized family names in greetings” is on and the cloud naming notice has been seen. Otherwise the question is “Use your preferences this time?”.
- A new greeting decision drops the previous call's voice candidate.
- `memoryCandidate()` gives the face candidate first (same tracking generation, within 60 s) and the voice candidate only when there is none. Names given by SP-02a's voice-only test switch are still never candidates.
- Logs carry only states and relations, e.g. “通話中聲音（matched，沒有本次人物，提出聲音候選，門檻未校準）”; never names, `person_id` or scores.

### 3.3 Memory layer

- `LiveMemoryBinding.voiceCandidate()` does not ask while the opening candidate is still pending (look-to-talk or wake, before the greeting), while a candidate or a pending voice card is open, or if this call has already asked.
- The question, answer and time window reuse the face candidate: “yes” must come within 10 s after the question finishes, and the candidate must still be the same; “no” keeps household memory only. Selecting a person is not a write and needs no source ticket (17 §9.2).
- The per-utterance gate (“do not write personal memory for this sentence”) is not built: the memory layer only has epoch-level gates today (§6).

## 5. Mac trial (2026-11-01, George only)

- Switch on; George started a ChatGPT-plan voice call without looking at the screen and asked about the weather and a few other things.
- The core log has 3 lines of “通話中聲音（matched，沒有本次人物，提出聲音候選）”: the voice was recognised as George.
- First round: **“Use George's preferences this time?” did not appear**: family memory had never been turned on on this Mac (`~/Library/Application Support/Nous/memory/` did not exist and the log had no `memory:` lines), so the memory layer had no person to select. George chose to wrap up and open the PR (#78) at that point.
- **Follow-up (same day, after PR #78 was merged)**: George turned memory on in “Memory…” and allowed two accounts, then created a memory profile by typing “我是 George，記住…” in the input bar (typing only “我是 George” does not create one; this is an existing rule: no existing person and no “remember” after it means ordinary chat).
  - Second round: the profile was not yet linked to family recognition. The core logged “matched, no current person, voice candidate raised” for 7 windows, but the memory layer could not match a profile by `facePersonId`, so it did not ask.
  - Third round, after linking George to family recognition in “Memory…” and restarting Nous (current person unselected): at 08:53:45 the in-call voice matched and raised a candidate → the card “Use George's preferences?” appeared → George chose “Yes” → at 08:53:55 the log shows “本次人物 selected” and the screen shows “本次人物：George”. **Success.**
  - The card always appears; when the ChatGPT-plan voice memory consent covers it, Nous also reads the question aloud and it can be answered by voice. Whether the question was read aloud this time was not checked, and a spoken answer was not tried.
- The log-only speaker change was not tried (it needs a second family member).

## 6. Not done

- Revoking the current person on a speaker change (17 §9.2, first point): George chose log only.
- The per-utterance write gate (17 §9.2: for `ambiguous`, do not write personal memory for this sentence and show a pending card): the memory layer has no per-utterance gate; this needs changes to its write flow.
- The air-conditioner convenience limit (17 §8).
- Reading the memory question aloud and answering by voice (the third round answered on screen); a second family member; TV on; the API key route.
- Threshold calibration: SP-03.

## 7. Risks

- Uncalibrated thresholds: someone else may be taken for a family member and asked about with the wrong name; the question always needs “yes” to select, and a wrong selection can be changed on screen.
- One more microphone lease during calls and a feature computation every 6 s (tens of milliseconds); CPU and memory were not measured.
- Windows during which Nous speaks are discarded entirely, so the seconds when the user talks over Nous are not recognised.
