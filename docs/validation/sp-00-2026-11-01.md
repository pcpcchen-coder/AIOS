# SP-00 講者模型 spike 與 SP-01 聲音登記驗證

日期：2026-11-01，Asia/Taipei。分支：`claude/sp-00`（基於 main `32efe10`）。範圍：[17 §13.4](../17_Wake_Word_and_Speaker_Recognition_Plan_2026-10.md#134-交付批次與估時) 的 SP-00 與 SP-01 的登記部分。規則見 [ADR-0003 草案](../adr/ADR-0003-local-wake-and-voice-recognition.md)；臉的登記見 [ID-01 驗證](family-id-01-2026-10-25.md)。

**這批只做登記，不做辨認。** 家人可以在「家人辨識」畫面錄聲音、存成加密的聲音特徵，也可以刪除。通話中**還不會**用聲音認人，也不會因為聲音稱名（SP-02、SP-03）。登記時的一致性與重複門檻是起點，**未校準**；真人家人的分數分布還沒量。

## 2. SP-00：模型選擇

素材：macOS TTS 6 個聲音（中文 Meijia、Tingting；英文 Samantha、Daniel、Karen、Fred），每個聲音 Hey Nous＋3 句。**是合成語音，不是真人。** 數字只用來挑模型，不代表家人的辨識率。

| 模型 | 句子對句子：同聲音最低 | 句子對句子：不同聲音最高 | 判斷 |
|---|---|---|---|
| CAM++ zh-cn common（sha256 `f682b514…21fd11`） | 0.766 | 0.812 | 重疊，不採用 |
| CAM++ zh_en advanced（sherpa 原生） | 0.776 | 0.698 | 分得開，**採用** |
| CAM++ zh_en advanced（瀏覽器語意，§3.2） | 0.788 | 0.673 | 分得更開 |

- Hey Nous 對句子：同聲音最低 0.45、不同聲音最高 0.58，**重疊**。所以喚醒片段要和登記的喚醒詞模板比（[17 §4.4](../17_Wake_Word_and_Speaker_Recognition_Plan_2026-10.md) 文字相關比對），不能和朗讀句子比。這是登記要分開存 `keyword` 與 `utterance` 兩組的原因。
- 速度：sherpa-onnx Node 每秒音訊約 2–7 ms。`onnxruntime-web`（在 Node 裡跑 wasm、單執行緒）：fbank 2–6 ms＋推論 25–78 ms（片段 1–3.7 秒）。

## 3. SP-00：瀏覽器路徑

### 3.1 fbank

sherpa-onnx 的瀏覽器 wasm 沒有單獨輸出講者特徵的 API，所以採 [17 §7](../17_Wake_Word_and_Speaker_Recognition_Plan_2026-10.md) 的備案：自寫 Kaldi 式 80 維 fbank（`src/speaker/fbank.ts`）。設定依模型 metadata：25 ms 窗、10 ms 移動、`snip_edges` false、povey 窗、預強調 0.97、去直流、512 點 FFT、mel 20–7600 Hz、對數下限 FLT_EPSILON，最後減去整段平均（`global-mean`）。和 `kaldi-native-fbank` 逐格比較，最大差 4e-4（`tests/speaker-fbank.test.ts`，fixture `tests/fixtures/speaker-fbank-knf.json`）。

### 3.2 onnxruntime-web 與原生結果不同

同樣的 fbank，`onnxruntime-web` 1.30 算出的特徵和原生 onnxruntime 1.19（sherpa-onnx 用的）不同，cosine 0.83–0.99。原因在 CAM++ 分段池化的 AveragePool（kernel 100、`ceil_mode` 1、`count_include_pad` 1）：窗超出尾端時，原生 ORT 除以整個 kernel，`onnxruntime-web` 除以有效元素數（與 PyTorch 相同）。把模型改成 `count_include_pad` 0 後，原生結果與 web 完全相同（cosine 1.000000），證實就是這一點。

產品不改模型，維持清單上的雜湊。規則：**登記與辨認都在 App 的 worker 裡算**，兩邊自洽；不能拿 sherpa-onnx 原生或其他工具算的特徵來比。`model_version` 的 `preproc` 記為 `kaldi-fbank80-globalmean-v1`，模型或前處理變了，舊聲音會標成「需重錄」。

### 4.1 錄音流程

1. 開始時建立 worker、載入模型，再借麥克風：常駐喚醒有開就向 `WakeController.lease()` 租用（KWS 暫停、歸還後自動恢復），沒開就自己開，約束與即時語音相同（AEC／NS／AGC 開著）。
2. 每個提示先播約 0.15 秒的 880 Hz 提示音，再開始收音。5 次喚醒詞依序是 Hey Nous、Hello Nous、Hey Nous、Hello Nous、Hey Nous（各 2.5 秒、至少 0.4 秒人聲）；3 句朗讀（各 6 秒、至少 1.2–1.5 秒人聲）。
3. worker 以音量判斷留下有聲音的部分（20 ms 一格，門檻為 max(0.006, 安靜部分的 3 倍)，前後各留 100 ms），太小聲回「沒有聽到聲音」，太短回「念得太短」；每個提示最多試 3 次。
4. 8 段都有特徵後送到核心。核心檢查同組特徵的一致性（喚醒詞：對平均方向 ≥0.45、任兩段 ≥0.3；句子：≥0.5、≥0.4），和其他人的聲音 ≥0.8 就當成重複、不覆蓋。這些數字是起點，未校準。

### 4.2 隱私邊界

- 麥克風樣本由 AudioWorklet 經 MessagePort 直接進 worker，頁面主執行緒碰不到音訊。離開 worker 的只有 192 維特徵、有聲毫秒數與音量數字。
- 錄音與中間張量算完就以 0 覆寫；不寫檔、不連網、不用本機儲存。模型與 wasm 只從同源 `/speaker-runtime/` 讀。
- 只存加密的聲音特徵，不存錄音。聲音特徵只走 Electron IPC 到核心，不走本機 HTTP。
- 靜態檢查（`tests/speaker-enroll.test.ts`、`tests/audio-privacy.test.ts`）：`src/speaker/` 只有這 5 個檔案；沒有 `fetch`、本機儲存、WebSocket、IPC 或 console；worker 只送 `ready`／`level`／`segment`／`error`，`segment` 不帶樣本；只有 `family-view.ts` 與 `main.ts` 引用 `src/speaker/`。

## 6. Mac 上發現並修正的 bug

第一次在 Mac 上試，每一段都回「沒有聽到聲音」。原因：AudioContext 是 16 kHz 時不需要轉換，worker 收到的那塊樣本就是要量音量與收進段落的那一塊，但程式在使用前就把它覆寫成 0。48 kHz 會先轉換成新的陣列，所以不受影響；原本的測試只用了音量判斷的純函式，沒有走過 worker。修正：只有轉換過才立刻覆寫原塊；沒收進段落的才覆寫。新增 `tests/speaker-worker.test.ts`，舊程式在 16 kHz 那一項失敗，修正後通過。

## 9. 風險與限制

- 講者模型訓練資料授權照 17 §14 ② 接受並記錄；本批改用 zh_en advanced，它的訓練資料一樣沒有公開。
- 一致性與重複門檻是以 TTS 數字定的起點，真人的分布可能不同：可能拒絕正常的登記，也可能讓兩個聲音相近的家人都登記成功。
- 登記與日後辨認的麥克風不同時，分數可能下降（17 §13）。
- 錄音提示音從喇叭播出，回音消除通常會濾掉；沒有量測它是否進到錄音。
