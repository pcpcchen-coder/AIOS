# DUCK-1 validation: the duck (duck-link endpoint, duck adapter, interaction state)

Date: 2026-11-26, Asia/Taipei. Branch: `claude/duck-link` (based on main `c853078`). Scope: let Nous use a moving robot duck ([Nous Duck](https://github.com/pcpcchen-coder/Open_Duck_Mini), a fork of Open Duck Mini v2): the core gains a `/duck-link` WebSocket endpoint, a `duck` adapter (`app.duck.*`), and a duck interaction state (presence) driven by real events from the realtime voice session.

> **Follow-up (evening of 2026-11-26, branch `claude/duck-link-event-dedupe`)**: fixes events being dropped as duplicates after the duck-side program restarts. The duck side's `event_id` is a per-process counter that starts over on restart; the hub's de-duplication table used to persist across connections, so events after a restart collided (seen in Nous Duck's real-hardware test). The table is now cleared every time the duck completes `hello` (a new connection). `tests/duck-link.test.ts` gains one case that reproduces this (24 → 25 cases; the 5 test files added by this batch now total 123). Fixture tests only; not re-run on real hardware.

**This is not a hardware acceptance test, and it is not a real-voice acceptance test.** Everything is fixture tests (a fake duck labelled mock) plus one local check against the **simulated body** of the duck-side program `duckd`. Not one item has been run on a real duck, and nobody has called the duck with real realtime voice. The `NOUS_DUCK` flag is off by default; when it is off, behavior is the same as before this batch.

<a id="1-做了什麼"></a>
## 1. What was done

| Batch | Contents | Files |
|---|---|---|
| D1 | `/duck-link` endpoint: the core's http server handles one more WebSocket upgrade. The duck is the client (it reaches the core's loopback through an SSH tunnel); both sides send `hello` first, the core sends a heartbeat every 500 ms (the connection lease) and measures the round-trip time; commands are paired with `ack`; the latest `state` is kept; messages in both directions are validated against the duck-link v0 JSON Schema | `server/duck/link.ts`, `server/duck/schema.ts`, `shared/duck-link.ts`, `shared/duck-link.v0.schema.json`, `server/nous.ts`, `server/config.ts` |
| D2 | `duck` adapter: the definitions of all 17 `app.duck.*` tools are present, and **phase 1 enables only 6**: `status`, `stop`, `look`, `gesture`, `express`, `track`. The other 11 (walking, navigation, returning to charge, and so on) are `enabled: false`; they do not appear in the model's tool list and are not listed in the command table | `server/integrations/adapters/duck.ts`, `server/duck/exec.ts`, `server/duck/text.ts`, `shared/duck-capabilities.ts`, `server/integrations/index.ts`, `server/integrations/catalog.ts`, `server/messages.en.json` |
| D4a | Session observation point: `RealtimeSessions` gains an optional `onSessionEvent` (start decision, connected, live delegation, end); the core turns these events into the duck's presence (`wake`/`thinking`/`listening`/`working`/`error`/`idle`) and, after debouncing, sends it over duck-link | `server/realtime-routes.ts`, `server/app.ts`, `server/duck/session-bridge.ts`, `server/duck/presence.ts`, `server/nous.ts` |

Result semantics are the same as for the other adapters: a result is `confirmed` only when the duck accepts and the `state` read back afterwards matches (for motion tools this means only "accepted and started", not finished); accepted without a read-back is `unconfirmed`; no reply after sending, or a dropped connection, is `unknown`; the duck refusing, wrong parameters, or the duck itself reporting that it lacks the capability is `refused` (the duck's reason code is in `data.duck_reason`); no connection, nothing sent, is `failed`. When the other end is a simulated duck, the message starts with 「（模擬）」 ("(simulated)"), `data.mock` is true, and the integration status's `mock` is also true.

Safety boundary: Nous issues intent only (head target pose, gesture name, expression name). Clamping, falls, overheating, emergency stop and the connection lease are all judged locally on the duck; the protocol has no operations such as torque off, reboot or clearing an emergency stop, and the core cannot send a command that the schema does not have (there is a test).

<a id="2-旗標啟用與回退"></a>
## 2. Flags, enabling and rollback

| Setting | Default | Effect |
|---|---|---|
| `NOUS_DUCK=on` | Off | Creates the duck-link hub, handles the `/duck-link` upgrade on the core's http server, and wires session events to the duck's presence |
| `NOUS_AIL=on` plus `NOUS_AIL_SERVICES` containing `duck` | Off | Registers the `duck` adapter, which is what lets the model see those 6 tools. Listing only `duck` without `NOUS_DUCK=on` does not register it, and the log states the reason |

- When off: no hub, no `upgrade` listener (an upgrade to `/duck-link` is closed just as before), no observer on `RealtimeSessions`, no duck adapter. `tests/duck-core.test.ts` and `tests/duck-presence.test.ts` each have one item confirming this.
- Rollback: remove `NOUS_DUCK` from `.env` (or set it to `off`), remove `duck` from `NOUS_AIL_SERVICES`, and restart Nous. No settings file or data file is written, so nothing needs cleaning up.
- There is no password or key to configure. The trust boundary is the same as for the Raspberry Pi terminal: the core listens only on `127.0.0.1`, and the duck comes in through an SSH tunnel. `/duck-link` additionally does this: the path must match exactly, `Host` must be the core's own port, **every request carrying `Origin` is refused** (a browser page cannot impersonate the duck), a single message is capped at 64 KiB, there is only one duck connection at a time, and the connection is closed after 3 seconds without any message. Any program on the Pi that can reach the tunnel's port can impersonate the duck — this is the same as the Pi terminal's current situation; there is no additional device authentication.

Tunnel (choose one; the local port on the Pi must equal the core's port, otherwise the `Host` check fails):

```bash
# Mac 發起（不必開 Mac 的「遠端登入」）
ssh -N -R 127.0.0.1:8787:127.0.0.1:8787 <鴨子的主機>
# 或沿用 terminals/rpi4 的作法：Pi 發起 -L 127.0.0.1:8787:127.0.0.1:8787
```

Note: this tunnel opens the core's entire HTTP API to programs on the duck's Pi (the Pi terminal already works this way).

<a id="4-沒有驗證的事"></a>
## 4. What was not verified

- A real duck: any motion on hardware. The duck-side hardware head tests take place in the Nous Duck repo.
- Real realtime voice: no Nous that connects to a cloud model was started, and nobody called the duck by voice; how the model actually uses these 6 tools has not been observed.
- The presence timing (debounce 120 ms, `wake` at least 600 ms, `error` 1.5 s) has not been tuned against a real conversation and a real duck.
- The core knows only the session's start, connection, delegation and end; **it does not know that the model is speaking**: after connecting, the duck is always `listening`, and there is no `speaking`. Accurate listening/thinking/speaking needs the page to report its phase, which is a later batch.
- Long-lived connections, degraded Wi-Fi, and recovery after the Mac sleeps.
- Behavior inside the macOS App (Electron): it has only been run in tests of the terminal version (`startNous`).

<a id="5-使用者要怎麼試不影響正在跑的-nous"></a>
## 5. How the user can try it (without affecting the running Nous)

The steps below **have not been run by anyone** (they connect to a cloud model and make sound, so you have to start them yourself). The approach is to start a separate development instance with a different port and settings directory, leaving the running Nous untouched.

1. In a checkout of this branch: `cd prototype/ambient-shell && npm ci`.
2. In `prototype/ambient-shell/.env` (the terminal version reads this file; do not change the macOS App's `.env`) write:

   ```bash
   PORT=8790
   NOUS_CONFIG_DIR=<一個新的空資料夾，例如 ~/.config/nous-duck-dev>
   NOUS_OAUTH_PORT=1456
   NOUS_DUCK=on
   NOUS_AIL=on
   NOUS_AIL_SERVICES=duck
   ```

   You set up the sign-in or API key that realtime voice needs yourself, following [INSTALL](../../prototype/ambient-shell/INSTALL.en.md) (the new settings directory is empty, so the sign-in state of the running instance is not carried over).
3. Run `npm start` and open <http://localhost:8790> in a browser. The log should have the line 「鴨子：duck-link 已開在 ws://127.0.0.1:8790/duck-link」 ("Duck: duck-link is open at ws://127.0.0.1:8790/duck-link").
4. Open the tunnel and let the duck connect (the port must match the one above): `ssh -N -R 127.0.0.1:8790:127.0.0.1:8790 <the duck's host>`, with the duck-side `duckd` connecting to `ws://127.0.0.1:8790/duck-link`. The log shows 「鴨子：鴨子已連線」 ("Duck: the duck is connected"); the integration status on the settings page will show the duck (labelled simulated when the other end is a simulated body).
5. Start realtime voice and say 「鴨子看左邊」 ("Duck, look left"), 「鴨子點點頭」 ("Duck, nod"), 「鴨子停」 ("Duck, stop"). The duck should react when the conversation starts and ends (presence).
6. To finish: stop `npm start` and the tunnel. To go back to a state without the duck, remove `NOUS_DUCK` and the `duck` entry of `NOUS_AIL_SERVICES` from `.env`.

Still uncertain: whether ChatGPT sign-in works after `NOUS_OAUTH_PORT` is changed to 1456 has not been tried (the API key route does not go through it); when two Nous instances have realtime voice open at the same time, neither knows the other exists.

<a id="6-依賴"></a>
## 6. Dependencies

Adds `ajv` 8.20.0 (a JSON Schema draft 2020-12 validator, used only in the core and not included in the page's bundle). The integration layer deliberately added no dependencies before (`server/integrations/schema.ts`); it is added here because the duck-link contract is a JSON Schema file from another repo and both ends must validate against the same file, and a hand-written validator would drift from the schema.
