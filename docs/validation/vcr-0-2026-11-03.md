# VCR-0＋VCR-1（Fake Output）驗證：跨品牌命令查表、每台音箱的 TTS 設定與假輸出

日期：2026-11-03（Asia/Taipei）。分支：`claude/vcr-0-catalog`，從 `docs/voice-command-relay-multibrand-2026-11`（Draft PR #88，main `c88ab77` 加上 George 的 VCR 設計文件）開出。規格：[19 設計](../19_Voice_Command_Relay_Design_2026-11.md)、[實作計畫](../development/voice-command-relay-implementation-plan.md) §1、§2、[實測表](../experiments/VOICE_COMMAND_RELAY_TEST_PLAN.md)。

**本批沒有任何實體播音。** 唯一的輸出是 `FakeRelayOutput`（mock）：沒有喇叭發聲、沒有呼叫 macOS `say`、沒有 Pi。Google Home Mini 的命令模板全部是「候選、待實測」，**不是官方相容保證**，也沒有任何辨識率數據。以下測試都在 Linux 雲端容器用 fixture 執行。

## 2. 設定與啟用

| 設定 | 值 | 行為 |
|---|---|---|
| `NOUS_VCR` | `off`（預設） | 沒有 `voice_relay`：即使 `NOUS_AIL_SERVICES` 列了它也略過並記一行 log；工具表、說明與 HTTP 路由和之前相同 |
| `NOUS_VCR` | `fake` | 需要 `NOUS_AIL=on` 且 `NOUS_AIL_SERVICES` 含 `voice_relay`；Adapter 標 `mock`，工具說明前綴「（模擬）」 |
| `NOUS_VCR` | 其他值（含 `on`） | 啟動時報錯：實體播音（VCR-2／3）尚未實作 |
| `<NOUS_CONFIG_DIR>/voice-relay/config.json` | 選用 | 使用者自己的 targets、voiceProfiles、voiceDefaults、額外 commandPacks。檔案不存在時用兩個 fixture 目標；檔案不正確時 `voice_relay` 不啟用並記 log（fail closed，不擋 Nous 啟動與語音對話） |

`fake` 模式的 fixture 目標（`fixture_google_mini_zh`、`fixture_google_mini_en`）在 `reviewedTemplates` 把已選定的非 Spotify 模板標為 approved，附註「fixture only — not a real test result」，只為了讓假輸出能走到 `unconfirmed`。使用者自己的目標一開始沒有任何 approved 模板，要等實測後由使用者手動加入。

## 3. 解析優先序

模板查找由具體到一般，每一層只看 `selected: true` 的條目；找不到才往下一層：

| 順序 | 層級（`level`） | 命中條件 |
|---|---|---|
| 0 | `diagnostic` | 只有 `diagnose()` 指定 `candidateTemplateId`，而且這個模板屬於同意圖、與目標相容的 pack |
| 1 | `device_override` | `target.templateOverrides[intentId]`；所在 pack 必須與目標相容 |
| 2 | `model_locale` | pack `scope: model`，vendor＋assistant＋model＋locale 全相同 |
| 3 | `assistant_locale` | pack `scope: assistant`，vendor＋assistant＋locale 相同 |
| 4 | `vendor_locale` | pack `scope: vendor`，vendor＋locale 相同 |
| 5 | `generic` | pack `scope: generic`，locale 相同且 `compatibleAssistants` 明確列出目標的助理 |

- 同一層有兩個以上 selected 條目 → `ambiguous_template`。
- 命中的條目 `supported: false` → `unsupported_intent`，**不**往較一般的層級找。
- locale 只做完全相同比對，永遠不改用其他語言。
- 之後依序：政策 → 審閱狀態 → 聲線（`diagnostic.candidateVoiceId` → `target.voiceProfileId` → `voiceDefaults` 先型號後助理）→ 輸出端（一律是目標自己的喇叭；聲線若指定了不同的輸出端就拒絕）→ 喚醒詞（`target.wakePhraseId`，必須來自同廠牌、同助理、同語系的 pack → 同型號 pack 選定的喚醒詞 → 同助理 pack；不從通用 pack、其他廠牌或語系取）→ 套入 slot 文字 → 以正規化文字（NFKC、小寫、去空白與格式字元）再檢查一次不含任何喚醒詞。
- 沒有亂數、沒有時間：同樣輸入永遠得到同樣輸出（測試比對深度相等與 JSON 字串相同）。

## 4. refused 原因

| `vcr_reason` | 意義 | AIL `reason` |
|---|---|---|
| `unknown_target` | 沒有這個目標 ID | `invalid_arguments` |
| `target_disabled` | 目標 `enabled: false` | `unavailable` |
| `unsupported_intent` | 沒有意圖、任何層級都沒有模板、模板 `supported: false`、覆寫不相容或沒有喚醒詞 | `invalid_arguments` |
| `invalid_slots` | 缺少、多出、型別或範圍錯、燈不在目標的裝置表、套入後的文字不合法或含有任何喚醒詞 | `invalid_arguments` |
| `ambiguous_template` | 同層級多個 selected 模板 | `unavailable` |
| `not_reviewed` | 模板是 candidate（只有診斷明確指定 `candidateTemplateId` 才能試）或 rejected（目錄標 rejected 時，目標的 approved 也不能蓋過；診斷模式也擋） | `unavailable` |
| `policy_blocked` | 非低風險意圖、Spotify 下游、目標音樂服務是 Spotify 或 unknown 時的任何音樂類意圖（不看模板標籤）、正規化後的命令文字含 Spotify／聲破天（全形、零寬字元、空白都擋）；在審閱檢查之前執行，診斷模式不能繞過 | `unavailable` |
| `tts_unavailable` | 沒有聲線、聲線 locale 不同、輸出端沒有這個聲音；**不會改用其他聲線** | `unavailable` |
| `output_unavailable` | 沒有輸出 node／device，或聲線指定的輸出端和目標的喇叭不同（`output_mismatch`，不把聲音換到別的喇叭） | `unavailable` |
| `diagnostic_invalid` | 診斷指定的模板或聲線不屬於這個目標 | `unavailable` |
| `output_busy` | 同一輸出端正在播另一條命令（一次只播一條） | `unavailable` |

AIL 的 `reason` 是共用的固定清單，所以 VCR 的細分原因放在 `data.vcr_reason`。

## 5. 結果狀態

| 情況（Fake 情境） | `status` | 說明 |
|---|---|---|
| 解析拒絕、輸出端忙碌 | `refused` | 沒有呼叫 `play` |
| 合成失敗、裝置無法使用、開始播放失敗，而且沒有開始播（`synthesis_failed`、`device_unavailable`、`start_failed`） | `failed` | 確定沒有發出聲音；每種失敗各有固定句 |
| 收據欄位不是布林、互相矛盾（沒開始卻播完）、開始前就回報中斷 | `unknown` | 不能確定沒有發出聲音 |
| 只回報合成完成、沒有開始播（`synthesis_only`） | `unknown` | `synthesisComplete` 不等於喇叭播完 |
| 開始播但中斷、逾時、收據遺失、收據的 jobId 或裝置對不上（`interrupted`、`timeout_mid`、`receipt_lost`、`wrong_job`、`wrong_device`） | `unknown` | 不自動重試（測試確認 `play` 只呼叫一次） |
| 選定的輸出端回報開始並播完（`finished`） | `unconfirmed` | 模型說「已發出語音命令，但執行結果尚未確認」；fake 加「（模擬）…這次是假輸出，沒有實體喇叭發聲」 |
| 任何情況 | 永遠不是 `confirmed` | 沒有獨立的下游狀態讀取；`ok` 一律 false |

回給模型的 `data` 只有 ID 與狀態（`mock`、target、intent、template、版本、voice profile、`test_status`、job ID），不含命令文字、喚醒詞或燈的名稱。

## 6. 模型工具

`app.voice_relay.send_intent`（`reversible_write`，`api_key`／`live`，時限 20 秒）。平面 schema 只有：`target_id`（已啟用目標的 enum）、`intent_id`（V1 意圖 enum）、`genre`（受控 enum）、`device`（已登記燈 ID 的 enum）、`on`、`percent`（0–100）、`seconds`（1–3600）。沒有 `raw_text`、`spoken_text`、`wake_phrase`、`voice_id`、`candidateTemplateId`、`candidateVoiceId`（測試逐一檢查）。沒有已啟用的目標時不提供工具。兩條路徑產生相同的函式規格。

## 10. 執行結果

雲端 Linux 容器（2026-11-03）：`npm ci` 完成；`npm run typecheck` 通過；`npx vitest run` 129 個檔案，2384 passed、5 skipped、0 failed；`node scripts/verify-aios.mjs` PASS；`node scripts/check-pstack.mjs` 通過；`git diff --check` 無輸出；`node scripts/check-bilingual-docs.mjs` 在翻譯審閱後 `--record` 並重跑通過。

獨立審查（同一模型、不同工作階段，以腳本實際重現）找到 10 項，全部修正並加回歸測試：使用者設定檔的 scope 用 `constructor` 等名稱會讓啟動崩潰（改成驗證錯誤，Adapter 建立丟錯一律記 log 並略過）；音樂服務是 Spotify 時可用別的下游標籤繞過；Spotify 文字可用全形、零寬字元或空白繞過；喚醒詞可經 slot 文字或裝置名稱夾帶第二條命令；喚醒詞可能來自其他語系或品牌；聲線的輸出設定可能把聲音換到別的喇叭；`NOUS_AIL` 關閉時 `NOUS_VCR` 無效值仍會讓啟動失敗；trial 分組鍵可碰撞；只給 `candidateVoiceId` 就能試未審閱模板、目標 approved 能蓋過目錄 rejected；收據矛盾時誤判 failed。輸出端忙碌鎖只在單一程序內，播放忽略中止時會一直佔用，留給 VCR-2／3 的實體輸出處理（見第 11 節）。

## 11. 未驗證項目

- 任何實體播音：Mac `say`、聲線是否存在、輸出裝置選擇（VCR-2）；Pi 4 output node 與回執（VCR-3）。
- Google Home Mini 能否辨識任何候選模板與聲線：**NOT TESTED**。
- 回音抑制（VCR 播音時暫停 Nous 自己的喚醒與 ASR）尚未實作，屬 VCR-2／3。
- 使用者觸發的診斷畫面、trial 紀錄的保存與畫面尚未實作；目前只有資料模型與計算。
- Siri／Alexa／小愛：只有空 pack，沒有模板。
- 「一般音樂播放」依賴目標宣告的 `musicService`；若音箱實際的預設音樂服務與宣告不符，政策無法得知。
- 輸出端忙碌鎖只在核心程序內、以 output node 為單位，不是以房間為單位；中止後若實體輸出仍在播，鎖會在播放結束前被釋放或一直佔用，VCR-2／3 接實體輸出時要重新設計。
- `summarizeTrials` 只有負樣本時狀態仍是 NOT_TESTED（正樣本未測），但會計算 `falseWakeRate`。

## 12. 回退方案

- 設 `NOUS_VCR=off`（預設）或從 `NOUS_AIL_SERVICES` 拿掉 `voice_relay`：不註冊 Adapter，模型沒有這個工具。
- 把目標 `enabled` 設為 false 或刪除 `voice-relay/config.json` 中的目標／聲線：只停用那台音箱。
- 不影響 HomeBridge、AIL 其他 Adapter 與語音對話：設定檔錯誤時 `voice_relay` 只是不啟用，Nous 照常啟動。
