# Pi 部署修正與實機驗證

日期：2026-11-05，Asia/Taipei。這份紀錄涵蓋本晚的部署整合、修正與指定裝置觀察。既有畫面效能選單與 Pi 辨識 API 由上游提供；本批修正它們和 Pi 本機鏡頭、服務模式及實際取樣節奏的整合。歷史雲端驗證文件維持原結論。

## 測試組合與資料範圍

- Raspberry Pi 4，64-bit Debian／Raspberry Pi OS 桌面，Chromium kiosk，Mac Nous 核心經 SSH loopback 轉送。
- USB CCB 雙目鏡頭，capture index 0；另一個 video 節點是 metadata，不是第二路取像。
- USB EMEET OfficeCore M0 Plus 麥克風／喇叭。聲紋原先使用 Mac 上的 reSpeaker 登記。
- 原始影像、錄音、聲音特徵向量、家人登記資料、帳號、金鑰與私人部署設定不放進 repo。以下只記程式、狀態 metadata 與使用者確認。

## 程式修正

| 問題 | 最後行為 |
|---|---|
| Pi 頁面沿用 Mac 全域鏡頭開關 | `terminal-camera.ts` 只在沒有 App preload 且網址只有一個 `terminal=rpi4` 時持有本機偏好。資料存在該 Chromium profile 的 `localStorage`，初次預設關閉；安裝啟用、標籤與幾何仍由核心提供。Pi 開關不呼叫全域開啟 API，Mac 原生限制保留。關閉保存失敗時，當前頁面仍保持停止 |
| Chromium 已有權限卻卡在鏡頭列舉 | kiosk 加入 `--disable-features=WebRtcPipeWireCamera`。保留 PipeWire 音訊、既有 profile 與 Chromium 權限提示，不使用自動允許媒體旗標 |
| Mac 鏡頭關閉讓 Pi 辨識回 `ready=false` | 核心依來源頁面判斷鏡頭資格。GET／POST 設定回應，以及 SSE hello／settings.updated 都保留來源；Mac 管理仍用主視窗規則，Pi 本機關閉鏡頭仍停止臉部辨識 |
| Pi 至少每 500 ms 取樣，核心超過 500 ms 就清空證據 | 終端 ambient 證據的相鄰間隔與最新有效期限各為 2000 ms。Mac／管理流程保留 500／1000 ms。仍需三格同人物與同 scope 的證據，換人、品質失敗、多臉或追蹤／epoch／gallery 改變仍重設，沒有降低相似度門檻 |
| 未認出人時語音把助手名稱加進問候 | 中英文指示明確說明 Hello／Hey Nous 是呼叫助手，不是使用者自我介紹；開場姓名只來自核心指定句。`live:greeting_mismatch` 以正規化後的完整相等比較記偏差，原本對話過濾的寬鬆比較保留。標記不含句子、姓名或音訊，也不阻擋已播出的聲音；中斷、改寫或全形／半形等逐字稿字形差異也可能觸發，提示修正不是確定性的音訊控制 |

SSE 的終端名稱仍只是來源標記，不是新配對或驗證機制。模型、加密、管理 session 與 Mac 原生開啟檢查保留。

## 指定裝置觀察

| 檢查 | 證據與結果 |
|---|---|
| 鏡頭與語音基本操作 | 使用者確認鏡頭預覽、看著螢幕開始語音、EMEET 播放回話，以及關閉再開啟鏡頭正常。這是頭向觸發，不是校準過的眼動追蹤 |
| 服務模式 | Mac 選單顯示 Pi 已連線，核心有實際 `rpi4` 頁面心跳；服務模式恢復後 Mac 本機捕捉暫停，Pi 繼續使用自己的周邊 |
| 臉部稱名 | 使用者聽到已登記人物的名字。核心問候決策 `ok`，6 格連續證據跨 8347 ms，最新一格為 1500 ms 前。先前的 `not_eligible`、`collecting` 與 `stale` 仍屬實際失敗，不回寫成成功 |
| Pi 實際取樣 | 曾擷取到同追蹤世代、單臉、`quality=ok` 的兩格間隔 1405 ms，超過原本 500 ms 上限。2000 ms 是有界的裝置政策，並非量測後的最佳值或準確率校準 |
| 問候誤稱助手名稱 | 使用者原先聽到無姓名模板多加助手名稱；修正後，使用者在不看鏡頭、只喊喚醒詞的測試確認沒有再誤稱助手名稱。這個觀察不保證所有未來輸出都逐字相同 |
| Mac EMEET 聲紋試認 | 在 Mac 以同一支 USB EMEET 重錄既有成員的五段喚醒詞與三段朗讀後，使用者確認喚醒詞與短句兩段都認成目標人物 |
| Pi 純聲紋稱名 | EMEET 接回 Pi 後，使用者不看鏡頭，只喊喚醒詞，確認叫出目標人物。核心為喚醒詞 `matched`、融合 `voice_only_test`、臉部證據 0 格、問候 `ok`。該次問候前話語是 `too_short`，不能宣稱通話中聲紋、其他成員或其他麥克風也通過 |
| 畫面設定 | 三種效能選項可切換，重載後保留；裝置最後選「省電」，預設仍是「平衡」。解析度試用 1280×720／60 Hz，使用者沒有感受到加速，已回到原本 1920×1080／約 55.758 Hz。沒有可發表的效能增益數字 |
| 自動檢查 | 部署前最後一輪 `node scripts/verify-aios.mjs` 通過，146 個測試檔、2688 項通過、3 項略過，包含型別、建置與隔離 mock HTTP 流程。這些不是硬體準確率證據 |
| 發佈前套件檢查 | 在 Linux／Pi 環境以假指令重跑套件 dry-run 與 shellcheck，103 項通過；沒有因這項測試重裝套件或操作實際服務 |
| 發佈副本檢查 | 最終交付副本再次完整驗證通過，146 個測試檔、2686 項通過、5 項略過。相較部署前，測試執行時尚未建立 `dist` 與 `desktop/build/app`，兩項選用產物檢查略過。補建 App 後再跑 `wake-privacy`，9 項通過、1 項因 `public` 目錄不存在而略過。聲紋登記的靜態測試改用 `fileURLToPath`，修正中文路徑的 URL 編碼問題，沒有改動產品執行行為 |
| 裝置健康 | `aios-doctor` 曾 16 項全 PASS；其他時段有溫度 WARN，約 53–72°C，讀到的 `get_throttled` 為 `0x0`。這不是長時間壓力或散熱驗收 |

## 聲紋重錄操作

這次從不同麥克風登記改為實際使用的 EMEET 後成功，支持先核對登記裝置的做法。尚未量測跨麥克風準確率，不能把裝置差異視為唯一可能原因，也沒有為了消除 `unknown` 而降低門檻。

1. 備份既有加密家人資料。現有登記流程會替換該人物的聲紋，不是同時新增第二組裝置模板；臉部資料保留。
2. 暫停 Pi kiosk 與喚醒聆聽，把 EMEET 暫接 Mac，再選「返回 Mac 使用」。
3. 在 Nous「聲音輸入」明確選 USB EMEET，避免選到 reSpeaker 或 Bluetooth 項目。
4. 從 Mac 原生選單開「家人辨識…」，選既有成員並由本人完成五段喚醒詞、三段朗讀與保存確認。再做「試認聲音」。
5. 把 EMEET 接回 Pi，恢復原聲音裝置偏好。喚醒由關到開只能經 Mac 原生選單與說明確認；HTTP 開啟會回 403。
6. 將 Mac 切回服務模式，再啟動 Pi kiosk，核對 Pi 實際 EMEET 輸入與心跳。
7. 先不看鏡頭測純聲音，再分開測看著說話。用核心的聲音／臉部證據來源和實際聽到的稱名核對，不能僅憑有回話就算辨識成功。

## 操作調整與限制

[套件指南](../../terminals/rpi4/README.md)列出安裝與服務指令。本次桌面的 `Ctrl+Alt+Delete` 開關機選單、`Ctrl+Alt+T` 開終端機。暫停全螢幕使用 `systemctl --user stop aios-kiosk.service`，恢復使用 `start`；服務重啟策略會讓只按 `Alt+F4` 的視窗再開啟。

通道開機啟動、桌面自動登入與 kiosk 桌面自動啟動已設定；最近一次開機實測為 2026-11-03，本晚未重測。修改解析度、重開頁面與關閉再開鏡頭後的操作都有觀察，仍不代表重灌後的每種映像都適用。

模型冷啟動、取樣不足／過期或多人入鏡時仍可能不稱名。聲音稱名目前使用原本的測試開關，門檻未校準；這份紀錄沒有陌生人誤辨率、多人、多支麥克風或長時間測試。帳號、加密家人檔、裝置私密識別、錄音、原始向量與本機部署備份均留在原裝置，不屬於此 repo 變更。
