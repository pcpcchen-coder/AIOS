# 喚醒詞方向性：eMeet M0 Plus 診斷工具與測試流程（2026-11-08）

George 2026-11-08 回報：用 **eMeet M0 Plus**（USB 會議音箱，4 顆麥克風）收音時，從音箱某個方向說喚醒詞，成功率比較高。他要求查清原因、設計在家可以照做的測試，並找出讓各方向都能喚醒的做法。

依 George 的要求分兩批：

- **第一批（本文件）**：方向診斷工具、方向測試流程與表格、原因分析。**產品程式沒有改**：喚醒的麥克風設定、混音、門檻都和之前相同。
- **第二批**：拿到 George 的實測數字後，再依結果做修正（§8 的候選方案，做成設定，預設維持現狀）。

雲端沒有這台音箱。本文件的數字只來自合成測試音（fixture）與無頭 Chromium 的假麥克風，**不代表實機改善**；實機數字等 George 量。

## 1. 結論摘要

1. **官方規格沒有寫波束成形、聲源定位或模式切換。** eMeet 官方頁面只寫 4 顆全向 MEMS 麥克風、360° 收音、VoiceIA 4.2 降噪與回音消除；使用手冊只有電源、音量、通話、靜音、藍牙五個鍵，沒有會議／個人模式之類的設定（§2）。輸出給電腦是幾個聲道、多少取樣率，官方沒有寫，要用診斷工具在 Mac 上讀出來。
2. **Nous 送進喚醒引擎的一律是單聲道。** 麥克風開啟時打開 Chromium 的回音消除、降噪、自動增益（`src/audio-devices.ts:24`），不指定聲道數；擷取的 AudioWorkletNode 以「喇叭規則」混成一聲道（`src/audio/capture.ts:58`）。這個規則對 2、4 聲道是平均，**對 3、5、7、8 聲道只取第 1 聲道**（§3）。
3. **最可能的原因還不能只靠程式判定。** 候選原因有：音箱本身的收音與 DSP 不對稱、Chromium 的處理疊在音箱 DSP 上、聲道處理、門檻餘裕太小、說話方向與房間反射（§4）。重新取樣對每個方向都一樣，可以排除。
4. **診斷工具**（`npm run wake:direction`，只在 127.0.0.1）用產品同一份引擎與關鍵詞，顯示實際的聲道數、取樣率、三項處理的實際值、各聲道音量，並同時跑多個偵測器：產品混音 × 4 個門檻、每個聲道各一個。這樣一次測試就能比較門檻與聲道（§5）。
5. **方向測試**：8 個方向 × 2 個距離（1 m、3 m）× 2 個喚醒詞 × 每格 5 次，共 160 次，外加電視與聊天負樣本；公式與判讀規則見 §6，`tests/wake-direction.test.ts` 驗證公式。

- 「從某個方向比較容易喚醒」不能用切換音箱模式解決，因為官方沒有提供模式。

## 3. 程式核對：送進喚醒引擎的是什麼

依 main `91c6f7f` 核對：

| 步驟 | 程式 | 行為 |
|---|---|---|
| 開麥克風 | `src/audio-devices.ts:24`、`openMic` | `MIC_CONSTRAINTS = { echoCancellation: true, noiseSuppression: true, autoGainControl: true }`；不指定 `channelCount`、`sampleRate`。即時語音、常駐喚醒、聲音登記共用同一組約束 |
| 混成單聲道 | `src/audio/capture.ts:58` | `AudioWorkletNode` 設 `channelCount: 1`、`channelCountMode: "explicit"`、`channelInterpretation: "speakers"`。聲音登記 `src/speaker/recorder.ts:54` 相同 |
| 分塊 | `src/audio/capture-worklet.ts` | 只讀 `inputs[0][0]`（已混好的單聲道），約 100 ms 一塊轉移給 worker |
| 取樣率 | `src/audio/resample.ts` | AudioContext 的取樣率（Mac 通常 48 kHz）→ 16 kHz，31 階視窗化 sinc 低通（截止 7.2 kHz） |
| 偵測 | `src/audio/detector.ts`、`shared/wake-runtime.json` | sherpa-onnx v2.0.1 KWS wasm、zh-en-3M；Hello Nous 三行用全域提升分數 1.5、門檻 0.15；Hey Nous 三行各自 1.0／0.25；`maxActivePaths` 4、`numTrailingBlanks` 1 |

**喇叭規則混成單聲道時**（Web Audio API 規格的 up-mixing／down-mixing）：

| 實際聲道數 | 產品的混法 | 說明 |
|---|---|---|
| 1 | 直接使用 | — |
| 2、4 | 所有聲道平均 | 只到一個聲道的聲音會小 6.02 dB（2 聲道）或 12.04 dB（4 聲道） |
| 6 | 0.7071 ×（L＋R）＋C＋0.5 ×（SL＋SR） | 5.1 公式，LFE 丟掉 |
| 3、5、7、8… | **只取第 1 聲道** | 規格只定義 1／2／4／6；其他退回 discrete，混成單聲道時丟掉第 2 聲道以後的聲音 |

如果 eMeet 給出 3 個以上、又不是 4 或 6 的聲道，產品只會聽到第 1 聲道，這會直接造成方向差異。`tests/wake-direction.test.ts` 用合成測試音驗證：聲音只在 4 聲道的第 3 聲道時，產品混音後小 12.04 dB；3 聲道時，第 2、3 聲道的聲音產品完全聽不到。

**Chromium 的處理會影響聲道數。** 無頭 Chromium 的假麥克風（Linux，雙聲道裝置）實測：三項處理都開時，track 的 `channelCount` 是 1，送到 Web Audio 是 2 個相同的聲道（單聲道複製兩份，平均後不變）；三項都關時，`channelCount` 是 2，兩個聲道各自不同。三項都開、聲音只在右聲道時，處理後的單聲道仍聽得到右聲道的聲音（§9）。Mac 的 CoreAudio 與 eMeet 可能不同，要用診斷工具在 Mac 上確認。

## 4. 方向差異的可能原因

| # | 候選原因 | 依據 | 怎麼用診斷工具分辨 | 能不能在程式裡修 |
|---|---|---|---|---|
| A | **音箱本身不對稱**：麥克風開孔位置、VoiceIA 的降噪或內部波束、喇叭位置與回音消除 | 官方沒有公開排列與演算法；手冊側視圖標了一個 MIC hole | 產品條件下，若每個偵測器（含各聲道、各門檻）都在同一個方向較差，而且把音箱轉 90° 後差的方向跟著轉 → 是音箱 | 只能間接補償（門檻、增益） |
| B | **Chromium 的處理疊在 VoiceIA 上**：雙重降噪會削弱遠處、帶殘響的語音；兩層 AGC 可能互相拉扯 | 程式一律開三項（§3） | 比較「產品」與「三項都關」兩個條件的同一個方向 | 可以（第二批 F1） |
| C | **聲道處理**：裝置給 3／5／7／8 聲道時只取第 1 聲道；或某顆麥克風單獨成一聲道 | §3 的混音規則 | 第 3 區看「實際送進 Web Audio 的聲道數」；多聲道時看各聲道音量與各聲道偵測器在哪個方向較好 | 可以（第二批 F2、F3） |
| D | **門檻餘裕太小**：較弱方向的分數剛好在門檻下 | Hey Nous 門檻 0.25 比 Hello Nous 的 0.15 嚴；引擎拿不到分數 | 同一次測試同時跑門檻 +0.10、+0.05、0、−0.05：差的方向若 −0.05 會中、0 不中 → 門檻問題；−0.05 也不中 → 收到的聲音本身不夠好 | 可以（第二批 F4），代價是誤觸增加 |
| E | **說話方向、距離與房間**：人聲高頻有方向性；3 m 是官方收音上限；靠牆那側的反射 | 物理常識；§2 的 9.8 ft | 測試時一律面向音箱；轉 90° 檢查：差的方向不跟著音箱轉 → 是房間或位置 | 只能調整擺放 |
| F | 重新取樣 | 每個方向走同一條路徑 | — | 不是方向性原因，排除 |

## 5. 診斷工具

開發工具，不是產品畫面，只在本機 `127.0.0.1:5184`。程式在 `prototype/ambient-shell/spike/wake/direction/`。

### 5.1 在 Mac 上啟動

```bash
cd prototype/ambient-shell
npm ci
npm run wake:setup -- --product   # 已裝過可略過 / skip if already installed
npm run wake:direction
```

用 **Chrome** 打開 `http://127.0.0.1:5184/`。Nous App 是 Chromium，Chrome 的處理行為最接近。測試前在 Nous 選單列把「常駐喚醒聆聽」暫停，避免測試時真的開始通話。

### 5.2 畫面

| 區塊 | 內容 |
|---|---|
| 1. 條件 | 麥克風（選 eMeet；條件名稱會帶麥克風代號，例如 `-mic:emeetofficecorem`，不同麥克風的結果分開）、`echoCancellation`／`noiseSuppression`／`autoGainControl` 三個勾選、聲道要求（不指定＝產品；或要求最多聲道）。三項全勾＋不指定就是產品現在的設定。改了要停止後重新開始 |
| 2. 偵測器 | 門檻位移（+0.10、+0.05、−0.05，越大越不容易觸發；0＝產品門檻一定會跑）；「多聲道時每個聲道各跑一個」 |
| 3. 實際收到的聲音 | 瀏覽器回報的實際值：三項處理、track 的聲道數與取樣率、裝置能力範圍、AudioContext 取樣率、**實際送進 Web Audio 的聲道數**、產品會怎麼混成單聲道；各聲道 RMS（dBFS）與峰值；每個偵測器的狀態與觸發次數 |
| 4. 方向測試 | 選方向、距離、喚醒詞，按「說一次」（或空白鍵）：嗶一聲後 5 秒內說一次，結束時每個偵測器記中或不中。偵測器全部載入完才能開始。每格滿 5 次自動換下一格；「刪除上一次」只刪這次開頁後記下的測試，並把選單退回那一格。空白鍵一律是「說一次」（焦點在按鈕上也一樣）。「負樣本」計時並記誤觸。時間窗以外的觸發記為「未提示觸發」 |
| 5. 結果 | 選條件與偵測器，顯示 8 方向 × 2 距離 × 2 喚醒詞的表、各方向合計與 Wilson 95% 區間、方向差距、最差方向、每小時誤觸。「匯出」產生 JSON 與 CSV，只有次數；JSON 可以貼回來「匯入」，匯入會**取代**目前的結果（同一份貼兩次不會算兩倍） |

**偵測器怎麼排**：依實際聲道數排出 `product+0.00`（一定有）與每個勾選的門檻；聲道數不是 1、2、4 時加 `average`（全部平均；6 聲道產品用 5.1 公式，也和平均不同）；多聲道時再加 `ch1`、`ch2`…（產品門檻）。最多 10 個，超過時紀錄區照實寫出略過幾個。

**引擎拿不到分數**：sherpa-onnx KWS 的結果只有關鍵詞、token 與時間，沒有分數。工具改用「多個門檻同時跑」：中了的最嚴門檻就是這次的餘裕。

### 5.3 隱私與限制

- 音訊只在記憶體：AudioWorklet 直接把樣本轉移給偵測器 worker，主執行緒只收到音量數字與觸發事件。不錄音、不建 blob、不寫檔、不用瀏覽器儲存；網路只有同源讀 `/wake-runtime/` 清單上的檔案，引擎載入完就關閉網路（產品的 `runtime-net.ts`）。開發伺服器對每個回應（含偵測器 worker 的腳本）都送同一組只限同源的 CSP，`/wake-runtime/` 和產品核心一樣每次讀取都核對 SHA-256，不符就 404。`tests/wake-privacy.test.ts` 的靜態掃描涵蓋這個資料夾，`tests/wake-direction.test.ts` 另檢查 CSP、檔案白名單與雜湊核對。
- 結果不會自動保存。**重新整理頁面就沒了**，每做完一段請按「匯出」，把 JSON 貼到備忘錄。
- CPU：每個偵測器各跑一次 KWS。WK-00 Mac 量到 Renderer 裡一條獨立執行緒約 6.7% 單核（當時推測是 KWS worker；整個喚醒約 14% 單核），以此估計 6 個偵測器約 6 × 6.7% ≈ 40% 單核（估算，未在 Mac 上量）。
- 這是 Chrome 分頁，不是 Nous App；兩者都是 Chromium，但版本可能不同。

## 6. 方向測試流程（在家照做）

### 6.1 擺放

1. eMeet 放在平常的位置。**0° 定為 Type-C 孔那一側**，從上往下看順時針 45°、90°…315°。
2. 在 8 個方向的 1 m 與 3 m 處貼膠帶標記（從音箱中心量）。
3. 安靜房間：電視關、Nous 不說話、Nous 的常駐喚醒聆聽暫停。
4. 每次都**面向音箱**、用平常的音量說；站或坐固定一種。

### 6.2 要跑的條件

| 代號 | 條件 | 用途 |
|---|---|---|
| **P（必做）** | 三項全勾、聲道不指定（`ec1-ns1-agc1-ch:default-mic:…`） | 產品現況；先找出差的方向 |
| **R（建議）** | 三項都不勾、要求最多聲道（`ec0-ns0-agc0-ch:max-mic:…`） | 看 Chromium 的處理是否造成差異（原因 B），以及 eMeet 是否給出多個聲道（原因 C） |
| N（R 明顯較好時） | 只開 echoCancellation（`ec1-ns0-agc0-ch:default-mic:…`） | 分出是降噪／自動增益造成，還是回音消除 |

每個條件完整一輪是 8 × 2 × 2 × 5 = **160 次**。每次約 8.2 秒（嗶聲 0.2 秒＋時間窗 5 秒＋準備約 3 秒），160 × 8.2 秒 ≈ 1312 秒 ≈ 22 分鐘，再加走到 16 個位置的時間。時間不夠時用**簡短版**：只做 3 m、只說 Hello Nous，8 × 5 = 40 次。

### 6.3 加做

- **轉 90° 檢查**：條件 P 做完後，把音箱順時針轉 90°，只做最好與最差的兩個方向（3 m、Hello Nous、各 5 次，共 10 次）。差的方向跟著音箱轉 → 原因 A；沒跟著轉 → 原因 E。
- **負樣本**：條件 P 至少電視（英文新聞台最好）30 分鐘、聊天 10 分鐘；條件 R 也想採用時，R 也要做同樣的負樣本。

### 6.5 公式

- 每格成功率 = 中的次數 ÷ 說的次數。
- 方向合計 = 該方向所有距離與喚醒詞加總後相除（不是把各格比例平均）。
- 方向差距 = 有資料的方向中，最高成功率 − 最低成功率（以百分點表示）。
- Wilson 95% 區間：p = 中 ÷ n，z = 1.96，中心 =（p + z²/2n）÷（1 + z²/n），半寬 = z·√(p(1−p)/n + z²/4n²) ÷（1 + z²/n）。例：5/5 → 56.6–100%；0/5 → 0–43.4%；3/5 → 23.1–88.2%。
- 每小時誤觸 = 誤觸次數 ÷（秒數 ÷ 3600）。例：30 分鐘 2 次 → 4 次／小時。

`tests/wake-direction.test.ts` 用上面的例子驗證這些公式。

### 6.6 怎麼判讀

- 每格只有 5 次，**一格差 1 次是雜訊**（區間大幅重疊）。看方向合計（每方向 20 次）與最差方向。
- 某條件比 P 好，要同時滿足：最差方向的合計至少多中 4 次（20 次中，即 +20 個百分點），而且電視的每小時誤觸沒有增加。
- 門檻：差的方向在 `product-0.05` 會中、`product+0.00` 不中 → 可以考慮放寬門檻（F4）；`product-0.05` 也不中 → 收到的聲音本身不好，先試 F1／F5。
- 多聲道：某個 `chN` 在差的方向明顯較好 → 考慮 F3（各聲道分別偵測）。

## 7. 其他產品怎麼做多方向喚醒（參考）

多麥克風喚醒的常見做法是先做波束成形，再在每個波束上各跑一次喚醒偵測，或先挑最可能有喚醒詞的波束再偵測；各波束都跑偵測比較吃運算。專利例如 [US 11335331 Multibeam keyword detection](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/11335331)（每個波束一個偵測器，再合併判斷）、[US 11337173 Method and device for selecting from a plurality of beams](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/11337173)、[US 9734822 Feedback based beamformed signal selection](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/9734822)（以喚醒詞的信心值回饋選波束）。（2026-11-08 搜尋，只作參考，沒有逐篇細讀。）eMeet 這類會議音箱在裝置內處理、只給電腦處理後的結果；如果它只給單聲道，Nous 這邊能做的就是不重複處理、調整門檻或增益，沒辦法自己做波束成形。

| 假麥克風內容 | 條件 | track 聲道數 → Web Audio 聲道數 | product +0.10／+0.05／0／−0.05 | ch1 | ch2 |
|---|---|---|---|---|---|

| 單聲道 | 三項都關、不指定 | 2 → 2 | 10／10／10／10 | 10 | 10 |
| 只在右聲道 | 三項都關、最多聲道 | 2 → 2 | 8／8／8／8 | **0** | 9 |
