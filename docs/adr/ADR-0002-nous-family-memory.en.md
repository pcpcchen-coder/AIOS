# ADR-0002: The local Nous core manages family memory

Status: **MEM-0 isolated implementation started at the user's request; product release is not approved**. Date: 2026-10-26. Baseline: `ca7a8fe`. After initial design delivery, a separate implementation conversation delivered the core-private foundation, still disconnected from product routes. See [16 family memory layer design](../16_Nous_Memory_Layer_Design_2026-10-26.en.md) for behavior, fields, wiring, and acceptance, and [MEM-0 validation](../validation/memory-mem0-2026-10-26.en.md) for actual differences.

<a id="問題與現況"></a>
## Problem and current state

Ordinary Nous chat has only page context, and live calls do not load previous content. Tasks and artifacts persist, without preference extraction or retrieval. Family recognition stores only names, face features, and related metadata, for addressing people only. Direct Codex-backend use does not access Codex App / CLI memory.

Nous must therefore own people, sources, corrections, and revocation, then supply necessary excerpts to the current model. Providers cannot maintain incompatible household truths independently.

<a id="呼叫端的用法"></a>
## Caller usage

- With a current person selected, an explicit “remember that I don't eat cilantro” invokes `memory.change`, which validates the core source ticket and persists before returning a success receipt.
- New-conversation adapters use `memory.withContext` for permitted excerpts. On correction, forgetting, or person switch, the service aborts outputs holding old content.
- “What do you remember about me?” uses `memory.inspect` for an on-demand list. It also queries operation results after interruptions.

For voice, `withContext` lasts until the entire call ends, not merely the connection handshake. Models receive compact facts, never person permissions, source tickets, or storage formats.

<a id="建議形狀"></a>
## Proposed shape

One `MemoryService` owns policy and writes. A private `store` handles encryption, atomic replacement, and deduplication. Persist one encrypted snapshot, rebuilding local indexes only in memory. Each write atomically commits facts, versions, consent, and operation receipts without body text.

Version one serves a single Mac with at most 1,000 ordinary memories, without a persistent data service. Profiles and face enrollment use different IDs. Spoken self-identification selects ownership of household-shared preferences and grants no private access.

Initially provide explicit remember, correct, forget, and on-demand inspection. Automatic organization proposes candidates only in later opt-in batches. Do not store full conversations, unawakened audio, or raw images initially. Data is encrypted locally. Authorized use still sends necessary excerpts to the current model, so transmission consent needs a separate explanation.

<a id="方案比較與綜合決定"></a>
## Alternatives and combined decision

Two independent designs were compared and cross-checked by another review seat using the same model. This is independent design review, not cross-model diversity or a performance experiment.

| Option | Complexity it hides | Added cost and limits | Decision |
| --- | --- | --- | --- |
| A: Encrypted aggregate snapshot + in-memory retrieval | One commit for facts, receipts, and revocation version, without a second persistent index | Full rewrite per update. Must handle single writer, capacity, and failure recovery | Initial foundation |
| B: SQLite transactions + encrypted fields + in-memory retrieval | Clear multi-table atomic updates, operations, and dependencies | Runtime / Electron packaging, migrations, WAL, and encrypted-field policy expand verification | Reevaluate when volume or dependencies require it |
| Historical: Plaintext Markdown + FTS5 | Direct human editing and rebuildable full-text index | Personal data spreads into bodies, indexes, and backups. Files and indexes remain dual state requiring consistency | Not the initial default. Markdown only for explicit export |
| External memory service / framework | May provide storage or retrieval | Cannot replace Nous person attribution, source authorization, call revocation, or sharing policy | Not selected initially. No new claim about specific third-party versions |

Cross-review rated personal privacy, reliable updates, actual integration, MVP experience, and maintenance cost from 0–4 each. A scored 17/20 and B 16/20. Scores record judgment and have no statistical meaning. A wins because data is currently small, single-writer ownership is appropriate, and encrypted-storage experience already exists. SQLite integration costs do not yet justify themselves.

Adopt persistent receipt queries, revocation versions, and derived-source dependencies from B, within A's same snapshot, without another writable source. Five review findings are now in document 16's contract: whole-call lifecycle, tickets bound to actual commands, receipts without leftover body text, no memory copied by model delegation into plaintext tasks, and real presentation reasons for clarification cards.

<a id="接受的取捨"></a>
## Accepted tradeoffs

- Initial personal preferences are grouped by person but usable throughout the household. Individual secret spaces need separate authentication. Face calibration is incomplete and gains no broader authorization role.
- Snapshots are easier to audit, but capacity, write times, and Keychain behavior must first be measured on target Mac. Do not claim larger-volume suitability without evidence.
- Local forgetting clears active memories, sources, and affected context. It does not guarantee erasure of provider-received data, exports, or APFS / system backups.
- API-key voice receives no memory before reliable disconnect, playback stop, and reconstruction pass. Live-route results cannot substitute.
- Existing TaskStore is plaintext. Initial memory is excluded from background tasks, and memory-bearing model summaries or transcripts cannot become task titles. Task memory waits for protected artifact storage.
- Initial text retrieval does not guarantee complete semantic recall. Identify gaps with Chinese tests before deciding on vector or SQLite indexes.

<a id="歷史提案與遷移"></a>
## Historical proposals and migration

“ADR-001 memory layer” in 08 was a historical task name, not an implemented memory ADR. Existing `ADR-0001` now covers family recognition. This document uses `ADR-0002` to avoid confusion.

No old memory database currently needs migration. A future snapshot-to-SQLite change first supplies a versioned, integrity-checked, recoverable one-way migration. Switch the sole writer only after confirming the new database. Never allow simultaneous edits to old and new stores. Migrate people, consent, versions, deletion tombstones, and deduplication state, not just memory bodies.

Retain historical content in 01–03, 08, and 13, linking this proposal from status and indexes. Revise against current code and tests before adoption. This design is not an approved product capability.

<a id="待證明與下一步"></a>
## Unproven items and next step

MEM-0 first confirms secure-storage interfaces in packaged Electron, single-writer recovery, source tickets, and actual revocation on both voice routes. Capacity has isolated evidence below. The 50 ms retrieval and 300 ms write budgets remain unmeasured targets.

2026-10-26 MEM-0 isolated addendum: Verified packaged Electron 44.9.3 interfaces, snapshots / native locks, crash recovery, 1,000-item capacity, and source / revocation contracts. A separately packaged App passed encrypted-snapshot storage and cross-process restart readback with real Keychain. Formal Nous signing, actual denial, performance, and physical voice remain pending. Full product service and profile-management interfaces are not integrated. Operation IDs now use a UUIDv7 shape with an immutable time prefix, preventing altered-time replay of the same ID after receipt eviction. This batch's record contains reasons and evidence.

Whether private memory belongs in near-term scope, and how voice sources avoid false writes from television or bystanders, remain product and hardware questions. Version one limits scope to household-usable data and confirmation when unclear. The next acceptance-testable implementation after MEM-0 is the single-person loop of explicit saving, restart retrieval, correction, and forgetting.

MEM-2 addendum, 2026-10-30. ChatGPT plan realtime voice (Codex live) is wired to the same `MemoryService` (new file `server/memory/live.ts`); cloud tests pass, the Mac gate has not been run, and product release is still not approved. Consistent with this ADR's shape: `withVoiceContext` covers the whole call (the lease is held until `LiveCall.closed`), and revocation first blocks output, tells the page, and closes the sideband before waiting for the page's stop report. New or different: (1) a separate consent key `codex` (shared by ChatGPT plan realtime voice and the Codex it delegates to), not reusing ChatGPT consent; (2) boundary cleanup limits are per route (3 s for live), and if no stop report arrives within 1.5 s, Electron force-mutes and live memory is disabled until restart; (3) **for voice remember, correct, and forget, a spoken confirmation is the primary way and the on-screen card the alternative (George's decision of 2026-10-30)**, which differs from 16 §5 (“when the voice source cannot be reliably distinguished, only show a pending card and do not commit automatically”): the phrase must come from a sideband user final transcript, the model must have read the question and the user must start speaking after it finished playing, within 15 s after the question was read, as an anchored whole-sentence match, not an echo, with an unchanged generation, and once per card; the ticket and the fact's source are recorded as `voice_confirmed`. **The residual risk is a mistaken save when a TV or another person happens to say the phrase**; the core has no speaker recognition and can only reduce the chance; what the model itself says can never create a memory. Without codex consent, realtime voice is the same as before MEM-2: no memory rules and no memory metadata spoken. (4) Forget, correction, and person switches rebuild the call, whose first sentence is fixed and content-free; (5) a call carrying memory never delegates automatically. The API key path still injects no memory (MEM-3). Differences, cloud evidence, and Mac steps 0–11 are in [MEM-2 validation](../validation/memory-mem2-2026-10-30.en.md).

MEM-4a addendum, 2026-10-30. Background tasks are wired to the same `MemoryService`; the cloud tests pass and the Mac gate has not been run, and **memory for background tasks is off by default** (enabled only when `NOUS_MEMORY_ROUTES` lists `task`). Consistent with this ADR: the same retrieval (8 facts, 4 KB), consent, source tickets, and mutex; a delegated title can only be the user's original sentence. New or different: first, per George's decision, the macOS App encrypts all tasks (`server/sealed-vault.ts`: one file per record in `userData/data/sealed/`, one data key per file, AES-256-GCM, wrapped by safeStorage, 0600 / 0700, fsync; deletion is file deletion, not a cryptographic erase), outward channels get shells only, and the existing plaintext is migrated once inside the App with the backup kept until the user confirms deletion; the browser build does not encrypt; second, task encryption does not share the memory file's writer lock because it must work whether or not memory is on, while the dependency index is still written only by `MemoryService`; third, the memory snapshot gains `results` and is written as version 3 only when the first protected result is created, and older Apps reading it disable memory; fourth, revoke propagation is computed inside the same `MemoryService.commit` (forget, correct, consent revocation, person deletion, memory off, expiry), stopping running tasks and deleting the encrypted files of finished results, while switching person or idling does not abort; fifth, the boundary gains the route `task` and a one-time delegation ticket; sixth, delegations from realtime voice still go through `delegatePolicy` to the original-sentence card (MEM-4b); seventh, after the same day's independent review: unreadable encrypted files are not treated as orphans, there is no protected delegation unless tasks are actually encrypted, only tasks whose title is the user's own sentence re-retrieve memory on redo, and the task titles a model sees depend on each target's memory consent and the person (realtime voice included, George 2026-10-30). MEM-4c addendum, 2026-10-30. The search index for protected results and the core's in-memory plaintext lifecycle; cloud tests pass and the Mac gate has not been run. Consistent with this ADR: the index lives only in RAM, can be rebuilt, and is never written to disk (the same as document 16's rule that the in-memory index can be rebuilt and there is no second writable Markdown or vector database); withdrawals are still computed in the same `MemoryService.commit`. New or different: (1) finished protected tasks keep only a shell in core RAM and are decrypted from the sealed files only when needed, with at most 16 kept in RAM; on OS lock, sleep, 10 minutes of idle (`PLAINTEXT_IDLE_MS`, not the 30-minute current-person idle), memory off, memory-layer close, and App quit, the decrypted content, the inverted index, the title cache, and `CONTENT_CACHE` are dropped; queued and running tasks keep their content; (2) the in-App results history uses an inverted index that lives only in RAM (UTF-16 characters and character pairs, folded fields only), with results identical to the scan item for item, snippets decrypted only for the current page, and scope (D2) applied before decryption; (3) `MemoryServiceOptions` gains `holdResults` (between writing the snapshot and propagating to the task side, results being withdrawn are shown only as shells) and `onPlaintextDrop` (memory off, memory-layer close); (4) a key that is unavailable while reloading is reported honestly; (5) following the same-day independent review, every drop sends a content-free notification through the main process and the page clears its own caches and results history view; whether the task file and the result file were written is tracked separately, and a task can be dropped only when both are; the menu-bar "all" scope also opens the memory file first, so a withdrawal that was not fully propagated before a crash takes effect first. The MEM-4a residual risk "core memory holds plaintext" narrows to: queued and running tasks, at most 16 warm tasks and the index (a folded copy of the content), and the one-time verification at startup; dropping only releases references and is not a secure wipe (the JS heap and GC may keep copies). Mac steps 1–12 are in [MEM-4c validation](../validation/memory-mem4c-2026-10-30.en.md).

MEM-5a addendum, 2026-10-30. This is the first step of this ADR's "automatic curation only proposes candidates in a later opt-in batch"; cloud tests pass, the Mac gate has not been run, and it is **off by default** (`NOUS_MEMORY_ROUTES` must list `suggest`, and `settings.suggestions` must be turned on in the memory manager with the manager token). Same-day independent review fixes: whole-turn judgement, the candidate must be the first clause, whole-turn exclusion of proxy framing and special categories, object length limits, a fix for the control characters in the PIN rule of `SENSITIVE`, and no `by` for the memory manager or minors. Offline metrics (written alongside the rules, not an independent evaluation set; 19.6% on the reviewer's adversarial set before the fixes) and every decision pending George's confirmation are in [MEM-5a validation](../validation/memory-mem5a-2026-10-30.en.md).

MEM-5b addendum, 2026-10-30. This is the first implementation of this ADR's "later summaries record full dependencies and are removed when their sources are forgotten"; cloud tests pass, the Mac gate has not been run, and it is **off by default** (`NOUS_MEMORY_ROUTES` must list `work_summary`, and tasks must really be stored encrypted). Consistent with this ADR: writes still go through the single `MemoryService` entry point; nothing is saved unless the user clicks in the trusted main window (direct confirmation; the source ticket deterministically reparses the original sentence the core holds, and the task ID can only be one listed on the core's card); the value is the user's own words, with no model summary, task title or result; retrieval follows the normal person, expiry and consent rules. New or different: first, `fact.kind` `work_summary` with `derivedFrom: { taskId }` (already reserved in MEM-5a's version 4), linking exactly one protected task, with no expiry; second, the choice card lists only tasks that succeeded in the last 24 hours, are not withdrawn, are in D2 scope and are readable (at most 5), with titles over IPC only; third, cascading revocation (after same-day independent review M1 and m7): work decisions are forgotten, to a fixed point within the same commit, only when a result is withdrawn because a memory it used was forgotten, corrected or expired, or its person deleted; turning memory off, revoking consent and dependency-index overflow only withdraw results and keep work decisions; task deletion (HTTP, no memory ticket) does not change memory directly, and the reconcile on opening the memory file and on the trusted main window's turn/list purges only tasks that no longer exist, with retrieval excluding them before that; nothing is purged when the task side is not sealed or the key is unavailable, and unreadable tasks are not purged (consistent with MEM-4a B1); fourth, revocation ignores the flag. All decisions pending George's confirmation (W1–W19) and the residual risks are in [MEM-5b validation](../validation/memory-mem5b-2026-10-30.en.md).
